# S3：从后端到看得见 —— 一次「干了 90% 的活但用户什么都看不到」的现场复盘

> 学在公开素材 · 草稿 v0.9（2026-08-27，OntoRun 项目）
> 发布前需独立 red-team 审查（项目铁律：不接受自评定稿）。本文所有数字可在仓库 git log、测试输出与 curl 记录中复核。

## 一、症状

S3 收口时后端成绩单其实不难看：安平金控模拟企业 **54 张表 / 436,266 行**确定性数据、**33 对象 / 37 链接 / 9 动作**的风险本体、真实写回的动作引擎（冒烟 9/9）、P95 158ms 的受限查询引擎、全量 pytest 684 passed。但项目一把手打开演示环境只留下三条意见：

1. 看不到 DES 企业模拟升级的变化，连个界面都没有；
2. 演示环境丑，黑乎乎没美感；
3. 看不到数据表/本体/对象，看到的还是上一阶段的旧数和空表。

三条意见指向同一个事实：**这 90% 的实质工作里，「让它被看见」这一层的完成度是零**。

## 二、真凶不在前端

按惯性假设，这是「前端没接好」。排查第一层就推翻了它——风险数据浏览页一刷新就是 INTERNAL_ERROR：

~~~
File "src/ontology/registry.py", line 93, in object_type
    return self._objects[name]
KeyError: 'risk_customer'
~~~

注册表里的键全是驼峰类名（RiskCustomer），而演示前端、物化快照、文档体系统一走 snake_case 的 api_name（risk_customer）。/risk-objects/{type} 直接把 URL 参数塞进字典取值，于是：**所有 33 个对象在真实使用路径上一个都查不了**。「全部可查、冒烟 9/9」没有说谎——但那是在测试自己的宇宙里成立的：测试恰好也用了正确的名字。这个案例让我们把「承诺必须机器验证」升级成两问：*测试验证的是实现，还是使用路径？*

顺着同一根因又挖出两层：

- **数据模型臆造**：CoDebtCustomer 本体照 M2 设计稿写了 codebt_id 等字段，而 DES 流水线生成的真相源表 ap_codebt_customer 里根本没有这些列（真实 PK 是 codebt_customer_id）。设计稿和生成器分头演化没人对账——单一事实来源失守的经典形态。
- **fail-closed 清单过期**：「无源表不可查」拒答清单里躺着的四个对象早在提交 e88e558 就已映射了真实表。保守机制本身是对的，但保守的前提清单没有跟着演化，就从防呆变成了挡道。

## 三、结构补课：先让世界自洽

在动任何视觉之前先把路修通，避免精修被返工覆盖：

1. **修路径**（commit 8be37e9）：URL 参数做名称归一化（两种命名都可查）；CoDebtCustomer 字段按 DDL 真相源改正；拒答清单清空但机制保留（新增未物化对象仍要登记）；导出脚本加通用兜底采样——19 个主线外对象此前 sample=0，点开还是空表。完成后 66 个探针（33 对象 × 双命名风格）全部 200，这是当场扫出来的，不是推出来的。
2. **填存储**（33b967f）：把本体行程序化 seed 进构建段存储，builder 页面从空表变成 33/37 行。行内容由注册表导出而非手抄清单，对象链接以 draft 态入库——发布动作不越权代做。
3. **给 DES 一张脸**（f27cbd4）：新端点扫描企业目录返回实时统计（逐表 COUNT(*)，manifest 缺的字段如实 null 不编造），配浅色概览页。顺手长出一个意外价值：页面把实时行数与生成清单对账，**昨天人机双签真实写回的 +1 行被自动标注出来**——「模拟数据被真实动作改写过」这件事第一次变得肉眼可见，而这正是本项目「写回真实可验证」的研究卖点。

## 四、视觉：taste 是规格，不是感觉

深色风控风被明确否决后，方向收敛为「浅色专业金融风」。把它翻译成可派活、可验收的约束而不是形容词：

- 全站 LIGHT 锁定（theme.darkAlgorithm 全面移除）；冷灰白底一族（#f5f6f8/#ffffff/#e5e8ee），禁止冷暖灰混用；
- 唯一强调色克制蓝 #2a50ce（白字对比实测约 6.6:1 过 AA），红橙黄绿只保留给预警语义色；
- 圆角只剩 8/6 两档；阴影带色调且单层；大数字 tabular-nums；
- 产品决策：对话不再独占一页，做成数据浏览右侧常驻的分屏工作台——边看五万行真实数据边发起自然语言处置、走人机双签。

设计纪律方面站在既有 AntD 单一系统上做 token 化定制，反模板清单里真正起作用的是几条硬规则：单一主题锁定、单一强调色锁定、CTA 意图去重（原来 Landing 上有两个同意图按钮）。雷达扫描动画这类「工业风装饰」整体退场，最终 22 个文件改动静减负、深色遗留 grep 归零。

## 五、诚实的门禁

阶段末全量 pytest **698 passed / 2 skipped，10 分 18 秒零回归**，全仓 lint 清零。中间有一个值得记录的小插曲：子代理交付时报「18 个前端测试全绿」，验收方独立复跑却出现 3 个失败。追查结论是高负载下异步用例顶穿了 5 秒默认超时（单独复跑全过，断言本身没错）——但「重跑就绿」不该留给用户，放宽到 20s 并在同样负载条件下复验通过。交付报告与验收结论冲突时，以验收环境的复跑为准，这条纪律这次真的用上了。

## 六、方法论从里面长出来的部分

1. **可见性是语义接口的一部分**。本体、写回回路、审计链做得再实，如果使用者打开的第一个界面是 500 或空表，系统的可用性在他的坐标系里就是零。「研究对象锚定」在这里的具体含义是：让 33 个对象、9 个动作、每一次状态迁移都能在界面上被指认。
2. **两套标识并存是债**。CamelCase 类名（内部键）与 api_name（对外契约）并存本身可以是合法设计，但边界处必须显式适配层归一化，否则每个新消费方都要踩一遍 KeyError。
3. **承诺分级验证**。「全部可查」这句话，测试宇宙给了第一级确认，跨命名风格的实时探针给了第二级。高风险承诺值得两级都要。
4. **保守机制的清单也要进 CI 视野**。fail-closed 拒答是好机制，但它依赖一份会过期的清单；清单过期的唯一解药还是机器验证（本次用「33 对象按 api_name 全量遍历」的回归测试封死）。

## 七、尾巴（如实）

- DDD 业务域目前只存在于人读文档，des_enterprise.yaml 只有身份三字段——企业建模的 STEP2 产物该落盘为机器可读资产，概览页的业务域区块正等着它；
- 构建段的 draft 行批量 review/publish 进运行时图谱正在进行中；
- 测试环境仍有 React act() 告警噪音与 axe-core 可达性复核两项抛光未完。
