# 财富广场·mock 数据方案 v0.1（2026-09-10 定稿，实际生成排 09-11）

> 目的：**验证链路 + 理解业务**，不是数字真实。等真实数据导出手续期间，用它把语义层/编译器/对账回路的工程链路先跑通。演示时必须标注"仿真数据"。

## 一、范围：核心链路 6 张表（不是全部 19 张）

```
dim_cu_usr_info_df ──段A(直注,排除麦当劳/中信)──┐
dwd_cu_actv_df ─────段B(激活,限麦当劳/中信)────┤→ dwd_cu_rgst_fin_di → ads_rgst_chnl_cnt_df
dim_ch_chl_df(三级渠道) ─────────────────────┘        ↑
dim_pb_date_yf(日期维) ───────────────────────────────┘
```

对应操作单 C2 的"必给"表集，与真实对账链路同构。

## 二、规模与形状（小数据，本机零压力）

| 维度 | 值 |
|---|---|
| 用户 | 2,000 个（usr_id 顺序号） |
| 时间 | 2026-07-01 ~ 08-31，62 天 |
| 渠道 | 15 个：5 一级 / 10 二级 / 15 三级（含麦当劳、中信书院、中信优享+公众号、企微） |
| 注册分布 | ~70% 金融渠道直注（段A）/ ~30% 麦当劳·中信（其中 ~60% 在窗口内激活转段B） |
| 激活规则 | 造 if_act 标记 + actv_tag 两类 + 少量重复激活（验 row_number 去重） |
| 特意埋的 corner case | ①渠道编码不在维表的 3 条（验 left join 落 null 组+I1 拦截）②一人多账号 2 例（验去重键）③同日注册+激活 5 例（验段A/B 边界） |

## 三、生成策略（先明细、后按 ETL 逻辑聚合，保证自洽）

1. 生成用户维快照（62 天逐日，模拟每日新增）；
2. 按 KPI 口径规则（口径发现卡片卡1）生成 dwd_cu_rgst_fin_di：段A+段B union、if_act/激活去重/渠道约束全部按真实 ETL 逻辑实现；
3. **用数仓真实 ETL SQL 的聚合逻辑**（ads_rgst_chnl_cnt_df 脚本的 5 时间口径 cross join 日期维）从 mock 明细算出 mock ADS——不是独立造数，是从明细聚合出来的，保证 Σ自洽（I1 可验）；
4. 入库 DuckDB：data/fortune_mirror.duckdb，schema 对齐 DDL（raw 区）。

## 四、验收（做没做成的判据）

1. mock 明细按 ETL 逻辑聚合 = mock ADS 逐格相等（自洽对账通过）；
2. 埋的 3 类 corner case 在聚合结果里表现出预期异常（null 渠道组出现且 Σ≠总）；
3. T2 编译器开发可用它跑通"问题→原语→SQL→数字"。

## 五、明确不做

- 不还原全部 15 个 ETL 脚本（实名/授权/转化率链路二期再扩）；
- 不追求分布真实（渠道占比是拍的，数字结论不可外推）；
- 不替代数字对账——真数据到位后重跑 C1/C2 流程。
