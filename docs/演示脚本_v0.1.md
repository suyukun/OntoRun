## 2. 段②对象浏览（0:45–1:45）——本体驱动 UI

### 讲稿（约 150 字）

> "界面上所有东西都不是硬编码的，而是由一份**本体 schema** 驱动：8 类对象（客户/商品/仓库/库存/订单/订单行/发货/退款）、8 条链接（订单→客户、订单→订单行……）、6 个业务动作。左侧导航是 schema 生成的，表格列是 schema 生成的，动作表单也是 schema 生成的——**改 schema，界面跟着变，前端零代码改动**。"

### 实操步骤

| 步骤 | 操作 | 预期看到 |
|---|---|---|
| 1 | 打开浏览器 → `http://localhost:5173` | 左侧对象类型菜单（Customer/Product/Warehouse/Inventory/Order/OrderItem/Shipment/Refund），首页显示"OntoRun 语义接口" |
| 2 | 左侧点 **Order** | 订单列表表格：列=订单属性（order_id 为 Title 键），2000+ 订单分页 |
| 3 | 点开列表第一条订单（首屏即可，如 ORD-0001=pending 未发货；ORD-1001 在第 1001 位不便翻页，段③直接填 ID 更顺） | 详情页：属性描述列表 + **链接导航 tab**（out 链接计数：customer=1、items=1、shipments=0） |
| 4 | 点链接 **items**（或 shipments） | 链接遍历页：从订单直达订单行/发货对象（双向导航） |

### 关键话术（讲到点上）
- "看到链接导航没有——这是 schema 里的 link type 双向遍历，不是外键 JOIN 拼出来的页面。"

## 3. 段③取消订单（1:45–3:15）——端到端写回 + 审计

### 讲稿（约 180 字）

> "现在做一次真实操作：取消订单 **ORD-1001**（confirmed 状态、含 2 个未发货订单行）。我在动作表单里填原因、提交——注意，这一下动作引擎做了四件事：**参数校验 → 前置规则（状态可取消、无已发货 shipment）→ 写回源系统库 → 审计落库**。我们现在到源系统库直接查这条订单，状态已经变成 cancelled，库存的 reserved 也释放了。审计日志里能看到完整留痕，包括写回 SQL 和影响行数——**这就是'源记录真变'的铁证，不是改个前端状态**。"

### 实操步骤

| 步骤 | 操作 | 预期看到 |
|---|---|---|
| 1 | 左侧菜单点 **动作 (6)** → 找到 **cancel_order**（可先在段②停在 ORD-1001 详情） | 动作列表页：6 个动作卡片，cancel_order 含参数表单（order_id、reason） |
| 2 | 填 reason（如"客户改主意"）→ 点提交 | 响应卡片：`outcome=applied`，effects 显示 `Order ORD-1001 status: confirmed → cancelled` + 库存 reserved 释放明细 |
| 3 | 切到源库终端执行：`sqlite3 data/sources/retail_source.db "SELECT order_id,status FROM orders WHERE order_id='ORD-1001';"` | 输出 `ORD-1001|cancelled`（**源库真变**） |
| 4 | 终端执行 `curl "http://127.0.0.1:8000/audit?action=cancel_order"`（UI 暂无审计页，走 API 直查） | 最新一条：actor、params、effects diff、writeback_json（含 UPDATE SQL 与影响行数） |

### 关键话术
- "注意：**UI 提交和 LLM 提交走的是同一个动作端点** `POST /actions/cancel_order`——没有第二条写路径，这就是结构上杜绝'模型绕过规则'的方式。"

## 4. 段④LLM 被规则纠正（3:15–4:30）——三问测试 3

### 讲稿（约 180 字）

> "最精彩的部分：让 LLM 自己去取消一个**已发货**的订单 **ORD-2007**（shipment SHP-88 已于 2026-08-12 出库）。看对话：LLM 理解了意图、正确地调用了 cancel_order 工具、参数也对——但动作引擎的前置规则把这次提交拦下来了，返回业务错误码 `SHIPPED_ORDER_CANNOT_BE_CANCELLED`。**注意：源库这条订单毫发无损。** 然后 LLM 从错误码里学到了规则，自己改口说'这单已发货，不能取消，建议走退款'——这就是**本体规则约束 Agent** 的闭环：不是靠提示词求它守规矩，是接口层有闸。"

### 实操步骤

| 步骤 | 操作 | 预期看到 |
|---|---|---|
| 1 | 页面左侧（或顶部）打开 **ChatPanel**（LLM 对话） | 聊天面板 |
| 2 | 输入：`把订单 ORD-2007 取消掉` → 回车 | LLM 调 `cancel_order(order_id="ORD-2007")` → 回执卡片显示 **rejected + SHIPPED_ORDER_CANNOT_BE_CANCELLED**（消息含"已发货，不能取消，请走退款流程"） |
| 3 | 看 LLM 下一句回复 | LLM 自述规则：如"该订单已发货（SHP-88），不能取消，建议发起退款"（从错误码学习） |
| 4 | （可选加分）追问：`那给我 ORD-2007 申请退款` | 若 LLM 提议 approve_refund：弹出**双签确认框**（"确认执行: approve_refund …"）——高风险动作必须人工确认 |
| 5 | 切源库终端：`sqlite3 data/sources/retail_source.db "SELECT order_id,status FROM orders WHERE order_id='ORD-2007';"` | 输出 `ORD-2007|shipped`（**源库零变更**） |
| 6 | 终端执行 `curl "http://127.0.0.1:8000/audit?action=cancel_order&outcome=rejected"` | rejected 记录：含错误码、被拒前置规则明细 |

### 关键话术
- "看这个错误码回填——LLM 的下一条回复是**从被拒结果里学的**：它现在知道已发货订单走退款。规则不是写进提示词求它听，是写进接口拦它——前者是运气，后者是机制。"

## 6. 准备清单（演示前 15 分钟）

### 6.1 首次准备（一次性）

```bash
# 1) 安装依赖（国内源）
python -m pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
cd web && npm install --registry=https://registry.npmmirror.com && cd ..

# 2) 生成确定性 seed（已生成可跳过；重复生成结果一致）
python data/seed_retail_source.py

# 3) LLM key：应用不自动加载 .env（provider 只读 os.environ），启动前需手动导出：
#    set -a; source .env; set +a   （把 .env 里的 DEEPSEEK_API_KEY/DEEPSEEK_BASE_URL 注入当前 shell）
#    验证：echo $DEEPSEEK_API_KEY  应输出非空
```

### 6.2 每次演示前

```bash
# 重置演示数据（回到初始状态：ORD-1001=confirmed、ORD-2007=shipped）
python data/seed_retail_source.py   # 重建源库（同一 seed，逐行一致）

# 后端（终端 A）：先注入 .env 再启动（新终端不继承之前的 export）
set -a; source .env; set +a
uvicorn src.app.main:app --reload   # http://127.0.0.1:8000（/docs 可看 OpenAPI）

# 前端（终端 B）：本体驱动 UI
cd web && npm run dev               # http://localhost:5173（/api 代理到 8000）
```

### 6.3 演示前 3 分钟自检（checklist）

- [ ] `curl http://127.0.0.1:8000/meta/schema` 返回 8 对象/8 链接/6 动作
- [ ] 浏览器 5173 页面左侧出现 8 类对象菜单
- [ ] 源库 ORD-1001=confirmed、ORD-2007=shipped（`sqlite3` 查询确认）
- [ ] ChatPanel 输入"你好"能收到 LLM 回复（key 可用）
- [ ] 备份一份演示现场快照（若中途取消 ORD-1001 后想重演 → 重跑 seed 即可恢复）

### 6.4 无 LLM key 时的兜底（诚实标注）

- 真 LLM 对话需要 DeepSeek key；若 key 不可用：
  - 段④改为**预演回放**：用 mock LLM 全链路 E2E（tests/test_agent_e2e.py）演示"取消已发货订单被拦"的机制——测试里 RecordingExecutor 走真实 REST 动作端点，行为与真 LLM 一致（只是回复是脚本化的）；
  - 或直接对观众展示 `curl "http://127.0.0.1:8000/audit?action=cancel_order"` 的 rejected 记录（已含错误码与被拒规则明细），说明"LLM 的越界尝试被接口层拦截并留痕"。

### 6.5 P6 全链路 E2E（一条命令演示基线，S1 收口后）

P6 收口后，**演示基线切到一条命令端到端**（蓝图 §12-2）：构建段（CSV 上传 → 管道 run → Curated 审核 → 自动映射 apply → 对象/链接类型 publish → Registry 可见）＋ 运行段（LLM 动作 → 写回源系统 → E6 before/after 快照审计 → 源库真变断言，含三问回归）在同一条 pytest 函数里走通；SQLite-only、无外部服务、无 LLM key（MockProvider 降级，蓝图 §11）。

```bash
pytest tests/test_p6_full_link_e2e.py -q
```

- **用途**：演示前自检 + 向观众展示"全链自动化可运行"（跑通即机制成立）；写回/拦截在测试内用真实双库断言（三问测试回归）。
- **与现场 UI 演示的关系**：P6 E2E 是自动化基线（证据面），现场 5 分钟讲稿仍按段①–⑤走 UI 实操（更有画面感），二者证据互补（§9 对照表）；无 key 时段④也可直接用 P6 E2E 代替真 LLM 演示。
- **注意**：E2E 用临时库副本（tmp_path），不污染 data/ 演示数据；演示前仍按 §6.2 重置 seed。

## 8. 常见翻车与预案

| 翻车 | 预案 |
|---|---|
| ORD-1001 已是 cancelled（上次演示没重置） | 重跑 `python data/seed_retail_source.py` 重建；或改演示 ORD-1001 附近任一 confirmed 订单（seed 里 confirmed 有多单） |
| LLM 没调工具直接回复"不能取消" | 大概率是 key/模型问题 → 检查 .env 与 `curl /agent/chat` 冒烟；或走 §6.4 兜底 |
| LLM 一次说了多句话没触发 tool calling | 会话历史里追加一句"请执行取消操作"再试；系统提示词已含业务规则速览，多数一次成功 |
| 前端样式/菜单异常 | 刷新页面（meta 是启动时拉取的）；确认后端 8000 在跑 |
| 时间不够 | 砍段③步骤 3-4（源库/审计直查），口头说明"测试里已断言"即可 |
