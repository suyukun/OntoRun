# 本体管理台三方对标调研 v0.1

> 任务：为 OntoRun「本体管理台」决策做对标——Palantir Foundry（正统基准）/ 开源平台 / 国内指标平台，回答"造不造轮子"。
> 调研人：Rose（子代理）；日期：2026-09-10；检索：web_search 6 次 + 官方文档/GitHub API 深读（一手数据为主）。
> 来源分级按 T1（官方文档/官方规范）/T2（机构）/T4（媒体评测）标注；GitHub stars/license/pushed 为 API 实查，截至 2026-09-10。
> OntoRun 需求锚点：本体 = Pydantic 注册表（对象/事件/链接/度量 + 口径规则，每条带出处 + unverified/confirmed 状态），git 管理；用户 = 不读代码的数仓团队；三件最小能力 = 浏览 / 勾选确认 / 变更历史。

---

## 结论先行（BLUF）

**建议：不自建平台，也不引入开源平台，自建一个薄壳管理台（复用 git 做全部治理底座）。**
没有任何开源项目覆盖"操作型本体 + 口径确认"的管理——开源分两派：数据目录派（OpenMetadata/DataHub/Atlas，管"数据资产是什么"）和语义层引擎派（Cube/dbt/DJ，管"指标怎么算"），都不管"数仓老师傅勾选确认这条口径对不对"这个动作。而我们的单一事实来源已经是 git 管的 Pydantic 注册表，管理台本质只是 git 之上的一个可读视图 + 勾选按钮。Palantir 的正统形态（Ontology proposal 官方原话"analogous to a Pull Request"）恰好验证这条路：管理台 = git 流 + 人能看懂的界面。MVP 三件套约 3–5 天工作量，详见下文结论节。

## 块1：Palantir Foundry Ontology 管理侧（正统基准）

- **管理台双应用形态**：Ontology Manager（OMA，官方描述"enables you to build and maintain your organization's Ontology"）面向本体建设者，做对象类型/属性/链接类型的浏览与编辑（官方有 Edit object types 专页）；Ontology Explorer 面向业务用户探索对象与关系。**Explorer 的独立文档页未检索到**（URL 重定向，仅 learn.palantir.com 有课程 ONTOLOGY 01），以 OMA 文档为准。[T1] https://www.palantir.com/docs/foundry/ontology-manager/overview ｜ https://www.palantir.com/docs/foundry/object-link-types/edit-object-type ｜ https://learn.palantir.com/understanding-and-exploring-your-ontology
- **变更治理 = git 流的产品化**：官方原话——"An ontology proposal is analogous to a Pull Request in a version control system. Proposals serve as a mechanism for reviewing and approving changes"；旧版 proposals 已演进为 ontology branches（branch → 修改 → 提案 → 评审 → 合并）。确认/生命周期不是自由字段勾选，而是结构化的提案-评审-合并流。[T1] https://www.palantir.com/docs/foundry/ontologies/review-ontology-proposals ｜ https://www.palantir.com/docs/foundry/ontologies/ontology-branches-legacy
- **权限是平台级能力**：Foundry 的对象访问控制走平台安全体系（marking/restricted views/应用级 securing），本体层不单独发明权限模型。含义：OntoRun 的管理台权限应挂在 git 仓库权限上，不自建权限系统。[T1] https://www.palantir.com/docs/foundry/security/securing-a-business-application ｜ https://www.palantir.com/docs/foundry/platform-security-management/manage-restricted-views
- **对 OntoRun 的映射**：我们的 unverified/confirmed + git，就是 Palantir proposal 流的最小同构——缺的不是模型，是"人能看懂、能点选"的界面层。

## 块3：国内指标平台形态

- **阿里 DataPhin**：资产目录 → 指标资产详情。指标口径字段明写"当前指标的开发逻辑，便于业务人员了解"；业务/技术指标分离展示；**元数据变更记录 + 版本对比**（默认保留最近 10 条，字段级 diff 高亮）；指标关系图（以当前节点为根的加工逻辑图）。发布走资产"上架"。[T1] https://help.aliyun.com/zh/dataphin/fullmanaged/user-guide/view-business-indicator-details
- **腾讯 WeData（语义建模·指标管理，2025-12 更新）**：原子/衍生指标（筛选/累积/同环比/混合/转化五型），业务口径+技术口径双字段；**指标生命周期管理**（新建→发布→下线→删除→转交）+ **项目级"指标发布审批流程"开关**（开启则发布需审批）；业务/技术负责人 + 重要等级（核心/重要/一般/临时）+ 血缘 + 指标服务。[T1] https://cloud.tencent.cn/document/product/1267/126256
- **衡石 HENGSHI SENSE**：指标管理内嵌 BI 建模（数据集字段级指标）+ 指标集市/业务指标/指标探索分析，偏消费侧；**审批流细节未找到**（仅读到文档导航结构，正文未深抓，如实标注）。[T1] https://docs.hengshi.com/v6.0/business-indicator.html
- **网易有数（指标字典，最完整的国内参照）**：**注册/发布/下线/变更安全等级全部走审批工单**；业务口径负责人、技术口径负责人分设（技术负责人只能改技术字段）；版本历史（字段级 diff：变更标红+旧值删除线）+ **操作历史**（谁改了什么）；**相似性检测**（新建时防重复指标）；"申请确权"换口径负责人。[T1] https://study.sf.163.com/documents/read/EasyDataBook_LTS6.6.0/easyindex_index.md ｜ https://study.sf.163.com/documents/read/EasyDataBook_LTS6.4.0/date20210906112243.md

## 结论

### 1. 造 or 不造

**最接近需求的开源：OpenMetadata**（glossary 的 owner/reviewer/认证模型最贴"口径确认"），但它缺三样致命的：①操作型本体（对象/事件/动作/写回）在其元数据模型里不存在；②部署与模型改造重量（Java 全家桶 + 自定义模型二开）远超收益；③确认动作仍是数据资产语义，不是"老师傅对口径负责"的业务语义。
**判定：复用 git（治理底座）+ 自建薄壳（界面层）。** 理由：单一事实来源已经是 git 管的 Pydantic 注册表，浏览/确认/历史三件事全是 git 之上的视图操作；Palantir 用 proposal≈PR 验证了 git 流是正统，网易有数/WeData 给出了界面词汇表。要造的只有"把 Pydantic 注册表翻译成人话 + 一个勾选按钮"。

### 2. 自建薄壳的 MVP 功能集（三件套拼装可行性）

| 能力 | 拼装方案 | 可行性 |
|---|---|---|
| 浏览（列表+详情+出处） | FastAPI 只读端点读注册表 → React/AntD 列表+详情页（项目已有栈，且符合"本体驱动 UI"原则：界面由 schema 元数据生成，不是新轮子） | 高，1–2 天 |
| 确认（是非题勾选改状态） | 勾选 → 写端点把 unverified/confirmed 写入注册表 sidecar/字段并 commit（= 最小 proposal 流，无分支无合并） | 高，1 天 |
| 变更历史（谁改了什么） | **git 已内置**：git log --follow + git diff 渲染，按对象路径过滤即可；不需要自建版本系统 | 极高，0.5 天 |

合计 **3–5 天**（含每对象详情页显示出处与确认状态）。刻意不做：血缘图、权限矩阵、全文搜索、审批多级流——发布期再说（架构不设障即可）。
风险提示：①确认写操作要走 git commit（带操作人身份），不能绕过 git 直接改文件，否则单一事实来源被打破；②静态生成方案（纯 git web UI + 静态站）可再省后端，但勾选确认必须有一个写路径，纯静态不够——薄壳后端不可省。

### 3. 给 Jack 的建议（一段话）

建议**自建薄壳、复用 git，工作量 3–5 天（MVP）**：查遍 Palantir 官方文档、八个开源项目和四家国内平台，没有任何现成轮子覆盖"操作型本体 + 口径确认"——开源要么是数据目录（OpenMetadata/DataHub/Atlas），要么是语义层引擎（Cube/dbt/DJ），两者的管理台都答不了"这条口径对不对，老师傅来确认"这个问题；而我们 80% 的需求（浏览、历史）git 和项目现有 React/AntD 栈就能拼出来，Palantir 的正统做法（ontology proposal ≈ Pull Request）恰好证明 git 流就是治理底座，国内网易有数/腾讯 WeData 的指标字典给了现成的界面词汇表（口径双负责人、审批、版本 diff、相似性检测）。所以正确的切法是：**治理底座复用 git（0 新造），界面自建薄壳（一个 FastAPI + 两三张 AntD 页面），发布期再评估要不要把血缘/搜索接 OpenMetadata 这类现成目录**。
