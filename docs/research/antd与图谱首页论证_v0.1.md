# 本体管理台：AntD 选型与图谱首页论证 v0.1

> 架构视角轻量论证 · 2026-09-10 · Jack 授权 Rose 拍板（子代理执笔，资深前端架构师视角）
> 输入：docs/research/本体管理台UX调研与概念设计_v0.1.md + 仓库一手实查（web/、chatbi/ 各自 package.json）

## Q1 管理台组件库：引 AntD，版本取 6.x（不是简报说的 5）

**结论**：管理台独立引入 AntD，仅限管理台自己的包；chatbi（React 18、零组件库）一行不动。版本对齐仓库现状——`web/package.json` 已有 `antd ^6.6.0`，新代码跟当前稳定大版本走；同一仓库养 5/6 两个大版本是交接事故的种子。

**理由**：
1. **需求全在主场**：表格（对象/规则列表 → Table）、表单（确认/过滤 → Form）、抽屉（图谱详情 → Drawer）、布局（左导航 → Layout/Menu）四类开箱即用。shadcn = Radix+Tailwind 自组装、表格还要另配 TanStack Table，对"1 个 AI 维护者 + 数仓同学接手"是持续税；手写四件套 = 重复造轮子（违反项目铁律）。
2. **交接成本最低**：AntD 是国内后台事实标准、中文文档全，数仓同学上手即会；shadcn 社区与文档偏英文，拼装自由度对单人维护者是负资产。
3. **体积顾虑不成立**：仓库实为"同仓多独立包"（chatbi/ 与 web/ 各自 package.json，无 workspace 根），管理台新包依赖物理隔离，chatbi 构建零感知；内部后台无严苛首屏预算，tree-shaking 后常用组件 gzip 约一两百 KB 量级。

**风险与对策**：
- web/（React 19 + antd 6）后续若废弃：管理台仍用 6.x，不受牵连；若坚持保守用 5，须接受双大版本并写明理由（不推荐）。
- 两套视觉语言并存（chatbi 手写 vs 管理台 AntD）：theme token 对齐主色/圆角即可，不强行统一。
- 新增依赖属"先问"档：本文即问，拍板后记 ADR（概念设计开放问题 2 一并收口）。

## Q2 全局图谱当首页：混合首页（图谱主体 + 待确认横条），不退工作台

**结论**：图谱仍是首页视觉主体（占 ≥70% 视区），顶部加一条"今日待确认"横条（大数字 + 直通队列）。既不做纯图谱，也不退工作台。

**理由**：
1. **性能不构成风险**：几十节点 + 百条边以内的图，React Flow（SVG/HTML 节点）远低于其 canvas 化阈值（官方建议 100+ 节点才考虑 canvas 渲染）；d3-force 在该规模亚秒级收敛，用业务域聚类的预置初始坐标可把开场"爆米花"压到几乎不可见。13 寸屏 1440×900 整屏容纳，缩放 + 搜索定位兜底。首屏策略：壳与横条先渲染、图谱懒初始化，FCP 不受拖累。
2. **"好看"是伪风险**：概念设计 2.4 已锚定图谱的价值是"找异常"（默认高亮未确认关联），不是审美；≤3 种节点样式 + 业务域配色 + 固定初始布局下，几十节点的图下限可控，好看只是副产品。Jack 的担忧不该用"赌好看"来解。
3. **混合是价值对冲**：纯图谱首页把整页押在审美上，翻车即沦为屏保；横条让首页永远有功能价值（今天要钉死的口径）。图谱保住管理台最独特的身份——退工作台 = 自废武功，也丢 learn-in-public 演示素材。且 wireframe 顶栏本就有"待确认 12"角标，混合只是把首页的它放大，改造成本近零。

**风险与对策**：
- 图谱日均交互趋零 → 设回退判据：上线一个月后若待办动线几乎全部绕开图谱，降级为工作台首页 + 图谱二级页（路由换序，约半天）。
- 空状态难看 → 预置种子布局坐标兜底，不裸跑 force。
