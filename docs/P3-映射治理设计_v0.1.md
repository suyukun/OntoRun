## 0. 一句话设计

**P3 在 P1.5 打标骨架上接通「映射治理闭环」：DES 数据/外部导入 → 自动映射候选（P1.5 四适配器）→ classify 分级 → routing（高自动过/低进队列）→ 人工审核（CLI/CSV 批量导出导入，UI 后置）→ approved 入注册表（Registry 注册 + mappings 血缘记录 + self_check 验证）——配套 ground truth 阈值校准（对 0.9/0.6 默认阈值在 GT 上扫描最优，输出校准报告）与审核痕迹落审计（mapping_review_history + audit source='review'，WORM 保证），并用「60–100 条映射 GT + 单轮标注 + Rose 复核」的 demo 口径务实裁剪 P3 门禁（top-5 recall ≥80% 保留）。**

### 0.1 本轮范围声明（先对齐边界，防目标漂移）

P3（映射治理 + 审核，S2 计划阶段 P3，2 周）做四件事：

| # | 事项 | 落点 | 边界 |
|---|---|---|---|
| ① | 映射管道 | DES 数据/外部导入 → 候选 → 分级 → 队列 → 人工审核 → approved 入注册表（§1） | 管道编排 + CLI，**UI 后置**（议题2 §3.7-3 工作台留 P5 指针版或后续）；动作模板库/校验注册表属议题2 其他子项，**不在 P3** |
| ② | 审核流程 | 批量 accept/reject、冲突标记、改完即入注册表、审核痕迹落审计（§2） | CLI 先行；冲突标记 P3 用轻量标记，结构化冲突队列留 UI 阶段 |
| ③ | 阈值校准 | GT 数据集 + recall/top-5 recall 口径 + 阈值扫描 + 校准报告（§3） | 校准产出「建议阈值 + 报告」，**不把阈值写死**（C2）；P3 门禁 GT 规模按 demo 裁剪（§3.5） |
| ④ | 入注册表 | approved 候选写 Registry（对象/链接注册接口复用）+ 映射血缘落 mappings 表 + 映射变更影响分析（§4） | C2「必有映射变更影响分析」；approved 终态不可改，变更走新候选重审 |

**门禁原文（S2 计划 v0.3）**：ground truth ≥300 问/域，标注 ≥2 人+仲裁，top-5 recall ≥80%；自动化映射对人工版 recall 显式化；产出 = 映射管道 + 阈值校准报告 + 审核痕迹落审计骨架。

## 1. 映射管道

### 1.1 管道总览（每环节 输入/输出/接口）

```
 数据源装载 → 自动映射候选 → classify 分级 → routing → 人工审核 → approved 入注册表
   (阶段0)      (阶段1)        (阶段2)      (阶段2)      (阶段3)      (阶段4)
  DES/外部       四适配器       纯函数        纯函数      CLI/CSV       Registry
```

| 环节 | 输入 | 处理 | 输出 | 接口（复用/新增） |
|---|---|---|---|---|
| 0 数据源装载 | DES enterprise（config+manifest+生成库）或外部 dataset（csv/json） | DES：取表 schema+样本+语义声明；外部：schema_infer 推断 | `SourceDescriptor{source_kind, source_table, columns[], rows_sample[], des_mappings?}` | 复用 `schema_infer.infer_schema` / `src/des/config.load_config` / `manifest.json` |
| 1 自动映射候选 | SourceDescriptor + Registry（C4 target 校验） | P1.5 四适配器：naming（attribute 0.9）/ fk_detection（link）/ alias_matcher（link）/ DES（object/attribute 1.0） | `list[MappingCandidate]`（score+level+evidence） | 复用 `annotate_mapping_candidates(source, registry)`（P1.5 已实现，P3 只调度） |
| 2 分级 + 路由 | 候选 + 阈值（high/medium） | classify(score)→档位；routing：high→auto_approved+approved，medium/low→draft（队列） | 落 `mapping_candidates` 表；队列按 score 降序 | 复用 `MappingCandidateService.create / list(status, level, page)`；阈值读取配置（默认 0.9/0.6，校准后写回配置） |
| 3 人工审核 | 队列候选（draft/reviewing） | CLI 导出 CSV → 人工裁决 → CLI 导入（accept/reject/conflict + corrected_target） | 状态流转 + review_history + audit（source='review'）；accept 且改 target → 直接入注册表 | 新增 `src/builder/mapping/review_cli.py`（§2.3）；复用 `MappingCandidateService.transition` |
| 4 approved 入注册表 | approved 候选 + 注册必需附加元数据（pk/cardinality/fk_field/source_table/ownership） | enrich → 构建 ObjectTypeDef/LinkTypeDef → Registry.register_* + mappings 血缘 + self_check 验证 + audit（mapping_publish） | Registry 新增对象/链接；mappings 记录映射血缘 | 新增 `src/builder/mapping/registry_write.py`（§4）；复用 `registry_loader._build_dynamic_model`、`mapping/repo.create` |

**管道编排入口（新增，规格）**：`run_mapping_pipeline(source_kind, enterprise_code | dataset_path, *, store, registry, thresholds)` -> `PipelineReport`，`PipelineReport = {source_table, total_candidates, auto_approved, in_queue, by_level: {high/medium/low: n}, skipped_c4: [target,...]}`。单表一个批次跑通；管道内「候选 C4 未注册 target」跳过计数（对齐 P1.5 语义），并进待补录清单（P3 记数不处理）。

### 1.2 数据源装载（DES vs 外部导入，双通道对齐议题2 §3.7-1）

- **DES 通道（演示主路径，语义已知，半自动映射）**：
  - 输入：企业配置（`data/des/enterprises/<code>/des_enterprise.yaml`）+ 生成库（erp/mes/wms/scm/fin 各 .db）+ `manifest.json`；
  - 语义来源两路：① **DES 声明语义**——DES 管道按 §3.7-1 声明对象级/属性级已知映射（`des_mappings`，进入 adapt_des_semantics，score=1.0 高置信自动过）；② **自动推断**——对表列跑 naming（attribute）+ fk_detection（link，跨表 FK 用 config 的 fk/depends_on 关系驱动）+ alias_matcher（备用键，可选）；
  - 输出统一为 `annotate_mapping_candidates` 的 `source` dict 形态。
- **外部导入通道（交付接真实数据路径，语义未知，自动推断 + 审核）**：
  - 输入：外部 csv/json dataset（builder `datasets` 表已支持上传）；
  - 处理：`schema_infer.infer_schema` → `auto_map_from_inference`（复用，产出 field_mapping/fk_mappings/property_schema/alias_matches）→ 拆解为 `source` dict（columns/detected_links/alias_result）喂给适配器；
  - 差异：无 DES 语义 → 无 score=1.0 的 object 候选兜底，object 候选由命名/推断派生（score 较低，更多进队列，人工负载更高——符合「外部数据更需审核」的议题2 预期）。

> 两通道内部不绑定（§3.7-1「不内部绑定」）：演示走 DES，交付接真实数据。管道对 `source_kind` 只影响阶段 0/1 的装载与候选来源，阶段 2-4 完全同构。

### 1.3 分级与路由（阈值可配，C2）

- `classify(score, high, medium)` / `routing(candidate)` 为 P1.5 纯函数，P3 不改；
- **阈值读取顺序**：配置（校准后写入，如 `data/des/enterprises/<code>/mapping_thresholds.yaml`）→ 缺省 0.9/0.6（P1.5 默认，仅在无校准配置时生效）；
- 机验口径：管道输出中 `auto_approved ⟺ (score ≥ high ∧ status=approved ∧ 历史含 auto)`、`in_queue ⟺ level ∈ {medium, low} ∧ status=draft`（P1.5 机验 ②③ 在管道级重断言一次）。

## 2. 审核流程

### 2.1 审核工作流

| 动作 | 触发 | 状态机流转 | 落痕 |
|---|---|---|---|
| 一键接受 | reviewer 对单个候选 accept | draft→approved（或 reviewing→approved） | review_history（reviewer=human）+ audit source='review' |
| 批量接受 | CSV 导入多行 decision=accept | 同上，逐候选 | 同上（逐条） |
| 拒绝 | decision=reject | reviewing→rejected（draft 先转 reviewing） | history + audit |
| 冲突标记 | decision=conflict 或管道预标 | **不流转**（保持 reviewing/draft） | audit（error_code='MAPPING_CONFLICT'）+ history note 标记；候选留队列等待再次裁决 |
| 改完即入注册表 | decision=accept + corrected_target 非空 | draft→approved（target 先更新为 corrected_target） | history + audit + **立即执行 registry_write.apply_approved（§4.1）** |

- **改完即入注册表（议题2 §3.7-3 接线点）**：accept 且 reviewer 修正了 target（源字段映射错目标 → 填正确目标）时，更新候选 target 后直接走 §4 入注册表——P1.5 预留的「approved 候选如何写入注册表 = P3 接线点」在此落地；
- **批准即权限接线**：人工审核动作前先 `decide(subject=reviewer, resource=该候选 target 对象, operation="approve")`（P1.5 §4.4 预留；P3 至少走纯函数 decide 校验 human——agent 不可审，V9 兜底），P4 接 FastAPI actor 鉴权。

### 2.2 审核痕迹落审计（P3 交付 3 之一）

- **单一来源**：`mapping_review_history`（P1.5，append-only + WORM 触发器）= 审核痕迹权威；
- **审计同步**：每次人审动作（accept/reject/conflict/改 target）经 `AuditLog.append(AuditRecord(action_name='mapping_review', actor=reviewer, source='review', outcome='applied'|'rejected', detail_json=候选+裁决))` 落 audit_log；**入注册表发布**另落 `action_name='mapping_publish', source='review'`（同一治理证据链，区分「审」与「发布」两类事件）；
- **机验口径**：① 每次状态流转必有一条 history（P1.5 已有）；② 每条人审动作必有一条 source='review' 审计；③ history/audit 均 WORM（UPDATE/DELETE 抛错，P1.5 已验）；④ `audit.verify_integrity()` 全绿（哈希链含 review 记录后仍自洽）。

### 2.3 CLI 工具规格（新增 `src/builder/mapping/review_cli.py`）

```
python -m src.builder.mapping.review export   --enterprise hc_precision --out review_batch_20260821.csv   [--status draft,reviewing] [--level medium,low]

python -m src.builder.mapping.review import   --enterprise hc_precision --file reviewed_batch_20260821.csv   --reviewer jack
```

**导出 CSV 列（导出即快照，导入时以 candidate_id 关联回权威）**：

| 列 | 说明 |
|---|---|
| candidate_id | 必填，关联回 mapping_candidates（导入裁决的唯一锚） |
| kind / source_table / source_field / target | 只读快照，供审阅 |
| confidence_score / confidence_level / evidence | 只读快照（evidence 为 JSON 字符串） |
| **decision** | 空（待填）：accept / reject / conflict |
| **corrected_target** | accept 且映射目标需修正时填新目标值（改完即入注册表） |
| **note** | 审阅备注 |

**导入裁决规则（逐候选原子，失败不静默）**：

| decision | 处理 | 机验断言 |
|---|---|---|
| accept | `transition(candidate, approved, reviewer, note)`；corrected_target 非空 → 先更新 target 再 transition → `registry_write.apply_approved` | 状态=approved；历史含该次流转；若改 target 则 target=corrected_target 且已入注册表 |
| reject | `transition(candidate, rejected, ...)` | 状态=rejected；无入注册表 |
| conflict | 不流转；audit（error_code='MAPPING_CONFLICT'）+ history note 标记 | 候选仍在队列；audit 含 MAPPING_CONFLICT |
| 非法/缺失 | 抛错并停止该行（fail-fast），导入汇总报告列明失败行 | 无部分静默成功 |

导入结束输出 `ReviewBatchReport = {processed, accepted, rejected, conflicts, published_to_registry, failed}`。

### 2.4 冲突标记（二义性高亮）

- **管道预标**：导出时对「同 (source_table, source_field) 出现多个目标候选且 top-2 score 差距 < 0.1」的行预标 conflict 提示（写入 CSV 的 note 或独立列），对齐议题2 §3.7-3「同字段映射二义性高亮」——机器先找可疑，人只确认；
- **人工标记**：decision=conflict → audit（error_code='MAPPING_CONFLICT'）+ history note，候选留队列；
- **P3 边界**：冲突不落结构化表（最小改动，复用 P1.5 表）；若 UI 阶段需要「冲突队列/待决列表」，新增 `mapping_conflicts` 表作为可选扩展（登记于风险 R2），P3 不实现。

## 3. 阈值校准

### 3.1 ground truth 数据集结构

GT = 映射真值标注集（源字段/源表 → 目标本体），静态文件，可版本化：

```yaml
# data/des/enterprises/<code>/mapping_gt.yaml（或 data/gt/mapping_gt.yaml）
version: "0.1"
domain: "manufacturing"            # 对齐 DES 行业
entries:
  - source_table: "erp.MARA"
    source_field: "MATNR"
    kind: "attribute"              # object / attribute / link
    gt_target: "Material.material_number"   # 真值目标：属性带对象前缀；object 为对象名；link 为链接名
    verified_by: "jack"            # 标注人（demo=jack；正式口径=标注员A/B）
    verified_at: "2026-08-21"
    note: ""                       # 标注依据（口径/旁证）
```

- **单位口径（重要，见 §3.5）**：P3 的 GT 单位 = **映射条目**（一条「源字段→目标」真值），不是 ChatBI 的问答集（问答集属 P2 head-to-head 30 问范畴）；「≥300 问/域」若指问答级 GT，则属 P2，P3 不适用；
- 校验（GT 加载即 fail-fast）：kind ∈ 三类；gt_target 非空；同 (source_table, source_field, kind) 不重复；gt_target 尽量对到 Registry 已注册对象/字段（校验可过时给 warning，允许目标尚未注册——那正是待建映射）。

### 3.2 recall / top-5 recall 计算口径

对每个 GT 条目 i = (source_table, source_field, kind, gt_target)：

1. 取管道对该 (source_table, source_field, kind) 产出的**候选按 score 降序排序**列表 C_i；
2. `hit@k(i) = 1 if gt_target ∈ C_i 前 k 名 else 0`（k=1 即精确 hit；候选无该条目 → C_i 空 → hit=0）；
3. `recall@k = Σ_i hit@k(i) / |GT|`；**top-5 recall = recall@5**；
4. **双口径显式化（门禁点）**：
   - `full_recall` = 全量 approved（含人工审核补充后）口径：以「GT 目标对应的候选最终被 approved」判定 hit——即**门禁用 recall**；
   - `auto_recall` = 仅高置信自动过（routing 直接 approved）口径：GT 目标对应的候选 score ≥ high 且 auto_approved——**显式报告自动化映射的独立贡献**（不设硬门，供 C2 阈值决策）；
   - 报告同时给 `full_recall` 与 `auto_recall`，差值 = 人工审核的增量价值（C2「自动化映射对人工版 recall 显式化」的机器口径）。

### 3.3 校准方法（对 0.9/0.6 在 GT 上扫描最优阈值）

- **输入**：GT + 候选集（管道对 GT 覆盖的字段重跑一次即可）+ 扫描网格；
- **网格**：high ∈ [0.60, 1.00] step 0.05 × medium ∈ [0.35, 0.85] step 0.05，约束 medium ≤ high；
- **对每个 (high, medium) 计算**：
  - `auto_coverage` = 高置信自动过覆盖 GT 的比例（= 人工负载的反向指标，越高人审越少）；
  - `full_recall`（= recall@5，人工审核可补齐，用 §3.2 口径）、`auto_precision`（自动过中命中 GT 的比例，防自动错批）；
- **选择规则（目标函数，C2 语义）**：
  - 硬约束：`full_recall@5 ≥ 0.80`（门禁保留）；
  - 软约束：`auto_precision ≥ 0.80`（可配置，防高阈值全自动导致错批扩散）；
  - 目标：在满足约束的 (high, medium) 中选 **auto_coverage 最大**（最小人工负载）——但 demo 阶段没有「跑 1-2 月数据」，用 GT 一次性估计；
  - 平局/无解：报告如实标注「无满足约束的阈值」，回退默认 0.9/0.6 并给出差距，不静默。
- **校准输出**：`CalibrationReport` + 建议阈值写入 `mapping_thresholds.yaml`（配置，不硬编码——C2）。

### 3.4 阈值校准报告模板（P3 交付 3 之一）

```markdown
# 映射阈值校准报告（<enterprise_code> · <date>）
## 1 数据
- GT 规模：N 条（object x / attribute y / link z）；标注方式：demo 口径（见 §3.5）
- 候选集：来自 DES <表数> 表 / 外部导入 <n> 表；候选总数 M，去重后覆盖 GT 字段 <p>%
```

### 3.5 P3 门禁务实裁剪（demo 口径建议，交付 3 核心，需 Jack 确认）

**评估「≥300 问/域、≥2 人标注+仲裁」对 1 企业 DES demo 是否过重——结论：过重，建议按 demo 规模裁剪。**

|---|---|---|---|
| GT 规模 | ≥300 映射条目/域 | **60–100 条映射 GT**（覆盖 DES 18 表核心对象/属性/链接，三类 kind 全覆盖，含 1 物多码等注入字段） | ① demo 只有 18 表、几十对象/几十链接，映射候选全集天然就 ~100 条量级——「300 条」在 demo 下 GT 上限即候选数，无意义；② 60–100 条足以覆盖核心字段并支撑 recall 统计（top-5 recall 在 n≈80 时已有可辨识度，采样误差如实报告）；③ 对齐 C1「100 万行级、利于演示传播」的务实基调 |
| 标注人力 | ≥2 人独立标注 + 仲裁 | **单轮标注（架构/数据角色）+ Rose 复核**（复核 = 全量一致性检查 + 冲突项仲裁 + 抽样抽审） | 一人公司 demo 无真实「2 个独立标注员」；硬凑 2 人仲裁变形式主义。Rose 复核保留「仲裁否决权」的精神，两级 = 标注 + 复核，成本与价值匹配 |

## 4. 入注册表

### 4.1 approved 候选如何写入 Registry

新增 `src/builder/mapping/registry_write.py`（规格）：`apply_approved(candidate, *, registry, store, des_manifest=None) -> PublishResult`，按 kind 分派：

| kind | 写入动作 | 复用/新增 |
|---|---|---|
| object | ① 由候选 target + 源表列构建 property_schema（naming.derive_property_schema 已产出，或 DES 声明）；② 生成 Pydantic 动态类 = **复用** `registry_loader._build_dynamic_model(property_schema, name, extra_fields=fk字段)`；③ 构造 ObjectTypeDef{name, api_name（snake_case，复用 ObjectTypeRow.api_name 派生算法）, model, pk_field（源表 PK，取自 DES config pk 或 naming.is_id_only_column）, title_field=pk, source_table（DES manifest 表名）} → `registry.register_object_type`；④ 若已存在同名 → 抛错（对齐 Registry 重复注册拒绝，防静默覆盖） | `registry_loader._build_dynamic_model`；`registry.register_object_type`；`src/des/config` pk |
| attribute | 归并进所属 object 的 property_schema（对象级 approved 时统一落；attribute 候选不单独注册）——属性映射最终以「对象 model 字段」呈现，与 Registry 字段校验（V2/GOV_CAND）同口径 | — |
| link | ① 候选 target=链接名，source/target 类型由 fk_detection 的 (source_table→对象, target_field→目标对象) 解析；② 构造 LinkTypeDef{name, source_type, target_type, cardinality（fk_detection 产出）, fk_field（DetectedLink.source_field）, inverse_name（按 `<target api_name>.` 前缀约定，复用 `registry_loader._derive_inverse_name`）, description} → `registry.register_link_type`；③ 端点未注册/自环/基数 N:M → 拒绝（对齐 registry self_check） | `registry_loader._derive_inverse_name`；`registry.register_link_type` |
| 血缘记录 | 全部 kind：`mapping/repo.create(conn, ontology_id, entity_class, source_table, field_mapping, fk_mappings, cardinalities, status='published')` 落 mappings 表（映射层自己的记录，与运行时 Registry 双写，各司其职） | `src/builder/mapping/repo.create` |

**注册写前置校验清单（入注册表前必过，缺一拒绝，机验）**：

| 校验 | 对齐 | 说明 |
|---|---|---|
| 对象 pk 字段 ∈ model 字段 | registry self_check OBJECT_PK_MISSING | pk 取自源表 PK，必须落入 property_schema 字段 |
| 对象 source_table 非空 | self_check OBJECT_NO_SOURCE_TABLE | DES 通道从 manifest 取；外部通道需人工补（缺失则 reject 该对象候选，提示补 source_table） |
| 字段 ownership 标注齐全 | self_check FIELD_MISSING_OWNERSHIP | **动态 model 需对每个字段标注 ownership=source-backed**（DES 源列均为源系统权威）；_build_dynamic_model 不自带，注册写需补 json_schema_extra |
| 链接端点已注册 + fk_field 存在 + inverse_name 前缀 + 基数 N:1/1:N | self_check LINK_* | fk_detection 已产出 fk_field/cardinality；端点 = 两侧对象名 |
| **发布后自检全绿** | `registry.self_check()` | 注册写完成后立即跑一次，0 error 级 Issue 才接受发布（P1.5 已挂 GovernanceValidator） |

**审计**：发布动作落 `action_name='mapping_publish', source='review'`（§2.2），含 published 对象/链接名。

### 4.2 对象/链接注册接口复用结论

- **复用面**：`Registry.register_object_type / register_link_type`（内存注册）+ `registry_loader._build_dynamic_model`（model 生成）+ `mapping/repo.create`（血缘）；**不改造 registry.py**（对齐 P1.5「registry 保持通用」纪律）；
- **不走 builder object_types 发布表**（设计决策，见 §6 R3）：builder object_types 行 source_table 恒空（补丁 A2 构建产物只读）且 pk 由 required[0] 派生，绕行会触发 self_check 的 OBJECT_NO_SOURCE_TABLE / OBJECT_PK_MISSING；DES 通道源表明确，**直接构造 ObjectTypeDef/LinkTypeDef 注册**更贴合「approved 即运行时对象」，也满足 self_check。UI 阶段若需 object_types 表持久展示，再补一份写表（届时评估）。
- 内存注册与表持久化的时序：注册写在同一 Store 事务内先落 mappings 血缘表、再注册 Registry（内存），保证「入注册表」原子可验。

### 4.3 映射变更影响分析（C2「必有映射变更影响分析」）

新增 `src/builder/mapping/impact.py`：`analyze_change(candidate) -> MappingChangeReport`。对一次 approved 映射变更（新增/修正 target），反向扫描受影响面：

| 影响面 | 查询方式（SQLite 内可查） | 变更信号 |
|---|---|---|
| 对象/链接 | Registry 现注册集中是否存在同名/同端点 | 新增 vs 覆盖（覆盖被拒绝，只能新增 → 冲突显式化） |
| 指标（读侧） | `src/des/metrics.py` MetricRegistry：`object_type` 引用该对象、`source` 引用该表列 → 物化 SQL 受影响 | metric_id 清单 + 是否触发重物化（P2 refresh 管道） |
| 查询契约 | `src/des/contract.py` 契约执行器：link_traversal 端点 / 字段引用 | 受影响契约形态（v0.1 扩展 / v0.2 metric） |
| 审计 | audit source='review' 中该候选/对象的既有记录（哈希链不受影响，verify_integrity 仍全绿） | 变更前已入注册表的对象在审计中仍可追溯 |
| 语义接口 | /meta/schema 动态暴露（本体驱动 UI） | 新增对象/字段 → UI 自动出页面，无需手工改 |

**MappingChangeReport 形态**：`{change: {candidate_id, kind, source_table, source_field, target_from, target_to}, affected: {objects: [], links: [], metrics: [metric_id], contracts: [形态], audit_chain_ok: bool}, risk: high|medium|low}`。**变更流程纪律**：approved 为终态不可改 → 任何变更 = 新建候选重新走完整管道（draft→审核→approved→入注册表），旧映射不删除（保留审计与血缘），影响分析报告在变更前生成并归档（写入变更审计 detail_json）。

## 附：本设计对「研究对象锚定」的回答

这份映射治理设计不造「数据治理轮子」：它把 S1 靠手写注册表（8 对象/8 链接）的个体经验，升级为「**数据→本体映射**的可治理闭环」——DES/外部数据经四适配器自动产候选，阈值用 ground truth 校准（C2 反「拍脑袋 80% 自动」），人审经 approve 权限（人专属，V9）与 WORM 审计留下证据链，approved 经注册写前置校验（ownership/pk/source_table/inverse_name）进入 Registry 并被 self_check 兜底。这正是议题2 形态的落地：**映射自动化 + 轻人工审核**，人只审可疑项、从不从零建模；也是方法论「浓缩版六阶段·数据映射治理」阶段的可执行规范（P5 白皮书 v2 的机器可验支撑）。「approved 终态 + 变更走新候选重审 + 影响分析先行」对齐 C2 的映射变更影响分析要求，使映射治理从「一次性映射」变成「可审计、可回滚、可影响评估」的持续治理循环。
