## A 级三裂缝的拍板

### A1 本体单一事实来源 = 运行时合并后的 Registry（单向流入）

- **内置类型**：src/ontology/ 代码注册的 8 对象/8 链接/6 动作（现状不动）。
- **扩展类型**：builder 的 object_types/link_types 表，经 `draft -> reviewed -> published` 状态机（E4）后，在**应用启动时动态注册**进同一内存 Registry。
- **单一事实来源** = 启动时合并后的 Registry；runtime 索引 / API /meta/schema / Agent 工具生成 / 前端全部只消费它，**不直接读表**。
- 冲突消解：表类型不得与内置类型同名（self_check 报 error，拒绝 publish）；publish 后改名/删除 = 新版本注册（发布期，TODO）。
- 禁止出现第二套"表驱动本体定义"被任何运行时路径直接消费。

### A2 构建产物只读，写回走源系统权威表（拼接叙事，如实表达）

- 构建链产物（CSV/文档 -> 映射 -> published 对象类型）在运行时**只读**：可查询、可图谱导航、可被 LLM 作为上下文引用。
- 全链路验收（蓝图 §12-2）= **构建段**（CSV -> 管道 -> Curated -> 自动映射 -> publish -> Registry 可见）拼接 **运行段**（现有 8 对象的动作 -> 写回源系统库 -> 审计含 before/after 快照）。
- 动态对象类型的写回（action_types 表的 effects 落库）列**发布期 TODO**；E3 提取的动作类型只注册元数据 + E6 审计记录，不执行动态写回。
- 白皮书如实写："构建产物只读，写回面向源系统权威表"——这是设计决策，不是缺陷遮掩。

### A3 不引入 SQLAlchemy/Alembic，沿用 store.py 裸 DDL 风格

- 蓝图 §2 "与现有一致" 为事实错误：现有代码无 SQLAlchemy/Alembic（已核验 requirements.txt 与 store.py）。
- 新 10 张表进**本体库**（data/ontology/ontology.db）：`BUILDER_SCHEMA_V1` 常量 + schema_version 递增 + CREATE TABLE IF NOT EXISTS，风格与 store.py 现有 ONTOLOGY_SCHEMA 完全一致。
- 构建期数据（datasets/pipelines/curated/mappings/extraction_tasks 等）一律本体库；源库（retail_source.db）保持纯业务权威，零污染。

## C 级小硬伤的合理化（执行时按此处理并记入代码注释）

1. API 路径占位符 `glm-5.3_common` 统一按 `{name}` 路径参数实现。
2. datasets.kind 枚举 = csv/excel/json/md/pdf/docx（pdf/docx 依赖 markitdown 可用性）。
3. extraction_tasks 删除 progress 字段（同步执行无进度语义）。
4. pipelines.dag 的 JSON schema 在 P2 定义（节点：id/kind(connector|storage|transform|output)/config/next[]），前后端共用。
5. LLM 相关验收允许 MockProvider 全绿；**DEEPSEEK_API_KEY 可用时加一次真 LLM 提取冒烟**（非阻塞，结果如实记录）。
6. 白皮书「本体构建方法论」章节必须引用本项目实测数据（跑了多少文档、校验拦截了什么），素材不得只来自调研文档。
7. 表述规范："受 nano-ontoprompt 启发的重新设计"（不称独立原创，不抄代码）。
8. GitHub 发布白名单更新（scripts/publish_to_github.py）列 P6 收尾项。
