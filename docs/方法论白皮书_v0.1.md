## 一、定位：语义接口层

【实证状态：部分实证】切入路径、计算边界、LLM 角色定位是真实场景上的裁决与实践（L1 demo 已运行、结构化拒答已运行）；L2 目标态（原语组合）在建（见第二章）。

### 1.1 研究对象：操作型本体
- 不是把现有数据库结构画成 ER 图（描述型本体），而是**操作型本体**：对象/事件/链接/度量 + 口径规则，作为 LLM 消费真实业务系统的接口层。
- 企业本体的经典构成三层：静态（实体/结构）、**动态（事件/过程/状态）**、意图（目标/约束）——TOVE 企业本体里 Activity 是独立的核心本体。事件/过程类是第一等公民，"注册/活跃只是动作、不算本体"是错误印象。

### 1.2 两套坐标系：场景 ≠ 数据域
- 数仓按"数据是什么"组织（数据域：TR/CU/CH…），业务按"想问什么"提问。语义层是两套坐标系的转换器：**场景 = 横切若干数据域的表子集 + 问题集 + 口径卡**。场景到数据域的映射表本身是交付物。
- 注册场景实证（2026-09-10 依真实表清单修正）：注册属 **CU 用户域**（此前误设 TR 交易域，与"注册是用户实体的动作"互证）；注册场景**无 DWS 层**，ODS→DWD→ADS 直连——数仓建设不必然标准，语义层适配现实。

### 1.3 切入路径：decision-back，拒绝 data-forward
- 反面实录（Palantir Study 08 恒川故事）：数据团队带着 26 个系统、480 张表、3000+ 字段进研讨会，两小时白板上出现 20 多个候选 Object Type，被业务一句"下次缺料时，这套东西能不能让我在排产冻结前批准方案"问哑。data-forward 四种失败模式：对象多却无决策使用；属性齐全却没人知道哪些改变选择；Link 密如 ER 图却不解释影响；页面能看却无法安全改变业务状态。
- 正解 **decision-back**：Outcome → Decision moment → Action 契约 → 反推事实/关系/判断/证据 → 最小 Object/Link/Property 集合 → **最后**才核对 Dataset/Pipeline/缺失数据。筛选标准："删掉这个属性，目标决策还能安全完成吗？能 → 不进初版。"
- 学术根基：TOVE 方法论以 Competency Questions 为起点（Gruninger & Fox 1995，兼作验收标准）；构建三策略 top-down / bottom-up / **middle-out** 出自 Uschold & Gruninger (1996)，实践推荐中间向外。
- 本体落地没有"实体优先 vs 问题优先"的二元选择——问题定范围、实体做骨架，是同一方法论的两个层。

### 1.4 双轨方法论：切入按问题、组织按实体
- **切入点（战略层）= 问题/KPI 驱动**：决定范围、优先级、验收；第一问就是 ChatBI 场景的 Decision moment。
- **组织结构（架构层）= 实体+关系骨架**：对象/链接一旦建立即全局注册复用（O1 User 是三案共同底座），KPI 口径变化只改规则层不改骨架——实体骨架稳定（用户/渠道十年不变），KPI 口径易变（目标年年调）。
- **合并律**：从问题切入 → 切进来的实体沉淀为全局骨架 → 下一个问题复用骨架只加增量。这就是 middle-out 的操作化。
- 反面实证：实体先行（124 表全量理解）已实证失败；问题先行不抽象则停在 L0/L1。

### 1.5 计算边界：语义层不执行计算
- 语义层确认口径、生成 SQL、下推数仓查询引擎执行。计算资源永远是数仓的，"撑不撑得住"与本体层无关。
- 双路径：汇总层 DWS/ADS = 热路径（高频快答案）；明细层 DWD = 冷路径（下钻/溯源/即席）——语义层只登记其元数据（粒度/口径/关联路径）+ 按需生成 SQL 下推，明细永不进运行时内存。明细层三重意义：下钻路径声明、口径可验证（派生规则声明汇总数的聚合来源，数字不裸奔）、即席 fallback。
- 未预汇总查询的三级服务策略（例："男女注册比例"）：①先看维度挂载粒度——维表属性扫维表而非事实表，成本差数量级，"没预汇总"≠"要扫大表"；②即席下推，回答标注"明细级即席计算 + 数据截至时间"；③即席也不可行则诚实降级（"需离线物化，T+1 可答"）+ 登记为派生指标候选。
- **物化循环**：查询未命中热路径 → 语义层捕获登记 → 高频者物化成新热路径——"预聚合建哪些"从架构师拍脑袋变成问题驱动，数仓演进第一次获得精确需求反馈。

### 1.6 为什么不是裸 NL2SQL
区别不在"最后是不是 SQL"，在"**SQL 由谁决定**"：裸 NL2SQL 里 LLM 是 SQL 作者（每次从全部 schema 现场发明，表/join/去重键/口径全靠赌）；语义层里 LLM 只是规则选择者（意图 → 已注册规则 + 填参，SQL 由规则确定性编译，LLM 常不参与编译）。五条差异：
1. 搜索空间：480 张表 → 几十个已注册构件；
2. 口径：现场发明 → 只能引用（I4：两种口径=两条注册规则，不许发明第三种）；
3. 验证：输出无法机器验证 → 逐层可校验（规则存在/路径合法/参数在枚举内）；
4. 失败：错误答案 → 拒答降级；
5. 迭代：错了改 prompt → 回答沉淀进规则/物化循环。
代价（诚实）：放弃表面灵活性，超范围问题必须降级——企业经营分析场景可信度 > 灵活度。一句话：**本体层把 LLM 从"SQL 作者"降级为"规则选择者"——它不需要懂数仓，只需要懂手册，而手册每条都是人裁决过的。**

### 1.7 待验证（提纲，不展开）
- L2 原语组合目标态全量落地（当前在建）；
- 冷路径启用与维表属性类验收题（MVP 裁决：第一问切片全走热路径，DWD 只登记元数据）；
- 语义层 = 查询路由器 + 口径守门员 + 物化循环管理器的完整闭环。

## 二、方法：middle-out 卡 → 原语 → 组合

【实证状态：部分实证】机制在 mock 镜像库上拿到首验数据点（非菜单第一验通过、11 题 4-5 卡）；完整 L2 编译器在建，真数据未过。

### 2.1 三段循环
问题钉住口径（口径卡）→ 口径提炼成原语（对象/度量/维度/身份规则）→ 确定性编译器组合原语生成 SQL。LLM 只选原语，永不写 SQL。
输入规范：**给可执行的 SQL，别给描述性文字；按问题拉取，不按库存推送**——场景外字段不读。

### 2.2 能力分级之一：生成方式轴（L0-L3）

| 层级 | 机制 | 判定 |
|---|---|---|
| L0 报表菜单 | 预写 SQL 一问一答 | 死路（问题空间组合爆炸，人工枚举追不上） |
| L1 规则选择 | LLM 选规则 ID（当前 demo，四条规则） | 安全但不可扩展，过渡态 |
| **L2 原语+受约束组合** | 度量 × 维度 × 时间粒度，确定性编译器生成 SQL | **目标态，本体收益所在** |
| L3 自由 NL2SQL | LLM 直接写 SQL | 幻觉面失控，拒绝 |

### 2.3 提炼规则：卡片如何变原语

| 卡片成分 | 提炼为原语 | 注册表示例 |
|---|---|---|
| 去重键 | 身份规则（实体粒度） | 用户数一律归一到 usr_id |
| 聚合表达式 | 度量（measure） | 注册用户数 = COUNT(DISTINCT usr_id) |
| GROUP BY 列 | 维度（dimension） | 渠道 / 性别 / 时间粒度 |
| JOIN | 链接（link） | 注册事件 → 渠道 |
| 源表+过滤 | 对象绑定 + 口径声明 | 事实表 + 有效期 |

示例：REG_BY_CHANNEL 与 GENDER_RATIO 两张卡 → 一个度量（注册用户数）+ 两个维度（渠道/性别）→ 新问题"分性别分渠道注册数""按周注册趋势"零新人工 SQL，组合生成。
术语对齐（阿里 OneData 规范定义层，与数仓同学说同一种语言）：度量 = **原子指标**（基于业务事件、不可再拆）；**派生指标 = 原子指标 + 修饰词 + 时间周期**；维度 = "可称为实体对象"（反向佐证 §1.2 场景横切数据域）。

### 2.4 为什么必须先有卡再抽象
- 口径真相只存在于现行 SQL 里，字典里没有（干瘪是行业常态，语义在数仓同学脑子里）；
- 从已验证口径提炼的原语**继承正确性**——middle-out = 实体先行与问题先行的合取（见 §1.4 反面实证）；
- 安全边界不变：编译器是确定性代码，LLM 自由度 = 选原语 + 给参数。**智能在模型，正确在编译器，真相在已验证口径。**

### 2.5 卡增长律与自检器（核心实证数据点）
- **卡随度量×维度增长，不随问题增长**：11 道题背后仅 4-5 张卡。
- 方法论失败判据 = 每道新题都要新卡（退化 L0）；自检指标 = **新问题命中率 ÷ 新增卡数**；非菜单证明即此指标的验收形态。
- **非菜单第一验（2026-09-10）**：channel_l1 × week 组合（从未做卡、无 ADS 对照）以同源参照 SQL + Σ分组=总数不变量验证通过——"卡随度量×维度增长"拿到第一个数据点。
- 口径卡模板（填空题）：指标名/业务问题、口径使用方、指标分层+修饰词+时间周期、官方 SQL（可直接跑）、源表+过滤+时间字段、维度关联、去重键、更新频率/分区字段、已知坑。

### 2.6 能力分级之二：编排深度轴（M1-M3，与生成方式轴正交）

| 编排级 | 形态 | 现状 |
|---|---|---|
| M1 单轮识别 | LLM 一次语义识别→选规则→返回 | 当前 demo（四条规则） |
| M2 单步组合 | 原语×维度×时间组合，非菜单证明 | 当前在建（主线） |
| M3 多步编排 | 外圈规划循环套里圈安全管道 | **未建**（前提：L2 落地+第二场景接入，实施顺序不可倒） |

深邃问题 = 多次安全组合的编排：外圈 LLM 拆子问题（智能在模型），里圈每个子问题锁死在"选原语→编译→校验"管道（正确在编译器）。**NL2SQL 一深就幻觉，我们一深只是多查几轮。** 深邃问题需要的三样东西语义层全有对应物：指标树（复合→派生→原子）、对象+链接图（下钻分解）、业务链路（漏斗=沿时间对齐的事件序列）。
诚实边界：承诺**诊断级**（哪里低、差多少、沿什么维度分解、跟什么联动）；**处方级**（怎么改）输出候选动作+数据依据，真因果需业务实验验证——敢承诺诊断、不吹处方。

### 2.7 待验证（提纲，不展开）
- 11 题 4-5 卡仅为 mock 环境单场景数据点，多场景扩展后需复测；
- 热门聚合三档演进（V1 查询时全算 → V2 日志统计+人工确认 → V3 自动建议，不做全自动 view selection）；
- 指标树/漏斗编排的落地形态。

## 三、口径治理：四要素与三陷阱

【实证状态：已实证】2026-09-10 注册场景 T1a/T2 全天实录，三个陷阱全部当日真实踩到并解决，零生产成本（全在 mock 镜像库上暴露）。

### 3.1 核心论点
**口径 = 粒度 × 字段来源 × 过滤条件 × 快照策略**。"数字对不上"很少是算错，几乎总是四要素之一没说清。四个要素都必须显式建模进语义原语的绑定声明——靠人记忆/口头约定必然踩坑。

### 3.2 陷阱一：粒度（同数据不同粒度不可比）
- 现象：明细按二级渠道名分组得"优享+线上 232"，ADS 标准答案按三级渠道分组（同名拆 91+79+…）——直接比对全错。
- 解法：对账先统一粒度（三级聚合到二级后才相等，8 渠道全 PASS）。
- 论点：粒度是口径的组成部分，语义层的维度定义必须带层级。

### 3.3 陷阱二：字段来源（同名不同源不可混）
- 现象：明细自带渠道名"幽灵渠道"1 条，ADS 里没有这个组——数仓 ETL 用"明细渠道码 JOIN 维表"分组，落 null 组；用明细自带名字段则另立一组。
- 解法：维度绑定声明字段来源 = 维表 JOIN 列，禁止用明细自带字段（编译器硬编码此规则）。
- 论点：字段来源是口径的组成部分，两个"看起来一样"的字段是两个字段。

### 3.4 陷阱三：快照策略（日分区维表不选分区=扇出）
- 现象：渠道维是 62 天×15 渠道=930 行日快照，JOIN 不选分区 → 1760 行明细扇出成 108,937 行，数字全错且不报错。
- 解法：注册表绑定 snapshot_policy=latest_partition，编译器自动生成 `WHERE ds=(SELECT max(ds)…)`。
- 论点：快照策略是口径的组成部分，慢维度的"取哪天"必须显式。

### 3.5 一个业务名词多个口径：显式建模
"注册"在真实数仓中有**三个口径**：KPI 口径（fin）/ 原始注册（nonfin）/ 激活口径（act），三张 ADS 日度汇总正好对应——"一个业务名词多个口径、语义层必须显式建模"的核心案例（I4：两种口径=两条注册规则，不许发明第三种）。

### 3.6 对账的本质
不是"数字对上"，是**同一口径定义的两次独立实现必须收敛**（编译器生成 SQL vs 数仓 ETL 原样重放，双向 EXCEPT=0）。

## 四、架构：数仓=源 → 数据平面三区 → 语义层

【实证状态：部分实证】ADR-0010 已接受；镜像库（data/fortune_mirror.duckdb）三区已建并运转（mock 先行，血缘解析与三陷阱对账均在其上完成）；联调期调度与生产接入未到。

### 4.1 三层定位与查询路径
数仓 = 源 → 数据平面（自有镜像库）→ 语义层（元数据+编译器）。语义层只封装语义、不复制数据，但封装"对数据的访问"。查询路径：问题 → LLM 选原语（不写 SQL）→ 编译器生成 SQL → 数据平面执行 → 返回数字 + 审计记录。

### 4.2 三区
| 区 | 存什么 | 性质 |
|---|---|---|
| raw | 导入的原样表 | append-only/快照，不改不删；对账/审计/回溯的根基 |
| derived | 编译器生成的派生表 | 可随时 drop 重算 |
| meta | 语义定义/口径卡/审计日志 | 语义层的持久化 |

**账本不囤货：语义层是账本加理货规则，数据平面是货；查货走账本，账本不囤货——但能决定新添货架（物化）。**

### 4.3 派生即编译产物
三个触发：身份归一（mapping 链查询时算太贵）/ 热门聚合（每问一次全表扫）/ 本体友好重塑（特例封装进绑定）。派生表 SQL **由编译器从语义定义生成，不是手写**——因此可追溯（从哪个定义编译）、可重建（drop 重跑）、血缘自动成立（定义里写着源表）。这是与传统手写 ETL 的本质区别，也是"语义层管理数据平面"的真正含义。
诚实边界：维表快照只给当前状态，事件史以事实表为准；两者都没有的概念只承诺**事件锚点**（发生过、何时），不虚构完整状态变迁史。

### 4.4 引擎无关
语义定义不绑存储，绑"编译目标方言"：DuckDB（本地）/ PG / DWS（PG 系）/ MySQL 各一个 emitter；物理位置抽象为**逻辑表名注册表**（逻辑名→物理位置+引擎）——该间接层映射表本来就有，lakehouse 演进（Parquet on 对象存储 + Trino/StarRocks/DuckDB）预留免费。慢了换引擎/加物化，语义层一行不改。方法论写"引擎能力分级"，不硬性规定引擎。

### 4.5 ADS = 口径源，不进数据平面绑定
几百张 ADS 表（注册场景 8 张）不进数据平面绑定，其表结构与报表 SQL 进口径库当对账基准（考试答案）；数据平面只绑 DWD/DIM。**表在数据平面的角色 ≠ 表在语义层的角色。**

### 4.6 对数仓的要求 = 真相可及三条，不是建设规范
① 现行 SQL 可得；② 数据可导出；③ 字段语义有人能答（是非题形态，不写文档）。
数仓不规范时（如实名无事实表）成本不消失、**转移到派生层**。**语义层不要求上游完美，但会把上游的不完美显性化**（口径冲突/字段坑/血缘断链在对账时暴露，反哺治理）。分级适配：规范数仓→薄语义层，野数仓→厚派生层，同一套机制。

### 4.7 调度与性能（已定案，提纲级事实）
- 调度三档：研究期静态无调度 → 联调 T+1 cron 跟随导出（导出→刷 raw→重算 derived→自动对账）→ 生产接现成调度，不自研。
- 性能三层解：分析场景 join 九成是维表 join（星型，天然可控）/ 热点路径物化成对象宽表（join 提前算好，SQL 由编译器生成）/ 慢了换引擎加物化。

## 五、验证

【实证状态：部分实证】非菜单第一验通过、I1 拦截器先例在手、三陷阱对账当日闭环；**真数据数字对账未做**（见开放问题清单）。

### 5.1 不变量 I1-I5（governance 测试锁死）
- **I1 同源一致**：Σ分渠道 = 总数（热路径 vs 明细下推，1778/1781 拦截器先例）；
- **I2 身份粒度**：所有"用户数"度量 dedup 到归一身份，禁止混用 anony_id；
- **I3 时间显式**：默认时间字段必须显式声明（rgst_dt vs data_dt），禁止隐含；
- **I4 组合保真**：编译产物在卡片参数子集上必须与卡片 SQL 数字相等；
- **I5 拒答完整**：未注册原语的问题必须结构化拒答并说明，禁止静默降级。

### 5.2 对账三层
1. **同源一致（I1）**：同一口径的热路径与明细下推数字收敛；
2. **组合保真（I4）**：组合生成的新答案与原卡片口径数字相等；
3. **逻辑 vs 数字对账**：逻辑对账 = 同一口径定义的两次独立实现收敛（编译器 SQL vs 数仓 ETL 原样重放，双向 EXCEPT=0），**不依赖真实数据**——真实 ETL SQL 可在 DuckDB 逐字重放；数字对账才依赖真实数据（当前未做）。

### 5.3 非菜单证明
验收含"非菜单证明"：两道从未做过卡的题（如"8 月按周注册趋势""分性别分渠道注册数"）必须由组合生成答案且对账通过——**答不出 = 只是报表菜单，不验收**。首个实证：channel_l1 × week（§2.5）。跨域问题（如"注册后 N 日活跃"深入活跃域）结构化拒答且指向正确扩展路径。

### 5.4 mock 先行的价值
- 三陷阱全部在仿真数据上提前暴露，零生产成本；
- 逻辑对账不依赖真实数据：真实 ETL SQL 逐字重放即可验证口径逻辑，数字对账才依赖真实数据；
- 纪律：**mock 成功 ≠ 真数据验证声明**——价值验收以真数据数字对账为准。

### 5.5 待验证（提纲，不展开）
- 真数据数字对账（内网 DWD/DWS 脱敏通道接入后执行）；
- 对账断言参数化双 profile 实测；
- 口径确认状态变更 → 对账断言基线联动刷新机制。

## 六、治理与运维

【实证状态：部分实证】本体=git 声明式资产与确认生命周期运转中（口径规则已带 confirmed/unverified 状态与出处；注册场景血缘机器扫描 17 脚本/54 边/28 表）；管理台未实施；隔离四原则已定案。

### 6.1 本体 = git 管理的声明式资产
- 本体注册表**全局一份**（Pydantic 声明式文件，git 管理）：可 diff/评审/回滚/交接，数仓团队管 ETL 脚本的方式直接适用；版本/审计/回滚全部复用 git，**不自建版本系统**。
- 治理复用 git：Palantir Foundry 官方 proposal ≈ Pull Request（branch→提案→评审→合并），我们的 unverified/confirmed 状态 + git commit 是其**最小同构**。
- 三类变更：新场景/新口径 = 确认流程走一圈；源表改字段 = 改映射层（同 ETL 适配上游）；口径演进 = 改规则字段 + 对账回归。诚实成本：源表变更要同步映射（任何元数据层都有），换口径不散落。

### 6.2 对象全局唯一，场景引用不复制
场景引用共享对象、只新增场景特有的对象/事件/度量；对象缺字段就在对象上加（一处加处处用）。**重复定义同一业务概念 = 口径分裂的开始 = 本体头号反模式。**

### 6.3 确认工作台：机器起草 → 人勾选 → 落本体
生命周期：SQL 解析/机器起草 → 口径卡片（unverified）→ 是非题给数仓同学勾选（"激活边界 2024-07-09 仍生效？对/错"）→ confirmed → 写进本体注册表规则字段（永久带出处）→ 此后每次问答自动套用，口径文档自动沉淀。
**人的投入 = 选择题；机器的投入 = 解析/起草/执行/对账。**
移交路径：研究期 Rose 主维护（本体从场景长出）→ 生产期移交数仓团队，操作界面 = 确认工作台，同学不碰代码不碰 git 命令。红线：确认写操作必须走 git commit（破单一事实来源即废）。

### 6.4 管理台（后台；前台 = ChatBI）
- 自建薄壳：对标结论——开源两派（数据目录 OpenMetadata/DataHub = 描述型；语义层引擎 Cube/dbt = 无治理 UI）**均无可复用的操作型本体管理台**，引入 = 削足适履 + 部署重；
- 选型（ADR-0012）：AntD 6.x（仅管理台新包引入，chatbi 保持零组件库）+ React Flow **混合首页**（图谱主体 ≥70% 视区 + 顶部待确认横条；降级判据：一个月图谱交互趋零 → 换工作台首页）；MVP 3-5 天（浏览/确认/变更历史三件），排 F（语义层）交付后实施；
- 重点 = **用户友好的呈现与交互**：实体/关系/属性/口径怎么让不写代码的人看懂、敢改、改不错——版本管理不是难点。权限：MVP 全员可确认+落身份，接口预留双负责人制。

### 6.5 mock/真数据隔离四原则（已定案）
1. **schema 硬隔离**：mock.* 独立、真数据进本位 schema、永不混灌；
2. **编译器 profile 显式声明 + 结果打标"仿真数据"**；
3. **对账断言参数化双 profile**；
4. **生产期物理隔离独立实例**。（源自阿里全链路压测经验）

### 6.6 全仓扩展两速制
- **结构层（血缘）：全仓可扫**——工具批处理，一次建结构地图。已有实证：注册场景血缘 V0 机器生成，17 个 ETL 脚本全部解析成功，去重后 54 条边、28 张表（断链 7 张显性暴露）；
- **语义层（口径）：永远按场景滚**——机器扫得出语法，业务含义的最后一公里必须人确认（上千张表=几千道题没人答也不该答）。装修哪间房取决于谁要住（业务问题在哪）。

### 6.7 待验证（提纲，不展开）
- 管理台实施与确认写路径（先验证 git 写权限/身份）；
- 生产期移交数仓团队的完整演练；
