## 一、表规模（回答 Jack 质疑：55 不是瞎选，15 不够）

我的选表不是拍脑袋：55 张 = 贴源层 34 + 应用层业务 19 + 业务字典/组织 2，是完整读过 211 张表后，排除技术底座（流程引擎 30 / 决策引擎 91 / 系统管理 20 / Quartz 13）的结果。这些是真正的业务数据表。

但四路复核说得对：55 张全部建本体对象 = 过度设计（55x20 字段=1100 概念做不完）。正确做法是分层：

| 层 | 规模 | 干什么 |
|---|---|---|
| 数据生成层 | 55 张全部 | DES 配置驱动生成模拟数据（真实感的基础：表结构齐全） |
| 本体建模层 | 15-20 个核心对象 | 业务对象视角建模（客户/集团客户/预警信号/处置/审批单/风险项目/押品/集中度/指标/机构），不逐表建模 |
| 演示叙事层 | 5-8 个 demo 问题 | 围绕真实风险故事线（如"某集团客户关联交易预警→处置→审批→销号"） |

结论：数据全生成 55 张（保真实感）+ 本体聚焦 15-20 对象（控复杂度）+ 演示聚焦 5-8 问（保说服力）。三层解耦，互不牺牲。

为什么 15 个对象够真实感：真实感来自"业务链路完整 + 字段语义真实 + 有风险故事"，不来自表数量。预警→处置→审批→风险项目这条核心链，加上押品/集中度/共债/指标，已经覆盖金控风管部领导最关心的点。

## 二、动作清单（回答 Jack 质疑：2 个太少 → 扩为真实动作体系）

网络调研 + 表结构字典还原了真实风控预警的业务动作：

### A. 预警生命周期动作（核心）
| # | 动作 | 说明 | 双签 |
|---|---|---|---|
| A1 | 预警信号确认 | 人工核验系统预警（确认/误报） | 低风险 |
| A2 | 预警等级调整 | 红/黄/蓝 等级上调下调（建议→确认→执行） | 高风险 |
| A3 | 预警事由修改 | 补充/修正预警原因 | 低 |
| A4 | 处置方案提交 | 选定处置措施（约谈/追加担保/压降额度/提前收回/诉讼） | 高风险 |
| A5 | 处置审批 | 岗位级审批链（风险预警管理岗→风控部门→金控领导，对应 approve_node 多级节点） | 高风险 |
| A6 | 推送子公司/金控领导 | 预警推送（push 表：推送人/接收人/接收批示） | 低 |
| A7 | 预警销号/解除 | 处置完成，销号闭环 | 高风险 |

### B. 集中度/限额动作
| # | 动作 | 说明 | 双签 |
|---|---|---|---|
| B1 | 集中度限额调整 | 调整大额客户集中度限额（保留旧值审计） | 高风险 |
| B2 | 集中度预警调整 | 集中度预警信号级别调整 | 高风险 |

### C. 风险项目管理动作
| # | 动作 | 说明 |
|---|---|---|
| C1 | 风险项目登记 | 录入风险项目（五级分类/担保方式/减值） |
| C2 | 项目进展更新 | 更新处置进展 |

动作机制（读/写分离）：所有动作走动作模板——固定参数 schema + 前置校验 + 状态机 + 权限 + 双签 + 审计，LLM 只做"问询理解+动作选择+参数填槽"，不生成任何写语句。这与只读查询（受限结构化查询）是两套引擎（四路复核一致意见）。

## 三、本体设计（本体优先 + 表为业务参考）

- 起点：先定义安平金控的语义层（对象/链接/动作/指标），表结构 211 张只作为字段语义对齐 + 脱敏映射参考（保证业务基础坚实、不闭门造车）。
- 对象类型（15-20 个）：Customer(单一客户) / GroupCustomer(集团客户) / WarnSignal(预警信号) / Disposal(处置) / ApprovalOrder(审批单) / RiskProject(风险项目) / Pledge(押品) / ConcentrationLimit(集中度限额) / CoDebt(共债客户) / Metric(指标) / Organization(机构) ...
- 链接类型：客户-集团(所属)、客户-预警、预警-处置、处置-审批、风险项目-客户、客户-押品、客户-集中度、客户-共债 等。
- 指标注册：comb_dim_index 维度指标（客户/机构/集团x维度x指标值）→ 注册 + 物化预聚合（ChatBI 数据底座）。

## 四、安平金融控股集团设定（数据故事）

- 名称：安平金融控股集团有限公司（虚构）。
- 牌照：全牌照——银行（安平银行）+ 证券（安平证券）+ 保险（安平人寿）+ 信托（安平信托）+ 融资租赁（安平租赁）+ 基金（安平基金）。
- 视角：集团风险管理部统一风管（跨业态风险监测），下属子公司风管岗分工处置。
- 数据量：总 20~30 万行（客户 5 万 / 预警 8 万 / 指标 5 万 / 审批 2 万 / 其他），比 S2 小便于演示。
- 风险故事线（演示主线）：某集团客户（如"华夏新能源集团"）出现关联交易+押品贬值预警 → 确认 → 升级红色 → 处置方案（追加担保+压降额度）→ 审批链 → 推送子公司 → 销号。数据围绕故事设计，一问一个准。

## 五、DES 架构（配置驱动 + 金融专用生成函数，既真实又可配）

- 配置驱动：55 张表定义（字段/类型/枚举/外键/依赖/行数）进 YAML，DES 读配置生成——可复用、可复现（固定 seed + manifest 校验）。
- 金融专用生成函数（真实感来源）：贷款合同号编码规则、五级分类迁移路径、预警信号时间衰减、押品估值模型、集中度计算逻辑、共债关联——用注册的专用生成函数实现，不靠通用随机。
- 易用性第一位（Jack 要求）：一条命令生成 + README 级文档 + 示例配置。

## 六、里程碑（垂直切片并行，非严格串行）

M1a 选表+脱敏+表结构确认（1 周）
   -> M2 本体语义层（第一版本体 3-5 对象先跑通，迭代扩展）
          -> M3 Agent 对话窗口（读引擎+写引擎，30 题评测集）
   -> M1b DES 配置化+数据生成（55 张 20-30 万行）
   -> M4 演示界面（全程并行，mock 数据开发 UI）
   -> M5 收尾（备份清空/测试/文档/验收）
关键路径：M1a -> M2 <-> M3 -> 联调 -> M5

- M1a 选表脱敏：55 张选表 + 全表改名（ap_* 前缀）+ 字段语义改写 + 字段值脱敏。产出：脱敏 schema 清单 + ADR。
- M2 本体：15-20 对象 + 链接 + 动作模板 + 指标注册物化。产出：本体可查、图谱无孤岛。
- M3 对话：读引擎（受限结构化查询产品化）+ 写引擎（动作模板）+ 金融领域注入 + 30 题评测集 + 双签 UX。产出：精准问答 + 真实动作闭环。
- M4 界面：Landing + 数据浏览 + 图谱 + 对话窗口 + 演示剧本（5 步）+ 拒答演示。产出：5 分钟 Demo 顺畅。
- M5 收尾：备份旧数据（135M<200M 达标）+ 清空 + 全量 pytest + CI + ADR/AGENTS.md 更新 + 文档。
