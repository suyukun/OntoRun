## 0. 一句话设计

**把 P1.5 的治理骨架接到运行面：① 操作权限实接线（6 动作 → 对象/操作映射 + PermissionEnforcer 真执行，deny→PERMISSION_DENIED，越权 0）；② 数据权限下沉（DuckDB 对象级视图，与 P2 读侧 visible_attributes 分层：语义层标注 + 数据层强制）；③ 会话持久化（S1 内存 SessionManager → SQLite sessions/messages + TTL 30 天 + 审计关联，重启重建 Agent 回放历史）；④ 审计收口（演示库旧链回填 + 字段级镜像完整性 + TTL 清理任务）。**

## 1. 操作权限接线设计

### 1.1 action → (object_type, operation) 映射表
| 动作 | object_type | operation | 说明 |
|---|---|---|---|
| create_order | Order | write | 下单写回 |
| confirm_order | Order | write | 确认 |
| cancel_order | Order | write | 取消（三问核心） |
| create_shipment | Shipment | write | 发货 |
| adjust_inventory | Inventory | write | 库存调整 |
| approve_refund | Refund | **approve** | 双签退款（审=人专属 V9） |

映射表 = 单一来源常量（ACTION_PERMISSION_MAP，放 src/runtime/permissions.py 或 action_engine），机验「每动作有映射、operation 合法」。

### 1.2 actor → PermissionSubject 解析
- API 层：X-Actor 头 → PermissionSubject(kind="human", id=actor)（S1 已有 X-Actor 白名单校验）
- Agent/LLM 执行：PermissionSubject(kind="agent", id="llm")
- resolve_actor(actor, is_llm) 纯函数；approve 动作强制 human（V9：agent 一律拒）

### 1.3 PermissionEnforcer 实接线（P1.5 预留 + 9858f83 接口）
- ActionEngine.execute ①参数校验后 ②源库事务前插门位（已就位）：调 enforcer.decide(action_name, params, actor) → deny → rejected + PERMISSION_DENIED + 审计落 rejected（含 matched_policy_ids）+ **零源库变更**
- 接线：DefaultPermissionEnforcer（包装 permissions.decide）——动作名 → 映射表取 (object, operation) → decide(subject, object, operation) → None（无策略）= fail-closed deny
- **越权 0 口径**：任何无显式 allow 策略的动作执行 → denied；approve 给 agent → denied

## 2. 数据权限下沉设计（C3）

### 2.1 分层
- **语义层（P2 已做）**：读侧 decide(read) + visible_attributes 过滤返回列（对象/属性级标注）
- **数据层（P4 下沉）**：DuckDB 对象级视图——对 metrics.db / 物化库建「权限视图」：按对象类型读权限创建可见视图（deny 对象不出现在视图），查询强制走视图（对象级强制，属性级仍靠语义层标注）
- S2 范围：对象级下沉（视图）+ 属性级标注（语义层）；字段级 RLS 发布期（PostgreSQL）

### 2.2 实现形态
- create_permission_views(registry, permission_registry, subject) → DuckDB CREATE VIEW（每对象一张，按 decide 结果过滤）
- 契约执行器查询路径改为走视图（对象级 deny → 视图不存在/空 → 拒答）

## 3. 会话持久化设计（议题 4 形态）

### 3.1 存什么/存哪/怎么恢复
- **sessions 表**（SQLite，复用 store.py schema 管理模式）：{session_id PK, created_at, updated_at, ttl_class, audit_link}
- **messages 表**：{message_id PK, session_id FK, role, content, tool_calls_json, created_at}
- **恢复**：重启后 SessionManager 从表加载消息 → 重建 Agent（配置固定）→ 回放历史消息（Agent 支持从历史恢复，S1 agent 已支持 history 累积）
- 会话状态（选中对象/待确认提议）：pending_confirm 序列化到 sessions（ToolCall JSON）
- **TTL**：30 天分级（sessions 表 ttl_class；清理任务 P4 落：DELETE WHERE updated_at < now-30d，可配）

### 3.2 审计关联
- 会话内动作审计：session_id 写入动作审计（audit_log 加 session_id 列，幂等补丁）——可追溯「谁在什么会话做了什么」（议题 4 形态）
- 会话本身不存审计数据（C5：审计独立）

### 3.3 S1 改造
- SessionManager 内存态保留为缓存；读写走 SQLite（写-through）
- get_or_create/set_pending/clear_pending 全部落表

## 5. 门禁 → 可机验断言（供测试角色 test_p4_*.py）
| 门禁 | 断言 |
|---|---|
| **越权 0** | ① 无策略动作执行 → rejected+PERMISSION_DENIED+审计+零源库变更；② approve 给 agent → denied；③ allow 策略 → 执行成功；④ X-Actor human approve 通过 |
| **审计不可篡改** | ① UPDATE/DELETE 被 WORM 拒；② 哈希链 verify ok；③ 旁路篡改检出；④ 演示库回填后 verify ok |
| **会话重启不丢** | ① 建会话+发消息 → 重建 SessionManager → 会话可恢复+消息完整；② 待确认提议恢复；③ TTL 过期清理生效 |
