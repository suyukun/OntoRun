## 0. 执行摘要

1. **定位裁决**：管理台 = ChatBI 数字的可信生产线——ChatBI 负责把数字算出来说得清，管理台负责让每个数字**有人认账**；验收即三问测试（怎么算的/谁确认的/哪个版本），管理台是信任链里唯一「人的判断进系统」的环节，这是它不可替代的理由。
2. **四页职责重锚**：口径确认=信任链核心（最重投入）；首页=待办+健康度驾驶舱（图谱降为概览卡与局部视图）；对象页=数字与口径的说明书（口径字典）；变更历史=审计轻量（Jack 已降级，仅补诚实性小项）。
3. **万表策略一句话**：展示的是「信任状态」不是「全部表」——全图退役为统计数字，图谱转为**局部血缘视图**（从任一数字/表进入的邻域图），搜索升一等公民，分层/邻域查询留给后端。
4. **MVP 裁决**：P1 = 分歧裁决卡（R8）+ 确认队列清爽化 + 全局搜索（前端过滤）+ 降级模式诚实标记，合计 ≈4.5 天，与门槛稿工期吻合；P2 = 脚本片段展开、对象历史 Tab、万表后端地基。
5. **拖拽明确不做**：Jack 说「卡片不能拖动」，其真实诉求是「我要能看清我要的」——用搜索定位+固定分层布局满足，手工拖拽布局在数据增量下必然回乱，不做。
6. **开放问题恰好 5 条**（PC-1..PC-5，§6）：首页降级是否提前触发、术语双编码、R8 裁决逃生口、万表地基本轮投不投、ChatBI 透出钩子——全部不推翻已裁决策，每条带默认建议。

## 1. 定位与页面职责

### 1.1 产品定位：ChatBI 落地信任链中的管理台

信任链条：**数仓脚本（事实从哪来）→ 语义注册表（口径怎么定）→ 管理台确认（人认账）→ ChatBI（数字出口）→ 业务决策**。

- ChatBI 回答「数字是多少」，管理台回答「这个数字凭什么信」——两者是同一本体的两种界面人格（Palantir Ontology Manager / Object Explorer 同构，UX 调研 v0.1 已证）。
- 管理台的核心产出不是「注册表的浏览界面」，是**一条条带身份的 git commit**：每确认一条口径，就有一个数字从「机器算的」变成「人认账的」。确认数/规则数 = 数字可信率的分母与分子，这就是首页健康度的定义。
- 北极星验收形态：Jack 在 ChatBI 里随便指一个数，王工不看代码能答出三问——三问的答案全部存放在管理台（对象页口径卡 + 确认记录 + commit 短码）。

### 1.2 四页职责裁决表

| 页面（现名→建议名） | 一句话职责 | 核心用户动作 | 投入权重 |
|---|---|---|---|
| GraphHome → **首页** | 今天要钉死哪些数字：待办队列入口 + 信任健康度（N 待确认 · X% 已确认 · M 条分歧未裁）+ 分层概览（全图只以统计出现） | 看健康度 → 点「去确认」；点概览卡进局部血缘 | 中（清爽化重排） |
| ObjectsPage → **数字与口径** | ChatBI 每个数字的说明书：度量=数字怎么算，维度=按什么切，规则=算数的规矩（口径字典） | 搜数字/表名 → 看口径卡 → 跳确认或历史 | 中低（改名+双编码） |
| RulesPage → **口径确认**（名不动） | 信任链核心：把「机器算的口径」变成「人认账的口径」——是非题队列 + 分歧裁决卡 | 填名 → 逐条是非确认 / R8 三选一裁决 | **最高**（P1 主战场） |
| HistoryPage → **变更历史**（名不动） | 审计轻量：谁在哪个版本认了账（人话账本） | 查记录；git 降级时明示「未产生 commit」 | 最低（仅补降级标记） |
| ObjectDetailPage（不入导航，维持现状） | 单个数字的全部真相：定义/绑定/规则/关系/（P2 增变更 Tab） | 从列表行、搜索、图谱节点进入 | P2 |

裁决理由：Jack 四条反馈逐条对照——①首页挤=图谱降维（见 §3）；②对象页专业=口径字典人话化（见 §4）；③不敢确认=分歧裁决卡+人话是非题（P1 核心）；④历史好简单=顺水推舟降级，只补「git 降级必须明示」这一诚实性边界（门槛稿 A4-2 已要求）。

| 6 | toast：「裁决已记录：并存 · 王工（版本 e4f5g6h）」 | — | 首页红点消解；图谱该表红色虚线变实线；健康度「分歧未裁」1→0 |

## 3. 万表规模的展示策略（回答 Jack 原话：「上万张表怎么处理，如何展示」）

**总原则：管理台展示的是「信任状态」，不是「全部表」。** 表是数仓的资产，数字的可信度才是管理台的标的——万表进来，界面不变大，只会让统计数字变大。

### 3.1 三层漏斗：万 → 百 → 十 → 一屏

1. **聚合层（首页，万→百）**：全图不再以力导向渲染，改为**分层/分域概览卡**——ODS/CDM/ADS/DIM 四层各一张卡（表数 · 未确认口径数），未来加业务域维（客户域/交易域/授权域…）。全图在首页的唯一存在形式 = 一行统计：「3,214 张表 · 87 条口径 · 62% 已确认」。点概览卡进该层对象列表（带筛选），不画图。
2. **检索层（搜索+筛选，百→十）**：顶栏全局搜索升一等公民（搜数字名/表名/规则关键词），万表时代搜索>导航；对象列表加业务域/分层筛选与服务端分页。
3. **关系层（局部血缘，十→一屏）**：图谱重定位为**局部血缘视图**——从任一数字/表/规则出发，展示中心节点上下游 N 度邻域（默认 1 度，可手动加层），节点硬上限（建议 50，超出提示「先筛选再加层」）。图的入口=对象详情「看血缘」、搜索结果、首页概览卡，**不再是首页主体**。

### 3.2 边界与分工

| 归产品/前端（本轮） | 归后端能力（P2/BACKLOG） |
|---|---|
| 首页统计条+分层概览卡（读现有 /api/lineage 的 layers 统计即可） | 邻域查询 API：/api/lineage?center=X&depth=2（当前 54 边全量返回无压力，万表必须服务端裁剪） |
| 局部血缘视图组件（前端裁剪现有 edges 数据即可起步） | 搜索索引、业务域/分层元数据维护、服务端分页 |
| 未确认高亮、点击抽屉（保留现有交互） | 血缘解析自动化（新表入仓自动挂边） |

### 3.3 明确不做（写进验收，防范围失控）

- **不做卡片拖拽布局**：手工布局在数据增量下必然失效（拖完→新表进来→又乱），且拖拽是「摆弄」不是「看清」；Jack 诉求的实质由「搜索定位+固定分层坐标+未确认高亮」满足（ADR-0012 已有的业务域聚类预置坐标方向继续走）。
- **不做全图性能优化**（canvas 换型、万节点渲染）：那是把产品问题当技术问题的方向；UX 调研 v0.1 §3.2 的退路条款（对象涨到几百+再评估 Cytoscape/G6）继续有效，但触发前提改为「局部视图仍不够用时」。

## 6. 开放问题 PC-1..PC-5（进 NC 答题卡，Jack 逐条裁决）

### PC-1 首页降级是否提前触发
- **背景**：ADR-0012 混合首页带降级判据（上线满一个月图谱交互趋零→换工作台），但 Jack 本轮已主动抱怨首页「一大堆挤在一起」且追问万表——等一个月的观测前提已被老板的实际不满抢跑。
- **选项**：a) 本轮直接把首页图谱降为分层概览卡+局部视图（待办+健康度升第一屏主体），一个月后仍按判据复查定去留；b) 维持全图混合首页原样，只做视觉清爽化，等判据自然触发；c) 首页做「概览/图谱」双 Tab 并列。
- **默认建议**：**a**——它不是推翻混合首页（图谱仍可从概览卡进入），是把 ADR-0012 的降级方向提前做了一半，且与 §3 万表策略同构；b 等于对已知不满不做响应，c 多一层导航与 Jack「清爽」诉求相悖。

### PC-2 对象页术语人话化的深度
- **背景**：Jack 原话「对象列表有点专业，看不懂也不会用」，但主用户王工（数仓）日常用「度量/维度」是效率语言，全替换反而让干活的人别扭。
- **选项**：a) 双编码：Tab/字段主标签保留专业词+人话副标（「度量 · 数字怎么算」）；b) 全人话替换（数字/切法/规矩）；c) 顶部加「老板模式」开关切换两套文案。
- **默认建议**：**a**——一份界面同时伺候两个人格（王工和 Jack），成本最低；b 驱逐专业用户，c 维护两套文案且开关本身是新概念，「妈妈能看懂」靠副标达成即可。

### PC-3 R8 分歧裁决的选项集合与逃生口

### PC-4 万表地基本轮投不投
- **背景**：Jack 已问万表，但当前实证规模是 10 规则/54 边/28 表——首页拥挤的真实原因是布局与信息密度，不是数据量；邻域 API 等后端改造（+1-2 天）会挤占 P1 预算。

### PC-5 信任链向 ChatBI 的透出时机
- **背景**：北极星「让 ChatBI 每个数字可信」的最终验收发生在 ChatBI 界面（数字旁能否看到「谁确认的」），但本轮非目标明确不动 chatbi/，透出是跨应用决策。

- **默认建议**：**a**——范围纪律优先（A5 非目标「不动 chatbi/」），数据结构预留即可让未来透出变成 ChatBI 侧纯读任务；b/c 待 ChatBI 展示层迭代排期时另行开单，届时管理台零改造。
