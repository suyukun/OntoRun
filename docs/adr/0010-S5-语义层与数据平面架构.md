# ADR-0010：S5 语义层与数据平面架构（数仓=源·三区镜像库·派生即编译产物）

日期：2026-09-09（夜间架构对齐会，Jack 与 Rose）
状态：已接受（Jack 口头确认方向，待方案 v0.2 随审）

## 背景（现状）

财富广场语义层落地启动前，Jack 连续五问架构根本：语义层封装语义还是封装数据？数据存哪？派生表怎么建、谁调度？存储引擎换了怎么办？同时澄清关键事实：

1. **Jack 本人即财富广场数仓负责人**——不存在"配合度"问题，操作单 v0.1 的"Jack 当传声筒转发消息给数仓同学"设计整个作废，重做为"Jack 拿着活清单直接派给最熟悉注册的同学"。
2. **生产环境与互联网物理隔离**（金融企业），本机 Demo 无法连生产；数仓跑在华为云 DWS（MPP，PG 系）。
3. ADS 层极重：几百张表、一张对应一张报表——这是口径资产的富矿，不是负担。

## 备选方案

| 备选 | 结论 |
|---|---|
| 语义层复制一份数据（封装数据） | 否：源/镜像/语义层三份数据，同步链更长一致性更差；复制过来只是另一个数仓，口径问题原样未解 |
| 语义层直连生产数仓执行查询 | 否（当前）：网络隔离 + 生产跑批管控固定，外部 SQL 打不进去。生产成熟后可演进 |
| 从 ERP 原始层开始重塑（Palantir FDE 模式） | 否：数仓 ERP→ODS→DWD→DWS 加工链已存在，FDE 最贵的重塑活数仓已干完 90% |

## 决定

### 1. 三层定位：数仓=源，数据平面=镜像库，语义层=元数据+编译器

- **数仓 = 源**。按语义层声明的范围导出（按场景拉取，最小字段）。
- **数据平面 = 自有镜像库**，三区：
  - `raw`：导进来的原样表，append-only/快照式，不改不删——对账、审计、回溯全靠它；
  - `derived`：编译器生成的派生表，可随时 drop 重算；
  - `meta`：语义层持久化——对象/度量/映射定义、口径卡、审计日志。
- **语义层只封装语义、不复制数据，但封装"对数据的访问"**：定义（对象/度量/维度）+ 映射（指回数据平面表字段）+ 编译器 + 规则。查询路径：问题→LLM 选原语→编译器生成 SQL→打数据平面执行→返回数字+审计。Palantir Foundry 同构（Ontology 绑定 dataset 不存数据；headless BI 形态，Cube/dbt metrics 同族）。

### 2. 派生层：三个触发条件，派生表=编译产物

| 触发 | 例子 | 为何查询时算不行 |
|---|---|---|
| 身份归一 | 匿名→注册打通（mapping 链） | 跨表递归解析，重算贵且易错 |
| 热门聚合 | 分渠道注册日表 | 每问一次全表扫 |
| 本体友好重塑 | "实名存于用户维表字段"→重建成 RealNameEvent | 让对象绑定干净，特例封装进绑定 |

派生表 SQL **由编译器从语义定义生成**，不是手写——因此可追溯（从哪个定义编译）、可重建（drop 重跑）、血缘自动成立（定义里写着源表）。这是与传统手写 ETL 的本质区别，也是"语义层管理数据平面"的真正含义。

诚实边界：维表只有当前快照无历史时，重建的是**事件锚点**（发生过、何时），不虚构完整状态变迁史。写进方法论。

### 3. 调度三阶段（不自研调度引擎）

1. 研究期（现在）：两个月静态导出，无调度；
2. 联调期：T+1 轻量跟随导出节奏（导出→刷 raw→重算 derived→自动对账），cron 级；
3. 生产期：接现成调度（DolphinScheduler / 数仓出数通知），铁律不造轮子。

### 4. 对数仓的要求 = "真相可及"三条，不是建设规范

① 现行 SQL/口径能拿到（哪怕散在几百张 ADS）；② 数据能导出（对账）；③ 字段语义有人能答（问答有出口，形态=是非题清单，不写文档）。

数仓不规范（如实名无事实表）时成本不消失、**转移到派生层**。方法论论点：**语义层不要求上游完美，但会把上游的不完美显性化**（口径冲突/字段坑/血缘断链在对账时暴露，反哺治理）。分级适配：规范数仓→薄语义层，野数仓→厚派生层，同一套机制。

**ADS 定位 = 口径源**：几百张 ADS 表不进数据平面绑定，但其 SQL 是口径库主要原料（对账考试答案）。表在数据平面的角色 ≠ 表在语义层的角色。

### 5. 引擎无关：绑"编译目标方言"，不绑存储

语义定义引擎无关；SQL 生成分方言 emitter（DuckDB 本地 / PG / DWS / MySQL，DWS 为 PG 系成本低）。物理位置抽象为**逻辑表名注册表**（逻辑名→物理位置+引擎）——该间接层映射表本来就有，lakehouse 演进（Parquet on 对象存储 + Trino/StarRocks/DuckDB）预留免费。慢了换引擎/加物化，语义层一行不改。MySQL 可跑但无列存，分析弱靠物化撑——方法论写"引擎能力分级"。

## 理由

- 网络隔离与生产管控决定了"镜像库起步"没有第二选择；且 Foundry 同构使其成为方法论论点而非妥协——**上游建模越规范，语义层越薄**，这是数仓场景做语义层的天然优势。
- 查询时编译 vs 加载时物化的取舍：第一版数据量小、全查询时计算；物化按审计日志统计（热门检测=审计日志的复用视图，V1 查询时算→V2 日志统计+人工拍板→V3 自动建议，不做全自动 view selection）。

## 后果

- 正面：口径唯一真相源（一个指标定义一次，消灭"同一个数三个版本"）；LLM 护栏（选原语不碰 SQL）；数据安全红利（镜像库可脱敏、最小字段、全审计）。
- 代价：镜像库同步运维与存储成本；查询时 join 的性能需靠物化+引擎演进兜底（维表 join 星型可控 / 对象宽表物化 / 引擎可换三层解）。
- 关联：能力分级路线（单轮识别→单步组合→多步编排）见方案 v0.2 §十一，不属本 ADR 范畴。
