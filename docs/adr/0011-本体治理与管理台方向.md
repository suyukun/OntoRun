# ADR-0011：本体治理与管理台方向（对象全局复用·git 治理·自建薄壳）

日期：2026-09-10（晚间讨论，Jack 确认方向）
状态：已接受（UX 概念设计 5 个开放问题待 Jack 拍板后实施）

## 背景
Jack 三连问：①对象（User/Channel）跨场景是否重复定义？②数仓团队不会 Pydantic/git，本体怎么维护、怎么移交？③管理台的做法是 Palantir 真实形态还是自创折衷？

## 决策

### 1. 对象全局唯一，场景引用不复制
本体注册表全局一份；场景（注册/活跃/交易）引用共享对象、只新增场景特有的对象/事件/度量；对象缺字段就在对象上加（一处加处处用）。**重复定义同一业务概念 = 口径分裂的开始 = 本体头号反模式**。

### 2. 本体 = git 管理的声明式文件（Pydantic），治理复用 git
- 变更走 git 流：Palantir Foundry 官方治理原话 proposal ≈ Pull Request（branch→提案→评审→合并）——我们的 unverified/confirmed 状态 + git commit 即其**最小同构**；
- 维护移交路径：研究期 Rose 主维护（本体从场景长出）→ 生产期移交数仓团队，操作界面=确认工作台（是非题勾选→落库走 git commit），同学不碰代码不碰 git 命令；
- 版本/审计/回滚全部复用 git，**不自建版本系统**。

### 3. 管理台（后台；前台=ChatBI）自建薄壳
- 对标结论（docs/research/本体管理台对标调研_v0.1.md）：开源两派（数据目录 OpenMetadata/DataHub=描述型；语义层引擎 Cube/dbt=无治理 UI）**均无可复用的操作型本体管理台**；引入=削足适履+部署重；
- 方案：FastAPI admin router + 独立 Vite 入口（npm workspaces 同仓）+ AntD 5 + React Flow（图谱）；MVP 3-5 天（浏览/确认/变更历史三件），排 T2 后期；
- **重点=用户友好的呈现与交互**（实体/关系/属性/口径怎么让不写代码的人看懂、敢改、改不错）——Jack 明确：版本管理不是难点；
- UX 概念设计见 docs/research/本体管理台UX调研与概念设计_v0.1.md（6 页信息架构，5 开放问题待拍板）。

### 4. 正统性对照结论（回应"是不是三四流折衷"）
架构/消费侧与 Palantir Foundry Ontology、dbt MetricFlow、headless BI 全部同构；middle-out 逆向生长（从存量 ETL 长本体）为我们的差异化主张（学术出处 Uschold & Gruninger 1996），非折衷。

### 5. 口径卡增长律（方法论自检器，Jack 挑战确立）
**卡随度量×维度增长，不随问题增长**（11 道题背后仅 4-5 张卡）；方法论失败判据=每道新题都要新卡（退化 L0）；自检指标=新问题命中率 ÷ 新增卡数；非菜单证明即此指标的验收形态。第一期 Q1-Q11 全列。

## 后果
- 正面：移交路径成立（不依赖 Rose 在线）；治理零新造（git）；管理台可控成本（3-5 天 MVP）；
- 代价/风险：UX 开放问题未拍板前不实施；确认写操作必须走 git commit（红线，破单一事实来源即废）；
