# 本体落地切入路径辨析：KPI 驱动 vs 实体驱动（白皮书素材 v0.1，2026-09-08）

> 缘起：Jack 在评审设计稿 v0.2 时的方法论恍惚——「我们以注册/活跃两个 KPI 切入，可我印象中本体论应该先识别实体、关系、属性。到底哪个对？」
> 结论先行：**两者都对一半，且不在同一层。教科书与 Palantir 实践的共同答案 = 问题驱动切入（decision-back / competency questions），实体关系组织（middle-out）。** Jack 已于 2026-09-08 拍板过同一原则：「切入按问题、组织按实体」（handoff-2026-09-08 关键决策）。

## 一、先拆掉一个错误印象：「注册/活跃只是动作，不算本体」

不对。事件/过程类是本体的第一等公民。企业本体的经典构成就是三层：静态（实体/结构）、**动态（事件/过程/状态）**、意图（目标/约束）——TOVE 企业本体里 Activity 是独立的核心本体。我们设计稿里 E1-E13（事件）、L1-L6（关系）、派生规则（口径）全是标准本体构件。「以 KPI 切入」≠ 离开本体论：KPI 背后是事件类型 + 实体类型 + 口径规则的全套。

## 二、真正的分野：data-forward vs decision-back

**data-forward（实体清单优先的错误用法）**：从全部表出发盘点实体。Palantir 社区文章（Palantir Study 08，腾讯云开发者社区，2026-09）里恒川的故事：数据团队带着 26 个系统、480 张表、3000+ 字段进研讨会，两小时白板上出现 20 多个候选 Object Type，被业务一句「下次缺料时，这套东西能不能让我在排产冻结前批准方案」问哑。四种失败模式：对象多却无决策使用；属性齐全却没人知道哪些改变选择；Link 密如 ER 图却不解释影响；页面能看却无法安全改变业务状态。

**decision-back（正确切入）**：Outcome → Decision moment → Action 契约 → 反推事实/关系/判断/证据 → 得出最小 Object/Link/Property 集合 → 用 Object Set 固定行动范围 → **最后**才核对 Dataset/Pipeline/缺失数据。筛选标准一句话：「删掉这个属性，目标决策还能安全完成吗？能 → 不进初版。」

**Palantir 官方最佳实践**（文中引用官方文档 Ontology design best practices / Delivering a use case）：先建模业务域，再连接数据，小步增量演进——**而不是把现有数据库结构原样搬进 Ontology**。

**行业方法**：EKGF（OMG 企业知识图谱论坛）的 Use Case Tree Method——企业知识图谱同样以用例树为起点、图谱随用例生长。

**学术根基**：Gruninger & Fox (1995) TOVE 方法论——本体设计起点 = Competency Questions（本体必须能回答的问题清单，兼作验收标准）；Uschold & Gruninger (1996)——三种构建策略 top-down / bottom-up / **middle-out**，实践推荐中间向外：从核心概念（既有问题牵引又有数据支撑的）向外生长。

## 三、双轨方法论（我们的表述）

- **切入点（战略层）= 问题/KPI 驱动**：决定范围、优先级、验收。第一问（S1 注册漏斗 / S2 日活结构 / S3 活动参与）就是 ChatBI 场景的 Decision moment；设计稿域划分（注册域/活跃域）= KPI 命名空间。
- **组织结构（架构层）= 实体+关系为骨架**：对象/链接一旦建立即全局注册复用（O1 User 是三案共同底座），KPI 口径变化只改规则层不改骨架。实体骨架稳定（用户/渠道十年不变），KPI 口径易变（目标年年调）——骨架按实体组织才能长期治理。
- **合并律**：从问题切入 → 切进来的实体沉淀为全局骨架 → 下一个问题复用骨架只加增量。这就是 middle-out 的操作化。

## 四、对设计稿 v0.2 的自检（用 decision-back 标准过一遍）

- ✅ 范围由两域 KPI 圈定（=Decision moment 锁定）；
- ✅ 24 张表是从手绘图关键表反推的最小集，不是 480 张全搬；
- ⚠️ 待补：每个对象/事件缺一行「它回答第一问的哪部分」——评审时逐个挂到 S1/S2/S3 上，挂不上的降级为备货（对应「删掉属性决策仍可完成 → 不进初版」）；
- ⚠️ 待补：缺失数据核对（六步的最后一步）——合成样本生成前，应先列「真数据按第一问产出时的可得性清单」。

## 五、语义层的计算边界（2026-09-08 Jack 两问的裁决）

**纠偏**：语义层不执行计算——它确认口径、生成 SQL、下推数仓查询引擎执行。计算资源永远是数仓的，「撑不撑得住」与本体层无关。

**明细层与汇总层的双路径**：
- 汇总层 DWS/ADS = 热路径（高频快答案）；
- 明细层 DWD = 冷路径（下钻/溯源/即席）——语义层只登记其元数据（粒度/口径/关联路径）+ 按需生成 SQL 下推，明细永不进运行时内存；
- 明细层三重意义：下钻路径声明、口径可验证（派生规则声明汇总数的聚合来源，数字不裸奔）、即席 fallback。

**未预汇总查询的三级服务策略**（例：「男女注册比例」未预聚合）：
1. 先看维度挂载粒度：维表属性统计（usr_sex 在 DIM_CU_USR_INFO_DF）扫维表而非事实表，成本差数量级——「没预汇总」≠「要扫大表」；
2. 即席下推：语义层生成 SQL 交数仓引擎执行，回答标注「明细级即席计算 + 数据截至时间」；
3. 即席也不可行：诚实降级（「需离线物化，T+1 可答」）+ 登记为派生指标候选进需求流。

**物化循环**：三级策略使数仓演进第一次获得精确需求反馈——查询未命中热路径 → 语义层捕获登记 → 高频者物化成新热路径。「预聚合建哪些」从架构师拍脑袋变成问题驱动。

**MVP 裁决（财富广场）**：第一问切片全走热路径（DWS 已就位）；DWD 只登记元数据，冷路径 MVP 不开；维表属性类问题作为冷路径启用后的第一道验收题。

## 六、白皮书论点雏形（learn in public 素材）

1. **本体论落地没有「实体优先 vs 问题优先」的二元选择**——问题定范围、实体做骨架，是同一方法论的两个层；
2. **操作型本体的切入 = decision-back（KPI/决策反推），组织 = entity-forward（全局骨架注册）**；
3. **BI/ChatBI 场景的本体增量价值不在「再画一遍 ER 图」，而在把口径固化成可执行规则 + 把关系路径显式化 + 让 LLM 知道边界**（I4 口径错配 = 反面实证）；
4. 数仓与本体分工：数仓管算得对算得快（物理），本体管问得准答得对（语义）；聚合下推数仓，语义层不做计算；
5. 语义层 = 查询路由器 + 口径守门员 + **物化循环管理器**（问题驱动的数仓演进需求回路）。
