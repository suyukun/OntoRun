# 白皮书素材：口径四要素与三陷阱（2026-09-10 全天实证）

> 来源：注册场景 T1a/T2 全天实战，三个陷阱全部当日真实踩到并解决，零生产成本（全在 mock 镜像库上暴露）。这是"方法论从闭环长出来"的当日沉淀。

## 核心论点：口径 = 粒度 × 字段来源 × 过滤条件 × 快照策略

"数字对不上"很少是算错，几乎总是四要素之一没说清。四个要素都必须显式建模进语义原语的绑定声明，靠人记忆/口头约定必然踩坑。

## 三陷阱实录

### 陷阱一：粒度（同数据不同粒度不可比）
现象：明细按二级渠道名分组得"优享+线上 232"，ADS 标准答案按三级渠道分组（同名拆 91+79+…）——直接比对全错。
解法：对账先统一粒度（三级聚合到二级后才相等，8 渠道全 PASS）。
→ 粒度是口径的组成部分，语义层的维度定义必须带层级。

### 陷阱二：字段来源（同名不同源不可混）
现象：明细自带渠道名"幽灵渠道"1 条，ADS 里没有这个组——数仓 ETL 用"明细渠道码 JOIN 维表"分组，落 null 组；用明细自带名字段则另立一组。
解法：维度绑定声明字段来源=维表 JOIN 列，禁止用明细自带字段（编译器硬编码此规则）。
→ 字段来源是口径的组成部分，两个"看起来一样"的字段是两个字段。

### 陷阱三：快照策略（日分区维表不选分区=扇出）
现象：渠道维是 62 天×15 渠道=930 行日快照，JOIN 不选分区 → 1760 行明细扇出成 108,937 行，数字全错且不报错。
解法：注册表绑定 snapshot_policy=latest_partition，编译器自动生成 `WHERE ds=(SELECT max(ds)…)`。
→ 快照策略是口径的组成部分，慢维度的"取哪天"必须显式。

## 当日配套实证（组合能力首验）

- **非菜单第一验通过**：channel_l1 × week 组合（从未做卡、无 ADS 对照）以同源参照 SQL + Σ分组=总数不变量验证通过——"卡随度量×维度增长、不随问题增长"拿到第一个数据点（11 道题 4-5 张卡，自检器=新问题命中率÷新新增卡数）。
- **对账的本质**：不是"数字对上"，是**同一口径定义的两次独立实现必须收敛**（编译器生成 SQL vs 数仓 ETL 原样重放，双向 EXCEPT=0）。
- **mock 的方法论价值**：三陷阱全在仿真数据上提前暴露；真实 ETL SQL 可在 DuckDB 逐字重放=逻辑对账不依赖真实数据（数字对账才依赖）。
