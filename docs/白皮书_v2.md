# OntoRun 方法论白皮书 v2 —— 本体语义层落地方法论（OSLM）

> 版本：v2 骨架 ｜ 日期：2026-08-22 ｜ 编制：Rose（接替产品角色，额度受限期）｜ 状态：骨架（六阶段 + 真实运行支撑，血肉随 P5 收口补充）
> 与 v0.1 的关系：v0.1（S1 闭环经验）为底；v2 升格为**可复述、可迁移的落地方法论**（议题 8 形态），六阶段框架 = P0 定稿的 **OSLM + 语义落地六步法（OSL-6）**。
> 核心主张（不变）：**大模型要操作企业，必须先有现实世界的语义层当接口**——本体是运行期语义层，落地方法论 = 数据 → 本体 → Agent 的映射与治理闭环 + 中小企业裁剪。

## 0. 一页读懂
- **做什么**：把「大模型 + 真实业务系统」之间的语义接口（本体）从设计、到落地、到治理，讲成一套可复述的六阶段方法。
- **凭什么是真的**：每条方法都有 OntoRun S1+S2 的真实运行支撑（阶段/commit/测试/实验报告引用，不空写）。
- **给谁用**：几千万级中小企业数智化（Palantir 百亿级项目的裁剪版）。

## 1. 六阶段框架（OSL-6：定界 → 建模 → 映射 → 成体 → 赋能 → 运营）
> 六步名：定界（准备）→ 建模（业务语义建模）→ 映射（数据映射治理）→ 成体（Ontology 构建）→ 赋能（应用赋能）→ 运营（运营迭代）。
> 每步 = 输入 / 做什么 / 输出 / 验收判据 / **在本项目的真实运行证据**。

### 1.1 定界（准备）
- 输入：业务范围 + 数据现状；做什么：划竖井系统边界、定首个端到端流程、定量级目标。
- 输出：企业数据地图（N 系统 N 库）+ 首个问题域（如 DQ-01 一物多码）。
- 验收判据：一个可机验的「穿通问题」+ 数据量级口径。
- **真实证据**：P1a 垂直切片（docs/P1a-*：3 系统×1 表 + 一物多码 DQ-01）；P1b 量级（18 表 100 万行，量级门禁 5 查询 P95 全达标，S2-P1b 完成记录）。

### 1.2 建模（业务语义建模）
- 输入：业务文档/表结构；做什么：把业务概念（物料/订单/库存）建模为对象/链接/动作（领域优先，不是表优先）。
- 输出：本体对象/链接/动作定义（Pydantic + 显式注册表）。
- 验收判据：schema 一处分发四处消费；self_check 0 error。
- **真实证据**：S1 8 对象/8 链接/6 动作（src/ontology/）；P2 指标模型（5 组 26 指标，des_metrics.yaml，M1-M9 校验）；P4 权限模型（对象/属性级策略）。

### 1.3 映射（数据映射治理）
- 输入：源系统表 + 本体定义；做什么：源表字段 → 本体 target 的映射候选 + 分级置信度 + 人工审核 + 入注册表。
- 输出：映射候选/置信度/审核轨迹（approved 才入注册表）。
- 验收判据：ground truth recall@5 ≥ 80%；映射变更影响分析；审核痕迹 append-only。
- **真实证据**：P1.5 打标骨架 + P3 管道（review CLI/publish/calibrate/impact）；62 条 GT（recall@5=1.0，P3 GT 门禁）；red-team P2-4 新对象闭环修复。

### 1.4 成体（Ontology 构建）
- 输入：映射审核后的对象/链接；做什么：注册 + 自检 + 跨系统物化（join key 对齐竖井）。
- 输出：可查询的本体运行时（对象/链接/动作 + 物化）。
- 验收判据：跨系统无孤儿；物化 reconcile diff=0；本体自检 0 error。
- **真实证据**：P1a 本体映射（Material 3 编码→1 概念）；P2 DuckDB 物化（26 指标 reconcile 全绿）；P4 4 对象注册（13 对象 self_check 0 error）。

### 1.5 赋能（应用赋能）
- 输入：本体运行时 + Agent/分析工具；做什么：ChatBI 读侧（对象→指标→物化）+ 动作写回（语义接口）。
- 输出：受限结构化查询契约 + 动作执行 + 读侧权限。
- 验收判据：head-to-head 实证查询形态；越权 0；拒答率 > 0。
- **真实证据**：P2 head-to-head v3（B=受限结构化查询 60% 首超 NL2SQL，可表达集 ~85-90%，混合形态定稿）；P4 越权 0 门禁；读侧 decide(read)+visible_attributes。

### 1.6 运营（运营迭代）
- 输入：运行中的本体 + 用户/审计反馈；做什么：审计 WORM + 权限治理 + 映射再校准 + 问题注入迭代。
- 输出：可信运行面（审计不可篡改、会话不丢、映射阈值随 GT 校准）。
- 验收判据：审计不可篡改（WORM+哈希链）；会话重启不丢；映射阈值不拍脑袋。
- **真实证据**：P1.5 审计 WORM 链 + P4 审计收口（演示库回填 verify ok）；P4 会话持久化；P3 阈值校准（GT 驱动，C2）。

## 2. 十条铁律（从项目纪律提炼）
1. 落地先行，方法论从系统里长出来（禁止先写方法论再落地）。
2. 竖井打通发生在语义层，不在数据层（N 系统 N 库，join 靠本体）。
3. 写回必须真实可验证（源记录真变 + 规则校验 + 全程审计）。
4. LLM 是受约束的执行者，不是自由操作员（受限查询/动作白名单/参数校验）。
5. 规则必须能机器验证（软规则配套 governance 测试）。
6. 单一事实来源（git + 配置；*.db 可再生成）。
7. 安全 fail-closed（权限缺省拒绝、审计不可篡改、输入参数化）。
8. 独立对抗复核（交付物定稿前独立 red-team，不接受自评）。
9. 不造轮子（成熟件优先，自研仅限研究本身：本体运行时 + 本体↔分析引擎映射）。
10. 量级诚实（不宣称未验证的量级；门禁以实测为准）。

## 3. 反模式（从真实落地提取，Top 15 候选）
> 每条 = 反模式 / 症状 / 在本项目的真实案例 / 对策。
1. **数字盆景**：方法论 UI 只展示静态图文，不绑定真实运行 → 指针版链到 git commit/真实输出（D2 决策）。
2. **权限死代码**：权限做了但无人接线、缺省放行 → red-team P1-1 抓到的 fail-open；对策=唯一入口强制 fail-closed。
3. **link 旁路**：只检 source 权限、link 目标直读 → red-team P1-2；对策=目标对象也过 decide。
4. **审计竞态**：哈希链序与追加序不一致 → red-team P2-1 同毫秒断链；对策=链序单调。
5. **静默忽略**：查询参数不实现也不拒答 → red-team P2-2 time_range 静默忽略；对策=fail-closed 拒答。
6. **自圆其说的测试**：测试把错误行为固化为预期 → red-team 抓「无 ctx 照常执行」；对策=测试先质疑预期。
7. **造轮子**：自研可被成熟件覆盖的东西 → 分析引擎/传输层用现成（DuckDB/HTTP），自研仅研究本身。
8. **拍脑袋阈值**：置信度/靶值凭感觉 → 85% 靶值经 head-to-head 实证重新对齐；阈值靠 GT 校准。
9. **过早掐断深思考**：用效率砍深度 → 子代理管理教训；对策=后台无时间墙、不凭「慢」打断。
10. **新对象死锁**：前置校验与发布语义互相矛盾 → red-team P2-4 C4 死锁；对策=语义单点化。
11. **GT 假乐观**：校准指标只统计己方键 → red-team P2-5 auto_precision；对策=分母=全部候选。
12. **事务不原子**：多副作用分笔提交 → red-team P2-6/7；对策=单事务。
13. **量级夸大**：宣称未验证的量级 → C1 拍板 100 万行级 + 量级门禁实测。
14. **注入面留白**：配置/表达式无白名单 → red-team P2-8 M8；对策=标识符白名单。
15. **模型判据漂移**：同模型自评当验收 → 四模型对抗复核 + 独立 red-team。

## 4. 十个开放张力点
1. 平台内置 vs 拼装（轻量平台 vs 成熟件拼装）。
2. 写回 vs 只读（S2 搁置写回，方法论=北极星、系统=当前能力）。
3. 受限查询 vs LLM 写 SQL（head-to-head 结论=混合，契约主路径 + 守卫 SQL 兜底冷问题）。
4. 语义层标注 vs 数据层强制（C3：S2 对象级下沉留发布期）。
5. 描述型本体（RDF/OWL）vs 操作型本体（Pydantic 注册表）——方法论论点，发布期如需再引 RDF。
6. 预聚合 vs 动态派生（Palantir 范式：<~1 万对象动态，指标预聚合）。
7. 自动映射 vs 全人工审（S2 轻人工审，1-2 月数据后再定阈值）。
8. 单企业 vs 多企业（模板复用已验：nh_heavy；多租户隔离留发布期）。
9. 单用户 vs 多用户（S2 显式单用户前提，权限已骨架化）。
10. 种子用户 vs 真实场景（DES 生成企业当种子用户，真实场景待接）。

## 5. 中小企业裁剪（vs Palantir 百亿级）
- 本体构建：Pydantic + 显式注册表（非 OSv2/Funnel 级基础设施）。
- 分析引擎：DuckDB（穷人版分析内存库），非 SAP HANA/云数仓。
- 治理：轻人工审（~80% 自动 + ~20% 人审），非全职数据治理团队。
- 部署：单机 SQLite + Docker Compose，非云原生集群。
- 成本：个位数元级 LLM 调用（火山套餐），非企业级 AI 预算。
