## 0. 一页读懂（给 30 秒读者的摘要）

**问题**：大模型能力已经很强，但它与真实信息系统之间没有标准接口——模型读的是文档/API 碎片，写的是数据库或什么都不写；企业不敢让模型碰业务，因为"没有一道闸"。

**我们的答案**：把"现实世界的语义层"（对象、关系、业务规则、治理边界）做成大模型与系统之间的**语义接口**，模型经语义接口**执行受治理的动作并真实写回源系统**。这不是新发明——Palantir Foundry Ontology 是这个押注的国外标杆；本项目的贡献是把这套机制**用最小可复现的闭环落地并公开证据链**，回答"本体论在中国企业怎么落地、每个机制长什么样、怎么验收"。

**一个判断**：设计期模型（ER 图/LDM/指标层）与运行期本体（Palantir Ontology）的差别不在建模符号——符号高度同构——而在**运行时与写回回路**。谁有"动作门控的写回回路 + 审计 + 规则前置校验"，谁才是"运行语义层"；否则只是"只读语义层"。

**三个验收问题（三问测试）**，本项目已用真实数据通过：
1. 能从语义接口取消订单吗？——能（`POST /actions/cancel_order`）
2. 源系统记录真的变了吗？——真变了（直查源库 status=cancelled，审计含写回 SQL 与影响行数）
3. 已发货的订单会被拦吗？——会被拦（`SHIPPED_ORDER_CANNOT_BE_CANCELLED`，源库零变更）

## 1. 问题：大模型与真实信息系统之间没有标准接口

### 1.1 现象

大模型（尤其是 tool calling / agent 形态）已经能理解自然语言、规划步骤、调用工具。但把它接进一个真实企业系统时，每一家都要从头解决同一组问题：

- **模型不知道"世界长什么样"**：客户、订单、库存、发货之间的语义关系没有标准表达；给模型一张裸表，它不知道"订单"和"客户"谁是主体、状态机怎么走、哪些字段不能改。
- **模型不知道"哪些事能做、哪些事不能做"**：业务规则（已发货不能取消、退款不能超实付）散落在代码/文档/人的脑子里，模型无法在调用前理解、调用后被约束。
- **模型做了事，系统没有可验证的变更**：很多"AI 接入"只写内存/只改前端状态/只调一个假接口，业务方无法证明"它真的改变了业务"。
- **没有审计、没有治理**：谁、何时、基于什么输入、做了什么变更、结果如何——没有一条完整链路可追溯。

这不是"加一个 API 网关"能解决的：网关管传输，不管语义；也不是"给模型发一堆工具"能解决的：工具越多，模型越容易选错，且无法表达"哪些组合是业务上合法的"。

### 1.2 三层接口框架（本项目的研究坐标系）

我们把"大模型 ↔ 真实信息系统"之间的接口拆成三层（方向与战略_v0.2 §2）：

| 层 | 回答"什么" | 成熟方案 | 本项目态度 |
|---|---|---|---|
| **语义接口**（★核心研究面） | 世界长什么样：对象、关系、业务规则、治理边界 | 本体论（Palantir Ontology 为标杆） | **自研最小闭环，作为研究主体** |
| 传输接口 | 怎么调用：工具/数据如何暴露给模型 | MCP 类协议 | 采用现成，不造轮子 |
| 操作接口 | 做了事真的改变系统：动作 + 规则校验 + 审计 + 写回 | Action 写回回路（各平台有实现） | 采用现成机制形态，自研最小实现 |

**研究对象锚定**：本文只谈语义接口层。传输层（怎么把工具发给模型）和操作层（底层怎么执行 SQL）都有成熟方案，重复实现它们没有方法论价值；价值在于**"模型看到的世界模型" + "世界允许模型做什么"**这一层——这正是本体论（ontology）的现代工程形态。

### 1.3 脊柱之问（为什么是现在、为什么是语义层）

> 数据仓库建模 30 年（Kimball 维度 / Inmon 范式），当消费者从"人看报表"变成"大模型读+操作"，建模范式必须变：从"为 BI 而建（只读）"变成"为 Agent 而建（可理解、可操作、可治理写回）"。

20 年数仓建模的经验资产在这里不是负担而是前提：我们懂"模型怎么表达现实"，现在只是把它的**服务对象**从报表换成了 Agent，把它的**能力**从只读升级为可写回。语义接口 = "本体化 + 动作化 + 治理 + 标准协议" 的接口机制。

## 2. 为什么"设计期模型 → 运行期本体"是落地关键

### 2.1 先说反方：建模符号高度同构

Palantir 的 Object type / Property / Link / Action，和传统 ER 的实体/属性/关系/（存储过程），在**建模符号层面高度同构**——第三方批判（vonng，"ontology-bullshit"）说得对：*"The same structure in different vocabularies. Highly overlapping and close to isomorphic in practical modeling terms."* 如果方法论只讲建模，会被一句"这不就是 CREATE TABLE"击穿。

### 2.2 同构的是 schema，不同构的是运行时与写回回路

我们接受的裁决（research/palantir-ontology.md §2.4 本报告裁决）：

- **静态 schema 确实同构**——ER 图也能画客户/订单/库存。
- **不同构的是三件事**：
  1. **运行时**：模型是否被索引、可查询、可遍历链接、可被应用与 Agent 消费（Palantir 有 OMS/OSS/Object Database 一套后端）；
  2. **写回回路**：模型/用户提交动作 → 规则校验 → **真实写回源系统** → 审计留痕；
  3. **治理一体化**：规则放哪、谁有权限、怎么演进。

所以关键论断：**"设计期模型"是蓝图（交付即过时的风险），"运行期本体"是可执行、可写回、可审计、可演进的系统。** 落地价值在后者，不在前者。

### 2.3 写回回路 = 分水岭（本项目最核心的方法论点）

> **A semantic layer lets you read your business. An operational ontology lets you run it.**
> （语义层让你"读"业务；运行期本体让你"运行"业务。）

判断一个"语义层/指标层/本体"是不是真的运行期，用**三问测试**（源自 operational-ontology 参考实现，本项目已实现并验证）：

| 问题 | 问的是什么 | "只读语义层"的回答 | "平行数据库"的回答 | "裸写 API"的回答 | **本项目（运行语义层）的回答** |
|---|---|---|---|---|---|
| 1. 能从语义层取消订单吗？ | 语义层是否暴露业务**动作**（不是裸 update） | 不能 | 能 | 能 | ✅ 能：`cancel_order` 是注册的业务动作（src/ontology/actions.py），UI 与 LLM 走同一 `POST /actions/cancel_order` |
| 2. 源系统记录真的变了吗？ | 写回是否命中**源系统权威库**（不是只改本体索引/内存） | — | 变了但源系统没变 | 变了 | ✅ 真变：动作引擎对源系统库执行真实 UPDATE，E2E 直查源库断言 `status=cancelled` |
| 3. 已发货的会被拦吗？ | 业务规则是否在**动作前置校验**里权威生效 | — | 不会拦 | 会拦但只是 if 分支 | ✅ 被拦：前置规则返回 `SHIPPED_ORDER_CANNOT_BE_CANCELLED`，源库零变更 |

三问挂掉任何一问，MVP 都不达标。它们也是**机器可验证的 DoD**：每个问题都有对应 E2E 测试断言（见 §2.4 证据链）。

## 3. 落地五步法骨架（基于本项目实际）

> 本方法从 OntoRun MVP 落地过程提炼，顺序即依赖顺序。每步给"本项目做法"与"证据"。

### 第 1 步：定义对象 / 链接 / 动作（领域优先，不是表优先）

- **对象** = 领域概念（Customer/Order/Shipment…），不是表或 API 页；属性按"状态归属"标注（见第 3 步）。
- **链接** = 领域关系，双向命名自解释（order.items / item.order），不建"仅因共享外键而存在"的链接。
- **动作** = 业务操作聚合（cancel_order 是"取消整单"，不是"改 status 字段"）——避免 Action Sprawl。

**本项目做法**：Pydantic 模型 + 显式注册表表达本体（D-T2 已拍板，MVP 不引入 RDFlib——价值在运行时机制，不在序列化语法）；8 对象/8 链接/6 动作见 src/ontology/。
**证据**：tests/test_d2_registry.py（35 用例）；技术方案 §2。

### 第 2 步：注册自检（schema 一处分发、四处消费）

- 注册表启动时执行 `self_check`：主键唯一性、链接双向命名一致、动作参数完整、状态归属标注完整。
- schema 是**单一元数据源**：同时驱动 ① 运行时索引、② API 的 /meta/schema、③ 前端动态 UI、④ Agent 工具生成（技术方案 §3.2）。

**本项目做法**：src/ontology/registry.py + src/ontology/ 下每对象/链接/动作一个定义文件。
**证据**：self_check 实现（registry.py）；前端 `useMeta()` 拉 /meta/schema 驱动全部页面（web/src/hooks/useMeta.ts）——**新增对象类型/动作，前端零代码改动**（验收 F1，web/src/components/*.test.tsx 23 用例）。

### 第 3 步：运行时写回（动作引擎——校验→变更→写回→审计）

**核心管道**（技术方案 §3.3）：参数校验(Pydantic) → 源库事务 → 事务内重读快照 → 前置规则(业务规则权威在此) → 纯函数计算变更 → 写回源库 → 更新索引 → 审计落库。

- **拒绝路径早退**：任何前置不满足 → rejected + 业务错误码 + **源库零变更**（三问 3 的机制保证）。
- **状态归属三分类**（写回目标的显式声明）：
  - `source-backed`：源系统权威（订单状态、库存数量）——动作必须写回源库；
  - `ontology-owned`：源系统没有的列（cancel_reason、review_note）——本体自有存储即系统记录；
  - `derived`：计算态（available_qty）——永不写。
  - 每个动作的效果必须标注改了哪几类状态；写回只针对 source-backed——**杜绝"平行数据库幻觉"**（三问 2 的机制基础）。

**本项目做法**：src/runtime/action_engine.py + actions_impl.py；双库（源库=权威，本体库=索引+自有态+审计），一致性取补偿式（D-T4 已拍板）。
**证据**：tests/test_b2_action_engine.py 37 用例（含拒绝路径零写库断言）；tests/test_b1_index_query.py 20 用例。

### 第 4 步：语义接口暴露（统一写入口，无泛化写路径）

- REST 薄壳，无业务逻辑（业务规则只能在动作定义里，不允许出现"UI 校验 ≠ 动作校验"双轨）。
- **一切写操作（人类 UI 或 LLM）必须且只能经过 `POST /actions/{name}`**——结构性保证"没有泛化 update 路径"。
- 统一响应信封 `{request_id, outcome, data|error}`；错误码全集（17 个，技术方案 §4.3）。

**本项目做法**：src/api/routes.py（FastAPI）；OpenAPI 自动生成。
**证据**：tests/test_b3_api.py 27 用例；tests/test_agent_api.py 9 用例（Agent 与 UI 同一写入口）。

### 第 5 步：Agent 接入与治理（LLM 是"受约束的执行者"，不是"自由操作员"）

- **工具从 schema 自动生成**：每动作 → 一个 function-calling 工具（参数 = 动作的 JSON Schema）；只读工具只给 1 个 search_objects（控制 tool 数量与 token）。
- **防注入三层防线**：① 结构层——无泛化写工具；② 服务端——动作引擎前置校验是权威裁判；③ 人机层——高风险动作双签（LLM 提议 → 用户确认 → 才提交）。
- **错误码回填学习**：动作结果（outcome + error_code + message）回填为 tool 结果再交给 LLM 生成回复——LLM 从错误码学习规则，下一次提出正确替代方案（"本体规则约束 Agent"的可演示闭环）。

**本项目做法**：src/agent/{provider,tools_generator,agent}.py；provider 热插拔（MVP=DeepSeek，key 仅环境变量）。
**证据**：tests/test_agent_tools_generator.py 9 用例（golden 快照：6 动作 + 1 只读工具）；tests/test_agent_e2e.py 15 用例（全链路 + 双签 + 防注入 + 轮次上限）。

## 5. 与 Palantir 机制的对照（防"这不就是 CREATE TABLE"质疑）

### 5.1 对照表（OntoRun MVP 组件 → Palantir 机制）

| OntoRun MVP 组件（本仓库可运行） | 对标 Palantir 机制 | 调研出处 | 差异/简化说明 |
|---|---|---|---|
| registry（对象/链接/动作注册 + self_check） | OMS + Ontology Manager + 主键确定性 | palantir §1.3 / §3.1 | MVP 显式注册表替代元数据服务；主键确定性要求已落实（PK 不可变） |

### 5.2 诚实结论（不给"复刻 Palantir"留话柄）

- **这些机制每一个都不是新发明**（索引、写回、审计、权限都是成熟技术）；Palantir 的价值在于**把它们与"模型"一体化**，并把本体做成平台级运行时。
- 本项目不是"我们复刻了 Palantir"，而是：**用最小可复现的闭环把每个机制做出来、测出来、公开证据链**——每个组件都小到能讲清、能测试、能被同行挑刺（技术方案附录 A）。
- **反方检验**：被问"这不就是表 + 存储过程？"时，回答 = §2.3 三问测试——你问的"表 + 存储过程"能不能回答"源记录真变了吗、已发货被拦吗、有审计吗"？能，那你已经做了一个（简版）运行期本体；不能，那它就是设计期蓝图。**分水岭不在名字，在机制。**

### 7.0 问题：本体不是「设计」出来的，是「长」出来的

传统 LDM 的最大失败模式是「模型交付即过时」（§6.1）——设计期交付一张 ER 图，业务一变图就废。本项目的替代答案是：**把构建期做成一条可执行、可审计、可评测的流水线**——表/文档/接口进，对象/链接/动作（draft）出，人工审批后进注册表，运行时消费（§3 五步法第 1-2 步的自动化补充）。

构建期流水线（builder 子系统）五件套：**三路径管道（E1）→ Curated 评审 → 自动映射（E2）→ LLM 提取 + 七道校验（E3）→ 逻辑规则推导（P4）**；产物 apply 进注册表，与运行时闭环（§7.4）。本章三块：① LLM 五流派（LLM 在本体构建中的五个作用位）；② 自动映射四技法（E2）；③ 三路径管道（E1）。每条论断给「本项目证据」（文件/测试/可复现命令）。

### 7.1 LLM 五流派：LLM 在本体构建中的五个作用位

|---|---|---|---|---|---|

**方法论判断（每派一句）**：

1. **五流派不是五选一，是同一条构建流水线的五个环节**，顺序即依赖：检索给上下文 → 模式抽底 → 映射生成草稿 → 校验对抗兜底 → 规则推导建议演进。
2. **LLM 的正确位置**：越靠近「写进注册表的决定」，越要把决定权交还给确定性规则 + 人工审批。本项目 LLM 用在「抽取」最多（②④），「生成映射」仅作草稿（③），「匹配/推导」走规则（①⑤）——与「LLM 全程端到端自动建本体」的路线相反，这是可评测、可追责的保守路线。
3. **校验对抗是「LLM 参与本体构建」的前提**：没有七道校验器，E3 提取就是把幻觉直接写进本体；黄金集埋雷 = 校验器自身的 TDD（校验器也要被测试）。

### 7.2 自动映射四技法（E2）：从「脏表」到「对象/链接」

> 四技法 = 别名匹配 / 宽表拆分 / 外键检测 / 值格式化；编排骨架 = 字段推断 + 映射审批（auto_map）。蓝图 v0.3 §7 六条规格归入此结构。

**技法 1 · 别名匹配（备用键匹配）**——文档自然语言提到的公司名 → 主表实体。

- 机制（src/builder/mapping/alias_matcher.py）：双轨候选抽取（全称触发后缀 + 2-4 字中文 n-gram）；五档匹配（exact_full_name 1.0 / abbreviation_stripped 0.95 / abbreviation_with_industry 0.92 / short_alias 0.85 / ambiguous_short_alias_resolved 0.75）；同段上文最近全称消歧；地点后缀（科技园/物流园）归 no_match；多候选冲突不决断。
- **P4 实测（tech-debt TD-4 记录，本次复现一致）**：partner_aliases.md × suppliers_dirty.csv → **172 提及 / 24 命中 / 148 no-match = 86.0%**；命中覆盖 10 个供应商（SUP-001/002/003/005/006/009/011/012/013/016）；匹配类型分布：exact_full_name 8 / abbreviation_with_industry 8 / abbreviation_stripped 5 / short_alias 3。
- **诚实拆解 148 no-match**：147 条归类「不在供应商主表」+ 1 条地点名（长江冷链科技园）。抽样显示主体是文档自然语言的非公司片段（「区域物流」「起草」「李军」等 2-4 字 n-gram 被抽为候选别名）；真实「提及但未建档」的外部公司仅 2 家（深圳前海新汇通贸易有限公司、上海元初冷链科技股份有限公司，文档自标「待补录」）。TD-4 结论：**匹配算法本身非瓶颈，瓶颈在候选抽取精度 + 主表覆盖**。
- **评估口径必须声明**：P3 fixture 按「文档语义提及」计 22 命中 / 6 no_match / 2 歧义（金辉、长江冷链按文档消歧声明解析）；P4 实测按「算法抽取的全部候选提及」计 172——同一输入两种口径数字都「对」，不声明口径就是耍流氓。
- 工程决策：no_match 全部汇入**待补录队列**，绝不自动建档（P3 断言 6 个 no_match 全部正确归入待补录）；别名匹配定位为「人审提示」而非「自动建档」。
- 复现：PYTHONPATH=. python 直接调 match_aliases（读 partner_aliases.md + suppliers_dirty.csv 为 master），输出 summary_counts = {total_alias_mentions: 172, matched_to_existing_supplier: 24, no_match: 148, matched_supplier_ids_count: 10}。

**技法 2 · 宽表拆分（E7）**——一实体一表；大宽表按列名前缀语义拆多表。

- 机制（src/builder/mapping/wide_split.py）：列名分类（头表/明细/冗余供应商列前缀语义）→ 头表按 PK 去重、明细逐行下推、冗余列按 FK 去重并合并首行非空 → 自动生成 FK 链。
- 实测：wide_table_purchases.csv（25 行、22 列混 3 实体）→ **purchase_orders 14 行**（PK purchase_order_id）/ **supplier_info 14 行**（PK supplier_id，按 supplier_id 去重）/ **purchase_order_lines 25 行**（PK (purchase_order_id, po_line_no)）；2 条 FK 链：purchase_orders.supplier_id→supplier_info.supplier_id（**N:1**）、purchase_orders.purchase_order_id→purchase_order_lines（**1:N**）。
- 设计：规则为主（零 LLM 依赖，未来可升级 LLM 辅助 + 人工复核，蓝图 §7-5）；增量更新三层（同步/处理/索引）暂降 TODO（补丁 B3）。
- 证据：tests/test_builder_p3.py::TestWideSplit；expected/wide_split.json。

**技法 3 · 外键检测**——跨表同名列对 → 值匹配 → 基数推断，自动建链接。

- 机制（src/builder/mapping/fk_detection.py）：候选列对（列名同名优先 exact）→ 三类匹配（direct / format_normalized / unmatched）→ 基数推断（source 行对 target 的引用分布 → N:1 / 1:1 / 1:N）。
- 实测：products_ref_suppliers.csv（34 行）× suppliers_dirty.csv（去重后 20 行）→ 链接 lnk_products_ref_suppliers_suppliers_dirty_supplier_id，**cardinality=N:1**；34 行匹配分布 = **26 direct + 5 format_normalized + 3 unmatched**；unmatched 为 typo（SUP-0051 / SUP-0014 / SUP-0018），检测器给 closest 提示供人工核查——fixture 注明 SUP-0051 实为 SUP-005 的 typo，而 closest 启发可能给出别的候选（本次复现给出 SUP-001）：**提示仅辅助，不自动写库**。
- 证据：tests/test_builder_p3.py::TestFKDetection（断言 unmatched=3 / format_normalized=5）；expected/fk_detection.json。

**技法 4 · 值格式化**——不同编码风格的主键/外键值归一，让跨表匹配跨越风格差异。

- 机制（src/builder/mapping/value_format.py）：抽「大写前缀 + 数字段」，去分隔符、**保留位数**（SUP-001→SUP001、SUP-0011→SUP0011）；归一后相等 = 同一实体。
- 实测：5 个 format_normalized 匹配来自值格式容错（SUP-003↔SUP003、SUP-006↔SUP006、SUP-008↔SUP008、SUP-016↔SUP016 等）；**位数敏感**（SUP-0011 vs SUP-011 不归一，防撞名）；**typo 不自动纠正**（SUP-0051≠SUP-005 → 走 unmatched 报告，绝不静默改值）。
- 证据：tests/test_builder_p3.py::TestValueFormat。

**编排骨架：字段推断 + 映射审批（auto_map）**：

- 字段推断（src/builder/mapping/naming.py + pipeline/schema_infer.py）：列名 snake_case→PascalCase 属性（supplier_id→SupplierId）；类型映射（string/integer/float→number/datetime→ISO 字符串）；**is_technical 列**（etl_loaded_at/source_system）进 property_schema.hidden_columns、不进 properties（技术列隐藏）；PK 推断（非空率=1.0 且 distinct==row_count）。
- 审批闭环（A1）：POST /mappings/auto（source + target + target_pk）→ MappingRow（status=draft，含 field_mapping / fk_mappings / cardinalities / alias_matches）→ POST /mappings/{entity}/apply 生成 draft object_types + link_types → review → publish → **/meta/schema 可见**（P3 端到端断言 test_mappings_auto_then_apply_then_publish）；同名冲突 apply 返回 400 BUILDER_NAME_CONFLICT；非法 X-Actor 返回 400 INVALID_ACTOR。

### 7.3 三路径管道（E1）：按数据形态递进的三档自动化

管道 = DAG（节点 kind：connector / storage / transform / output；每节点状态 pending→running→succeeded|failed|skipped；拓扑排序执行 + **失败传播 skip**（下游 SKIPPED）+ **独立分支继续**；环/自环/id 重复/next 未知全部校验）。证据：src/builder/pipeline/dag.py + tests/test_builder_p2.py::TestDAGEngine（11 用例）。

**A 路径 · 结构化直入（CSV）**——schema 推断 + 清洗 → 干净表 → Curated（带质量分）。

- 实测（suppliers_dirty.csv）：22 行 → 去重 **20 行**（2 条重复，key=SUP-001，data row 21/22 重复 row 1）；10 列推断：category/region→enum、rating→float（含「4.5分」单位后缀）、contact_email→string、etl_loaded_at→datetime；技术列 2 个（etl_loaded_at / source_system）；contact_phone 非空率 **0.8**（16/20）；清洗：rating「4.5分」→4.5、「N/A」→None。
- 端到端（管道 API）：CSV 上传 → connector → schema_infer → output → curated（row_count=20、quality.duplicate_rate>0、source=schema_infer）→ review×2（draft→reviewed→approved；第 3 次 review 报 BUILDER_INVALID_STATUS_TRANSITION）。证据：tests/test_builder_p2.py::TestPipelineE2ESmoke。
- 复现：PYTHONPATH=. python 直接调 infer_from_csv_path('data/builder_samples/suppliers_dirty.csv', pk_column='supplier_id') → raw=22 / dedup=20 / dups=2 / technical=['etl_loaded_at','source_system']。

**B 路径 · 半结构化清洗（JSON/XML）**——JSON 拍平（Explode 嵌套数组→独立行）+ XML 解析为行集（属性→列、子元素→子表）。

- 实测（orders_nested.json，16 订单）：orders **16** / items **29** / shipping **12** / notes **3** / replies **2**（双层嵌套也 explode）；corner cases：ORD-20250812-0007（cancelled，items=[]）不产明细行、4 个无 shipping 的订单不产 shipping 行、子表 FK 全部指向主表存在订单。
- 实测（catalog.xml，12 产品）：products **12** / product_specs **33** / product_certifications **12** / catalog_metadata **1**；X-9003/X-9004/X-9006 空 <certifications/> 不产 cert 行。
- 证据：tests/test_builder_p2.py::TestFlattenJSON / TestParseXML（对照 expected/flatten.json、expected/parse.json）。

**C 路径 · 非结构化提取（MD）**——MD 结构化（标题/表格/段落/列表→行，**每行带 source_ref{section,line}**）→ LLM 提取（E3，七道校验后入库）。

- 实测（supplier_memo.md，661 中文字 / 1261 总字符）：md_to_struct → **7 sections / 16 rows**（paragraph 3 + table_row 3 + list_item 10），报价对照表 3 行完整解析（物流商/报价/装车响应时长/温控达标率/联系人）；E3 黄金集 **21 实体**（19 干净 + 2 故意问题）/ **9 关系** / **5 逻辑规则** / **4 动作**。
- 诚实降级：PDF/DOCX → degraded=unsupported_kind_no_markitdown（MVP 不装 markitdown 新依赖，明确降级而非假装支持）；未知扩展同样 degraded。
- 证据：tests/test_builder_p2.py::TestMDToStruct；tests/test_builder_p3.py::TestExtractionEndToEnd（MockProvider 冻结响应，TD-3）。

**方法论要点**：

1. 三路径不是「三种工具」，是**按数据形态递进的三档自动化**：结构化=全自动、半结构化=自动 explode + 人工审子表语义、非结构化=规则结构化打底 + LLM 语义提取 + 七道校验兜底——自动化程度与数据熵成反比。
2. **source_ref 是「可追溯」的底线**：MD 每一行都能回到原文 section/line，LLM 提取产物可溯源（黄金集断言对行内容精确可控）。
3. **Curated 质量分 + 两段评审**（draft→reviewed→approved）把「人审闸」前置到构建期——管道跑得快不等于可以自动入库。
4. **DAG 失败传播**让管道「部分成功」可表达——真实企业数据管道必然部分失败，全有或全无是不现实的。

### 7.4 构建期与运行时的衔接（闭环 + 待定）

- **闭环（§12 验收 2 的「一条命令端到端」）**：CSV → 管道 → Curated → 自动映射 → 本体（apply→publish）→ LLM 动作 → 写回源系统 → 审计。P4 已打通「构建产物进运行时」：6 内置动作登记为 action_types（元数据来自引擎声明 = 单一事实来源）、submission_criteria 引用已发布逻辑规则（悬空/未发布引用拒绝执行）、E6 快照审计（applied / dry_run / rejected / failed 四态，before/after + audit_ref 对账）。证据：tests/test_builder_p4.py::TestActionTypesSync / TestSubmissionCriteriaLinkage / TestActionRunApplied 等。
- **待定/发布期（诚实标注，非结论）**：① 别名候选抽取精度改进（业务无关词过滤，TD-4 续）；② 宽表拆分 LLM 辅助增强；③ 增量索引（TD-5，100+ 类型时全量重载延迟）；④ PDF/DOCX markitdown 支持（现为诚实降级）；⑤ AI FDE 对话式构建/维护本体（§6.1 路线图）。
