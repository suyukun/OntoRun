## 0. 一页读懂（给 30 秒读者的摘要）

**问题**：大模型能力已经很强，但它与真实信息系统之间没有标准接口——模型读的是文档/API 碎片，写的是数据库或什么都不写；企业不敢让模型碰业务，因为"没有一道闸"。

**我们的答案**：把"现实世界的语义层"（对象、关系、业务规则、治理边界）做成大模型与系统之间的**语义接口**，模型经语义接口**执行受治理的动作并真实写回源系统**。这不是新发明——Palantir Foundry Ontology 是这个押注的国外标杆；本项目的贡献是把这套机制**用最小可复现的闭环落地并公开证据链**，回答"本体论在中国企业怎么落地、每个机制长什么样、怎么验收"。

**一个判断**：设计期模型（ER 图/LDM/指标层）与运行期本体（Palantir Ontology）的差别不在建模符号——符号高度同构——而在**运行时与写回回路**。谁有"动作门控的写回回路 + 审计 + 规则前置校验"，谁才是"运行语义层"；否则只是"只读语义层"。

**三个验收问题（三问测试）**，本项目已用真实数据通过：
1. 能从语义接口取消订单吗？——能（`POST /actions/cancel_order`）
2. 源系统记录真的变了吗？——真变了（直查源库 status=cancelled，审计含写回 SQL 与影响行数）
3. 已发货的订单会被拦吗？——会被拦（`SHIPPED_ORDER_CANNOT_BE_CANCELLED`，源库零变更）

## 1. 问题：大模型与真实信息系统之间没有标准接口

### 1.1 现象

大模型（尤其是 tool calling / agent 形态）已经能理解自然语言、规划步骤、调用工具。但把它接进一个真实企业系统时，每一家都要从头解决同一组问题：

- **模型不知道"世界长什么样"**：客户、订单、库存、发货之间的语义关系没有标准表达；给模型一张裸表，它不知道"订单"和"客户"谁是主体、状态机怎么走、哪些字段不能改。
- **模型不知道"哪些事能做、哪些事不能做"**：业务规则（已发货不能取消、退款不能超实付）散落在代码/文档/人的脑子里，模型无法在调用前理解、调用后被约束。
- **模型做了事，系统没有可验证的变更**：很多"AI 接入"只写内存/只改前端状态/只调一个假接口，业务方无法证明"它真的改变了业务"。
- **没有审计、没有治理**：谁、何时、基于什么输入、做了什么变更、结果如何——没有一条完整链路可追溯。

这不是"加一个 API 网关"能解决的：网关管传输，不管语义；也不是"给模型发一堆工具"能解决的：工具越多，模型越容易选错，且无法表达"哪些组合是业务上合法的"。

### 1.2 三层接口框架（本项目的研究坐标系）

我们把"大模型 ↔ 真实信息系统"之间的接口拆成三层（方向与战略_v0.2 §2）：

| 层 | 回答"什么" | 成熟方案 | 本项目态度 |
|---|---|---|---|
| **语义接口**（★核心研究面） | 世界长什么样：对象、关系、业务规则、治理边界 | 本体论（Palantir Ontology 为标杆） | **自研最小闭环，作为研究主体** |
| 传输接口 | 怎么调用：工具/数据如何暴露给模型 | MCP 类协议 | 采用现成，不造轮子 |
| 操作接口 | 做了事真的改变系统：动作 + 规则校验 + 审计 + 写回 | Action 写回回路（各平台有实现） | 采用现成机制形态，自研最小实现 |

**研究对象锚定**：本文只谈语义接口层。传输层（怎么把工具发给模型）和操作层（底层怎么执行 SQL）都有成熟方案，重复实现它们没有方法论价值；价值在于**"模型看到的世界模型" + "世界允许模型做什么"**这一层——这正是本体论（ontology）的现代工程形态。

### 1.3 脊柱之问（为什么是现在、为什么是语义层）

> 数据仓库建模 30 年（Kimball 维度 / Inmon 范式），当消费者从"人看报表"变成"大模型读+操作"，建模范式必须变：从"为 BI 而建（只读）"变成"为 Agent 而建（可理解、可操作、可治理写回）"。

20 年数仓建模的经验资产在这里不是负担而是前提：我们懂"模型怎么表达现实"，现在只是把它的**服务对象**从报表换成了 Agent，把它的**能力**从只读升级为可写回。语义接口 = "本体化 + 动作化 + 治理 + 标准协议" 的接口机制。

## 2. 为什么"设计期模型 → 运行期本体"是落地关键

### 2.1 先说反方：建模符号高度同构

Palantir 的 Object type / Property / Link / Action，和传统 ER 的实体/属性/关系/（存储过程），在**建模符号层面高度同构**——第三方批判（vonng，"ontology-bullshit"）说得对：*"The same structure in different vocabularies. Highly overlapping and close to isomorphic in practical modeling terms."* 如果方法论只讲建模，会被一句"这不就是 CREATE TABLE"击穿。

### 2.2 同构的是 schema，不同构的是运行时与写回回路

我们接受的裁决（research/palantir-ontology.md §2.4 本报告裁决）：

- **静态 schema 确实同构**——ER 图也能画客户/订单/库存。
- **不同构的是三件事**：
  1. **运行时**：模型是否被索引、可查询、可遍历链接、可被应用与 Agent 消费（Palantir 有 OMS/OSS/Object Database 一套后端）；
  2. **写回回路**：模型/用户提交动作 → 规则校验 → **真实写回源系统** → 审计留痕；
  3. **治理一体化**：规则放哪、谁有权限、怎么演进。

所以关键论断：**"设计期模型"是蓝图（交付即过时的风险），"运行期本体"是可执行、可写回、可审计、可演进的系统。** 落地价值在后者，不在前者。

### 2.3 写回回路 = 分水岭（本项目最核心的方法论点）

> **A semantic layer lets you read your business. An operational ontology lets you run it.**
> （语义层让你"读"业务；运行期本体让你"运行"业务。）

判断一个"语义层/指标层/本体"是不是真的运行期，用**三问测试**（源自 operational-ontology 参考实现，本项目已实现并验证）：

| 问题 | 问的是什么 | "只读语义层"的回答 | "平行数据库"的回答 | "裸写 API"的回答 | **本项目（运行语义层）的回答** |
|---|---|---|---|---|---|
| 1. 能从语义层取消订单吗？ | 语义层是否暴露业务**动作**（不是裸 update） | 不能 | 能 | 能 | ✅ 能：`cancel_order` 是注册的业务动作（src/ontology/actions.py），UI 与 LLM 走同一 `POST /actions/cancel_order` |
| 2. 源系统记录真的变了吗？ | 写回是否命中**源系统权威库**（不是只改本体索引/内存） | — | 变了但源系统没变 | 变了 | ✅ 真变：动作引擎对源系统库执行真实 UPDATE，E2E 直查源库断言 `status=cancelled` |
| 3. 已发货的会被拦吗？ | 业务规则是否在**动作前置校验**里权威生效 | — | 不会拦 | 会拦但只是 if 分支 | ✅ 被拦：前置规则返回 `SHIPPED_ORDER_CANNOT_BE_CANCELLED`，源库零变更 |

三问挂掉任何一问，MVP 都不达标。它们也是**机器可验证的 DoD**：每个问题都有对应 E2E 测试断言（见 §2.4 证据链）。

## 3. 落地五步法骨架（基于本项目实际）

> 本方法从 OntoRun MVP 落地过程提炼，顺序即依赖顺序。每步给"本项目做法"与"证据"。

### 第 1 步：定义对象 / 链接 / 动作（领域优先，不是表优先）

- **对象** = 领域概念（Customer/Order/Shipment…），不是表或 API 页；属性按"状态归属"标注（见第 3 步）。
- **链接** = 领域关系，双向命名自解释（order.items / item.order），不建"仅因共享外键而存在"的链接。
- **动作** = 业务操作聚合（cancel_order 是"取消整单"，不是"改 status 字段"）——避免 Action Sprawl。

**本项目做法**：Pydantic 模型 + 显式注册表表达本体（D-T2 已拍板，MVP 不引入 RDFlib——价值在运行时机制，不在序列化语法）；8 对象/8 链接/6 动作见 src/ontology/。
**证据**：tests/test_d2_registry.py（35 用例）；技术方案 §2。

### 第 2 步：注册自检（schema 一处分发、四处消费）

- 注册表启动时执行 `self_check`：主键唯一性、链接双向命名一致、动作参数完整、状态归属标注完整。
- schema 是**单一元数据源**：同时驱动 ① 运行时索引、② API 的 /meta/schema、③ 前端动态 UI、④ Agent 工具生成（技术方案 §3.2）。

**本项目做法**：src/ontology/registry.py + src/ontology/ 下每对象/链接/动作一个定义文件。
**证据**：self_check 实现（registry.py）；前端 `useMeta()` 拉 /meta/schema 驱动全部页面（web/src/hooks/useMeta.ts）——**新增对象类型/动作，前端零代码改动**（验收 F1，web/src/components/*.test.tsx 23 用例）。

### 第 3 步：运行时写回（动作引擎——校验→变更→写回→审计）

**核心管道**（技术方案 §3.3）：参数校验(Pydantic) → 源库事务 → 事务内重读快照 → 前置规则(业务规则权威在此) → 纯函数计算变更 → 写回源库 → 更新索引 → 审计落库。

- **拒绝路径早退**：任何前置不满足 → rejected + 业务错误码 + **源库零变更**（三问 3 的机制保证）。
- **状态归属三分类**（写回目标的显式声明）：
  - `source-backed`：源系统权威（订单状态、库存数量）——动作必须写回源库；
  - `ontology-owned`：源系统没有的列（cancel_reason、review_note）——本体自有存储即系统记录；
  - `derived`：计算态（available_qty）——永不写。
  - 每个动作的效果必须标注改了哪几类状态；写回只针对 source-backed——**杜绝"平行数据库幻觉"**（三问 2 的机制基础）。

**本项目做法**：src/runtime/action_engine.py + actions_impl.py；双库（源库=权威，本体库=索引+自有态+审计），一致性取补偿式（D-T4 已拍板）。
**证据**：tests/test_b2_action_engine.py 37 用例（含拒绝路径零写库断言）；tests/test_b1_index_query.py 20 用例。

### 第 4 步：语义接口暴露（统一写入口，无泛化写路径）

- REST 薄壳，无业务逻辑（业务规则只能在动作定义里，不允许出现"UI 校验 ≠ 动作校验"双轨）。
- **一切写操作（人类 UI 或 LLM）必须且只能经过 `POST /actions/{name}`**——结构性保证"没有泛化 update 路径"。
- 统一响应信封 `{request_id, outcome, data|error}`；错误码全集（17 个，技术方案 §4.3）。

**本项目做法**：src/api/routes.py（FastAPI）；OpenAPI 自动生成。
**证据**：tests/test_b3_api.py 27 用例；tests/test_agent_api.py 9 用例（Agent 与 UI 同一写入口）。

### 第 5 步：Agent 接入与治理（LLM 是"受约束的执行者"，不是"自由操作员"）

- **工具从 schema 自动生成**：每动作 → 一个 function-calling 工具（参数 = 动作的 JSON Schema）；只读工具只给 1 个 search_objects（控制 tool 数量与 token）。
- **防注入三层防线**：① 结构层——无泛化写工具；② 服务端——动作引擎前置校验是权威裁判；③ 人机层——高风险动作双签（LLM 提议 → 用户确认 → 才提交）。
- **错误码回填学习**：动作结果（outcome + error_code + message）回填为 tool 结果再交给 LLM 生成回复——LLM 从错误码学习规则，下一次提出正确替代方案（"本体规则约束 Agent"的可演示闭环）。

**本项目做法**：src/agent/{provider,tools_generator,agent}.py；provider 热插拔（MVP=DeepSeek，key 仅环境变量）。
**证据**：tests/test_agent_tools_generator.py 9 用例（golden 快照：6 动作 + 1 只读工具）；tests/test_agent_e2e.py 15 用例（全链路 + 双签 + 防注入 + 轮次上限）。

| 4 | **机制过载** | 双线/多角色/心跳/赛马/合并/审计/决策日志，仪式感 > 内容 | 机制从简：一条主线（最小语义接口闭环）+ 共享 git 仓库 + 明确验收门禁（三问测试 + E2E 全绿） |
| 5 | **自动驾驶空壳 + 基建摩擦** | automation 空会话不读写、依赖外部同步 | 单一事实来源 = 本地 git + 本目录文件；自动化须先有收敛判据与质量门禁 |

> 方法论写作的自省：本文"骨架"刻意不铺开成"七步法 + 二十条检查清单"——那正是反模式 2/4 的复发形态。每一步都可被本项目代码与测试验证，这就是骨架的合格线。

## 5. 与 Palantir 机制的对照（防"这不就是 CREATE TABLE"质疑）

### 5.1 对照表（OntoRun MVP 组件 → Palantir 机制）

| OntoRun MVP 组件（本仓库可运行） | 对标 Palantir 机制 | 调研出处 | 差异/简化说明 |
|---|---|---|---|
| registry（对象/链接/动作注册 + self_check） | OMS + Ontology Manager + 主键确定性 | palantir §1.3 / §3.1 | MVP 显式注册表替代元数据服务；主键确定性要求已落实（PK 不可变） |
| index（启动全量加载内存索引） | Object databases / Funnel 增量索引 | palantir §1.3 / §3.1 | 单机千级对象全量足够；增量管线发布期（技术方案 §7.4） |
| query（对象列表/详情/链接遍历） | OSS / Object Set Service | palantir §1.3 | MVP 支持等值/枚举过滤；模糊搜索待定 |
| action_engine（校验→变更→写回→审计） | Actions + submission criteria + rules | palantir §1.2 / §3.2 | 完全对齐：前置规则=submission criteria；拒绝路径早退 |
| **写回源系统库**（source-backed） | writeback / materializations | palantir §3.3 | MVP 直接写源库 SQLite（真实业务库），不做物化层——写回目标更直接 |
| 审计日志（audit_log，含 writeback_json） | action log | palantir §1.2 | 增加"写回 SQL + 影响行数"自证字段（三问 2 的证据面） |
| 冲突消解（策略 1 已实现，策略 2 预留） | 用户编辑优先 vs 时间戳优先 | palantir §3.2 | 与 Palantir 两策略一一对应 |
| 状态归属三分类 | source-backed / ontology-owned / derived | palantir §5.1.E | 完全对齐，落到每个属性与动作效果上 |
| 双库（源库=权威，本体库=索引+自有态+审计） | data layer vs object layer | palantir §2.2 | 补偿式一致性（源库先提交）；更强方案待定 |
| 本体驱动 UI（schema 一处定义四处消费） | Object Explorer / Workshop 读取运行时 | palantir §1.2 | 前端零硬编码业务页（F1 验收：改 schema 界面跟着变） |
| schema_version 演进 | branching / scenarios | palantir §3.5 / §6 洞察 3 | MVP 只做版本号；Git 式分支演进发布期 |

### 5.2 诚实结论（不给"复刻 Palantir"留话柄）

- **这些机制每一个都不是新发明**（索引、写回、审计、权限都是成熟技术）；Palantir 的价值在于**把它们与"模型"一体化**，并把本体做成平台级运行时。
- 本项目不是"我们复刻了 Palantir"，而是：**用最小可复现的闭环把每个机制做出来、测出来、公开证据链**——每个组件都小到能讲清、能测试、能被同行挑刺（技术方案附录 A）。
- **反方检验**：被问"这不就是表 + 存储过程？"时，回答 = §2.3 三问测试——你问的"表 + 存储过程"能不能回答"源记录真变了吗、已发货被拦吗、有审计吗"？能，那你已经做了一个（简版）运行期本体；不能，那它就是设计期蓝图。**分水岭不在名字，在机制。**

### 6.1 本体演进（洞察 3：被忽视的第二战场）

- 方法论与领域解耦：五步法第 1 步（定义对象/链接/动作）即领域工作，第 2-5 步是通用机制。
