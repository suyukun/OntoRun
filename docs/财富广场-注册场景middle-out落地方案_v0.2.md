# 财富广场·注册场景 middle-out 落地方案 v0.2

> 状态：v0.2（2026-09-09 夜间架构对齐后增补，待 Jack 终审）。**操作入口：数仓输入准备清单见 `docs/财富广场-数仓输入采集操作单_v0.2.md`（Jack 拿着派活的那一页，本篇是方法论备查）。**前置：docs/财富广场-ChatBI展示层产品设计_v0.2.md、demo（scripts/fortune_demo/）。架构决策详见 ADR-0010。

## 〇 一页结论

- 数仓按「数据是什么」组织（数据域：TR/CU/CH…），业务按「想问什么」提问。语义层是两套坐标系的转换器：**场景 = 横切若干数据域的表子集 + 问题集 + 口径卡**。
- 方法 = **卡 → 原语 → 组合** 三段循环：问题钉住口径（口径卡），口径提炼成原语（对象/度量/维度/身份规则），确定性编译器组合原语生成 SQL。LLM 只选原语，永不写 SQL。
- 输入规范：**给可执行的 SQL，别给描述性文字**；按问题拉取，不按库存推送。
- **架构分层（ADR-0010）：数仓=源 → 数据平面（镜像库 raw/derived/meta 三区）→ 语义层（只封装语义与访问，不复制数据）**。派生表 = 编译器产物，可重建、血缘自动成立。
- **能力两轴**：生成方式轴（L0 菜单→L1 规则→L2 原语组合→L3 自由 NL2SQL 拒绝）与编排深度轴（单轮识别→单步组合→多步编排）正交；深邃问题 = 外圈规划 + 里圈安全管道（§十一）。
- 验收含「非菜单证明」：两道从未做过卡的题必须靠组合答对并通过对账。

## 一 术语修正：场景 ≠ 数据域（2026-09 Jack 挑战确立）

| | 数仓数据域（官方分类） | 语义场景（本文） |
|---|---|---|
| 组织轴 | 按数据是什么分（名词） | 按业务想问什么分（动词性） |
| 服务对象 | 存储/治理/分工 | 消费/问答 |
| 例子 | 交易域 TR、用户域 CU、渠道域 CH | 注册场景、活跃场景 |

**方法论结论（进白皮书素材）**：语义场景横切数据域，两者不可混称。场景到数据域的映射表本身是交付物。

注册场景映射（2026-09-10 依 Jack 手工梳理的真实表清单重做，依据：`materials/fortune-warehouse-input/2026-09-10-注册场景关键表清单-Jack手工梳理.md`；此前 TR/dws_reg 假设作废）：

| 层 | 表 | 在场景中的角色 |
|---|---|---|
| ODS | ods_usms_lm_user_t_df / ods_usms_lml_account_t_df / ods_usms_lm_user_t_yx_df / ods_usms_sub_company_real_name_sync_record_df | 源头，仅血缘追溯，不进数据平面 |
| DWD | dwd_cu_rgst_fin_di | 注册事实·KPI 口径（业务过程主表，_di 增量） |
| DWD | dwd_cu_rgst_nonfin_di / dwd_cu_actv_df | 原始注册 / 激活事件（口径边界：麦当劳、中信书院激活进 KPI） |
| DWD | dwd_cu_real_df / dwd_ch_usr_rltv_df | 实名事实 / 渠道关联授权事实 |
| DIM | dim_cu_usr_info_df / dim_ch_chl_df | 用户属性（含实名状态、注册类型）/ 渠道维度（层级待确认） |
| ADS | ads_rgst_chnl_cnt_df 等 8 张 | 口径源：观远指标唯一数据源（不进绑定，见 §四） |

**关键事实（修正 demo 假设，全部是白皮书素材）**：
1. 注册属 **CU 用户域**（此前误设 TR 交易域）——与「注册是用户实体的动作」互证；
2. 注册场景**无 DWS 层**，ODS→DWD→ADS 直连——印证"数仓建设不必然标准，语义层适配现实"；
3. 「注册」一词有**三个口径**：KPI 口径（fin）/ 原始注册（nonfin）/ 激活口径（act），三张 ADS 日度汇总正好对应——「一个业务名词多个口径、语义层必须显式建模」的核心案例；
4. **实名有事实表**（dwd_cu_real_df），实名宽表 ads_chnl_real_info_df = 广场实名+银行同步合并——身份归一（I2）的现成案例。

本体视角：注册是用户实体的动作（事件），场景是「关于该动作的问题」的打包，不是给动作划存储地盘。

## 二 核心机制：卡 → 原语 → 组合（回应「这只是查 SQL」）

### 2.1 四层递进（生成方式轴）

| 层级 | 机制 | 判定 |
|---|---|---|
| L0 报表菜单 | 预写 SQL 一问一答 | 死路（问题空间组合爆炸，人工枚举追不上） |
| L1 规则选择 | LLM 选规则 ID（当前 demo） | 安全但不可扩展，过渡态 |
| **L2 原语+受约束组合** | **度量 × 维度 × 时间粒度，确定性编译器生成 SQL** | **目标态，本体收益所在** |
| L3 自由 NL2SQL | LLM 直接写 SQL | 幻觉面失控，拒绝 |

### 2.2 提炼规则（卡片如何变原语）

每张确认后的口径卡拆解为：

| 卡片成分 | 提炼为原语 | 注册表示例 |
|---|---|---|
| 去重键 | 身份规则（实体粒度） | 用户数一律归一到 usr_id |
| 聚合表达式 | 度量（measure） | 注册用户数 = COUNT(DISTINCT usr_id) |
| GROUP BY 列 | 维度（dimension） | 渠道 / 性别 / 时间粒度 |
| JOIN | 链接（link） | 注册事件 → 渠道 |
| 源表+过滤 | 对象绑定 + 口径声明 | 事实表 + 有效期 |

示例：REG_BY_CHANNEL 与 GENDER_RATIO 两张卡 → 一个度量（注册用户数）+ 两个维度（渠道/性别）→ 新问题「分性别分渠道注册数」「按周注册趋势」零新人工 SQL，组合生成。

**术语对齐（2026-09 调研后修正）**：上表「原语」词汇与业界两条主线同构，正式命名采用阿里 OneData 规范定义层（中文界事实标准，财富广场数仓大概率同源）：
- 度量 = **原子指标**（基于业务事件、不可再拆）；注册在本体系里是「业务过程」（不可拆分事件）
- 组合公式：**派生指标 = 原子指标 + 修饰词 + 时间周期**（OneData 原文；dbt 的 metrics 定义「functions combining entities, dimensions」与之等价）
- 维度 = OneData 称「可称为实体对象」——反向佐证 §一「场景横切数据域」结论
- 收益：与数仓同学说同一种语言，口径卡模板已加「指标分层」字段

### 2.3 为什么必须先有卡再抽象

- 口径真相只存在于现行 SQL 里，字典里没有（干瘪是行业常态，语义在数仓同学脑子里）。
- 从已验证口径提炼的原语**继承正确性**——实体先行（124 表全量理解）已实证失败，问题先行不抽象则停在 L0/L1。middle-out = 两者合取。
- 安全边界不变：编译器是确定性代码，LLM 自由度 = 选原语 + 给参数。**智能在模型，正确在编译器，真相在已验证口径。**

### 2.4 不变量（governance 测试锁死）

| # | 不变量 | 内容 |
|---|---|---|
| I1 | 同源一致 | Σ分渠道 = 总数（热路径 vs 明细下推，1778/1781 拦截器先例） |
| I2 | 身份粒度 | 所有「用户数」度量 dedup 到归一身份，禁止混用 anony_id |
| I3 | 时间显式 | 默认时间字段必须显式声明（rgst_dt vs data_dt），禁止隐含 |
| I4 | 组合保真 | 编译产物在卡片参数子集上必须与卡片 SQL 数字相等 |
| I5 | 拒答完整 | 未注册原语的问题必须结构化拒答并说明，禁止静默降级 |

## 十 数据平面与语义层架构（2026-09-09 夜间对齐新增；ADR-0010）

### 10.1 分层与三区

**数仓 = 源 → 数据平面（镜像库）→ 语义层（元数据+编译器）**。语义层只封装语义、不复制数据，但封装"对数据的访问"。查询路径：

```
问题 → LLM 选原语（不写 SQL）
     → 编译器按映射生成 SQL → 数据平面执行
     → 返回数字 + 审计记录
```

| 区 | 存什么 | 性质 |
|---|---|---|
| raw | 导入的原样表 | append-only/快照，不改不删；对账/审计/回溯的根基 |
| derived | 编译器生成的派生表 | 可随时 drop 重算 |
| meta | 语义定义/口径卡/审计日志 | 语义层的持久化 |

一句话：**语义层是账本加理货规则，数据平面是货；查货走账本，账本不囤货——但能决定新添货架（物化）。**

### 10.2 派生层：三个触发 + 实名示例

触发条件：身份归一（mapping 链查询时算太贵）、热门聚合（空间换时间）、本体友好重塑（特例封装进绑定）。

实名机制（编译产物，非手写；2026-09-10 依真实表更新——实名**既有事实表 dwd_cu_real_df 又有维表状态 dim_cu_usr_info_df**，正好演示「事件流 + 当前状态」双绑定，字段名待表结构确认）：

```
对象定义：User(usr_id)
  属性 gender ← dim_cu_usr_info_df.gender（直接绑定）
  当前实名状态 ← dim_cu_usr_info_df 实名状态字段（快照）
  事件 RealNameEvent(usr_id, event_time, ...)
       ← 源: dwd_cu_real_df（实名事实表）
```

编译器生成的派生视图（示意）：

```sql
CREATE VIEW user_real_name_events AS
SELECT usr_id, real_time AS event_time
FROM raw.dwd_cu_real_df
```

「实名既在事实表又在维表」的双源被封装在绑定里，LLM 永远不知道也不需要知道。一个对象可绑多张表（属性从不同表来，编译器生成 join）——Foundry object type backing dataset 同机制。

**诚实边界**：维表快照只给当前状态；事件史以事实表为准；两者都没有的概念只承诺**事件锚点**（发生过、何时），不虚构完整状态变迁史。

### 10.3 热门聚合与调度（三档，均不过度设计）

- 热门检测 = **审计日志的复用视图**（查询组合频次×耗时超阈值 → 建议物化 → 人工拍板）。V1 查询时全算（现状够用）→ V2 日志统计+人工确认 → V3 自动建议。不做全自动 view selection（学术深水区）。
- 调度：研究期静态无调度 → 联调 T+1 cron 跟随导出（导出→刷 raw→重算 derived→自动对账）→ 生产接现成调度，不自研。

### 10.4 引擎无关与演进预留

语义定义不绑存储，绑"编译目标方言"：DuckDB（本地）/ PG / DWS（PG 系）/ MySQL 各一个 emitter。物理位置抽象为**逻辑表名注册表**（逻辑名→物理位置+引擎）——映射表本来就有，lakehouse 演进（Parquet on 对象存储 + Trino/StarRocks/DuckDB）预留免费。MySQL 可跑但无列存，分析弱靠物化撑；方法论写"引擎能力分级"，不硬性规定引擎。

### 10.5 性能三层解（多表绑定 join）

① 分析场景 join 九成是维表 join（星型），数仓场景天然可控；② 热点路径物化成对象宽表（join 提前算好，与 DWS/ADS 同原理，只是 SQL 由编译器生成）；③ 慢了换引擎/加物化，语义层一行不改。

## 十一 能力分级（编排轴）与深邃问题路线（2026-09-09 夜间对齐新增）

### 11.1 两轴澄清

§2.1 的 L0-L3 是**生成方式轴**（单步查询怎么生成 SQL）；本节是**编排深度轴**（一个问题拆成几步）——正交，勿混。

| 编排级 | 形态 | 现状 |
|---|---|---|
| M1 单轮识别 | LLM 一次语义识别→选规则→返回 | **当前 demo（四条规则），v0.4 思考流是展示层的皮** |
| M2 单步组合 | L2 落地后：原语×维度×时间组合，非菜单证明 | **当前在建（本方案主线）** |
| M3 多步编排 | 外圈规划循环套里圈安全管道 | 多场景接入后做 |

### 11.2 深邃问题 = 外圈 + 里圈

```
外圈：LLM 看大问题 → 拆子问题1 → 查 → 看结果
    → 拆子问题2（可能因1的结果改方向）→ … → 汇总对比 → 答
里圈：每个子问题 = 选原语 → 编译 → 执行 → 对账（安全边界不变）
```

分工原则：**LLM 负责拆问题（智能在模型），每个子问题仍锁死在"选原语→编译→校验"管道（正确在编译器）**。深邃问题 = 多次安全组合的编排，不是放开 LLM 写 SQL——NL2SQL 一深就幻觉，我们一深只是多查几轮。

深邃问题需要的三样东西，语义层全有对应物：

| 需要 | 对应物 |
|---|---|
| "经营情况"可量化 | **指标树**：复合→派生→原子（OneData 分层本来就是树），逐节点查数、同比环比、好坏判定 |
| "为什么低"可下钻 | **对象+链接图**：用户↔渠道↔注册事件↔交易，沿图走：哪个渠道拖累、哪个客群低、贡献度分解 |
| "往前找原因"可串联 | **业务链路**：导流→注册→活跃→交易是本体上的事件序列，漏斗=沿时间对齐的事件查询 |

**诚实边界（写进方法论）**：承诺**诊断级**（哪里低、差多少、沿什么维度分解、跟什么联动）；**处方级**（怎么改）输出候选动作+数据依据，真因果需业务实验验证。敢承诺诊断、不吹处方。

### 11.3 实施顺序（不可倒）

没建。没有 L2 原语层，编排无米下锅（四条规则无可编排）；L2 落地 + 第二场景（活跃）接入后做外圈正合适——跨场景关联有真需求、有真原语可编。外圈是标准 planner-executor 循环（成熟模式不造轮子）+ 中间结果结构化上下文（控 token）+ 汇总判定逻辑。项目先例：金控 Agent 演示（S4 彩排九轮过线）已验证多步动作编排，`src/agent/` 基础设施复用。
