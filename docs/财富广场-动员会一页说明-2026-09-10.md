# 财富广场数据语义层·动员会一页说明（2026-09-10）

## 我们在建什么

给数仓建一层**语义层**：机器可读、人人可查的"口径资产层"。第一个样板间 = **注册场景**（19 张表、15 个加工脚本已交付起步）。

## 为什么值得做（今天已经拿出的证据）

数仓的口径真相——谁算注册、怎么算、什么时间窗、哪个渠道算数——**只存在于 15 个调度脚本的 SQL 代码里**。表结构里一个字都看不出来。

今天下午，我们让机器通读了这些脚本，已经自动读出（详见《口径发现卡片》）：
- 注册 KPI 口径的完整逻辑（麦当劳/中信用户要"激活"才算，含 3 个写死的业务日期边界）；
- 一张指标表同算 5 个时间口径；
- 渠道三级层级 + 三个口径开关；
- 一个潜伏的对账风险（left join 落空渠道组）。

**下一步：让"问一句话、答一个数"建立在确认过的口径上，而不是每次现写 SQL。**

## 怎么做（三步走）

| 步 | 干什么 | 状态 |
|---|---|---|
| 1. 读懂 | 机器解析 SQL：血缘图 + 口径规则提取 | **今天已出第一批** |
| 2. 确认 | 口径发现 → 是非题确认（你们勾对错，不写文档） | 下周 |
| 3. 组合 | 口径提炼成语义原语，新问题 = 原语组合生成 SQL，数字与现行报表对账 | 样板间目标 |

## 对数仓同学意味着什么

- **短期**：偶尔帮忙确认几个口径问题（选择题，几分钟一次）；
- **长期**：口径文档自动沉淀（每次确认即归档）、语义层对不上数时反哺发现 ETL 问题、报表取数不再逐个翻 SQL。

## 原则（这个项目怎么干活）

口径确认以**现行在跑的 SQL 为准**，不以记忆为准；机器生成的一切结论**可追溯**到具体脚本；对不上就亮黄牌，不静默兜底。
