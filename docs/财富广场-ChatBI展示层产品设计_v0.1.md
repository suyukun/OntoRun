## 一、背景与定位

### 1.1 一句话定位
面向数据分析场景的**可信问答入口**：用户用自然语言提问，系统在对话里给出**决策过程透明、数据可溯源、口径可审计**的回答。

### 1.2 与现有资产的关系
| 资产 | 状态 | 本设计的处理 |
|---|---|---|
| ChatBI 对话入口（批 3/4：SSE 流式、会话管理、证据抽屉、图表） | 已上线金控场景 | 交互模式与体验基线的来源 |
| 语义层机制（规则路由/口径/校验/trace 落库） | demo 已验证 | 被展示的数据源与后端 |
| 决策流水线/冷热路径/证据编号 | demo 已验证 | 融入对话消息的证据体系 |
| 金控证据抽屉（结论依据五区） | 金控场景在用 | 并入统一「证据面板」作为分区（不替换，见 §3.4） |

### 1.3 设计原则（对抗 demo 实测暴露的问题）
1. **过程透明即信任**：决策过程、SQL、执行耗时、校验结果默认可见于对话流——「快得像假的」的质疑只能靠透明消除；
2. **数据直接呈现**：回答后紧跟数据表格/图表，不许只给一句话让用户点按钮；
3. **渐进披露**：默认展示结论级信息（回答+数据+关键校验），完整 trace 折叠为「详情」——过程可见≠过程刷屏；
4. **失败可见且友好**：拒答/追问/超范围/校验失败/服务异常，每种失败都有明确人话，禁止无声卡死与编造；
5. **壳通用 + 业务可装配**：对话壳不含业务语义，业务差异收敛为 profile（业务档案：端点+主题+面板清单），新增业务=新增 profile，壳零改动。

## 三、信息架构与界面结构

### 3.1 整体布局（文字线框）

```
┌────────────────────────────────────────────────────────────────┐
│ Header：业务名 · 场景名 · 数据说明（合成/正式）· 全局入口        │
├──────────┬─────────────────────────────────────┬───────────────┤
│ 会话栏    │  对话区（消息流）                     │ 上下文栏（可选）│
│          │                                     │               │
│ ＋新对话  │  [用户气泡]                          │ · 当前口径卡片  │
│ 会话列表  │  [AI 消息卡]                         │ · 数据范围      │
│ ·置顶分组 │   ├─ 决策过程（摘要→可展开）           │ · 常用问题      │
│ ·普通列表 │   ├─ 回答（文本+图表）                │               │
│ ·历史归档 │   ├─ 数据表格/图                     │               │
│ 每条:    │   └─ 摘要条（路径徽章+证据编号+详情）  │               │
│ 重命名/  │  [用户追问…]                         │               │
│ 置顶/删除│                                     │               │
├──────────┴─────────────────────────────────────┴───────────────┤
│ 输入区：输入框 · 发送 · 示例问题 chips（首次展示）                 │
└────────────────────────────────────────────────────────────────┘
```

### 3.2 AI 消息卡结构（核心组件）

```
┌─ AI 消息卡 ────────────────────────────────────────────┐
│ ① 回答区（最先映入眼帘）                                 │
│    正文结论（LLM 生成判断性文字，数字由语义层注入）          │
│    ┌─图表/表格（按规则声明的可视化类型渲染）─┐              │
│ ② 数据区（「返回数据」表格，默认显示前 N 行+共 X 行）        │
│ ③ 决策过程区（三级呈现，见 3.3）                          │
│ ④ 摘要条：路径徽章 · 证据编号 · [详情] [追问建议…]         │
│ ⑤ 证据面板（详情抽屉，默认收起）：                        │
│    Tab1 决策过程全记录（含 LLM 原始输出/完整 SQL）          │
│    Tab2 结论依据（口径/命中规则/数据路径/校验记录）          │
│    Tab3 返回数据（全量）                                  │
└────────────────────────────────────────────────────────┘
```

### 3.3 决策过程的三级呈现（渐进披露，核心设计）

| 级别 | 内容 | 触发 |
|---|---|---|
| L1 摘要行（默认） | 「❄ 冷路径 · 4 步校验全过 · 1.9s · 证据编号」 | 生成回答后自动显示 |
| L2 过程摘要（默认展开于消息内） | 关键步骤精简列表：路由结果 / 口径 / 参数 / 校验结论（隐藏 SQL 全文与 LLM 原始输出） | 生成过程中实时直播，完成后保留 |
| L3 完整记录（详情抽屉） | 全部步骤含 LLM 原始输出、完整 SQL、逐项校验 | 点「详情」展开 |

> Demo 教训：9 步全部常驻展开占半屏（信息过载）；全部折叠进按钮又造成「快得像假的」的不信任。L2 直播 + L1 摘要是平衡点。

### 3.4 证据面板的统一（金控与财富广场的合并方案）
统一「证据面板」容器 = **结论依据（what）+ 决策过程（how）+ 返回数据** 三个分区，由 profile 决定分区构成：
- 财富广场 profile：决策过程 + 结论依据 + 返回数据；
- 金控 profile（未来）：结论依据五区（结论/basis/命中规则/口径分母/明细引用）+ 决策过程 + need_confirm 卡。
- 理由：金控证据抽屉回答「依据是什么」（what），决策流水线回答「怎么算的」（how）——都是「凭什么信」的子集，替换丢维度，合并成完整审计链。

### 3.5 会话栏
- 会话列表：置顶分组/普通分组；每条支持 **重命名、置顶、收藏、删除**（删除需二次确认）；
- 查询历史：当前会话内每次查询的 trace（证据编号+问题+路径），点击回放至对话流；支持单条删除；
- 会话持久化：刷新/重开不丢失（落本地存储或服务端，见 §6 非功能）。

### 3.6 输入区
- 输入框 + 发送；Enter 发送 / Shift+Enter 换行；
- 示例问题 chips：仅空会话首次展示；点击即发送；
- 输入中防抖：BUSY 时禁用发送并显示进行中状态。

## 四、交互流程与状态定义

### 4.1 一次查询的生命周期（SSE 事件驱动）

```
用户发送 → 消息流追加用户气泡 + AI 消息卡（骨架态）
  ├─ step 帧：决策过程 L2 实时逐条点亮（意图路由→口径→参数→编译→执行→校验）
  ├─ token 帧：回答区逐字流式
  └─ final 帧：数据表格渲染 + L1 摘要条 + 详情面板装载 + 历史刷新
异常分支：
  ├─ 网络失败/服务不可达 → 消息卡内红字「查询失败：原因」+ 重试按钮
  ├─ final 缺失/超时（>30s）→ 超时提示 + 重试
  └─ 拒答/追问/校验失败 → 决策过程显示拦截步骤 + 回答区显示人话说明（不编造）
```

### 4.2 六种回答状态的定义（每种都必须有明确 UI 形态）

| 状态 | 回答区 | 数据区 | 附加 |
|---|---|---|---|
| 成功（热/冷路径） | 结论文字 | 表格/图 | L1 摘要 + 详情 |
| 范围外拒答 | 人话说明 + 「为什么」引导（当前范围/如何扩展） | 无 | 拦截步骤可见 |
| 参数追问 | 追问句 + 快捷参数选项（如月份 chips） | 无 | 选中即续查 |
| 超数据范围 | 如实说明数据边界 | 无 | 边界信息 |
| 校验失败 | 「校验未通过，拒绝返回」+ 原因 | 无 | 强调「宁可不答不出假数」 |
| 服务异常 | 错误原因 + 重试按钮 | 无 | — |

### 4.3 多轮追问（P1，正式版）
「那 7 月呢？」「只看微广场呢？」→ 语义层上下文继承（复用上一问的规则与参数，仅替换变化项）；追问链在消息中可视化（引用哪一问）。

## 六、非功能需求
- 性能：热路径端到端 ≤3s（LLM 路由 1-2s + 查询 <100ms）；冷路径 ≤10s；超 30s 超时提示；
- 持久化：会话与消息落库（服务端），证据 trace 已有 JSONL，正式版迁审计库；
- 安全：密钥仅环境变量；PII 只呈现加密态；LLM 输出仅限规则枚举（发明即拒）；
- 可访问性：键盘可达、对比度达标、动态内容有 aria-live；
- 兼容：≥1280px 桌面优先；窄屏降级单栏（P1）。

## 七、验收标准（可测试）
1. 提问后消息内依次出现：决策过程摘要（≤5 条关键步骤）→ 回答 → 数据表格 → 摘要条；
2. 六种回答状态各配至少一个真实问题验证（热/冷/拒答/追问/超范围/校验失败）；
3. 任意回答可展开详情看到：LLM 原始输出、完整 SQL、逐项校验、证据编号；
4. 证据编号可在历史中回放出与当时一致的消息卡；
5. 会话管理四操作（重命名/置顶/收藏/删除）可用且持久化；
6. 刷新/重开浏览器后会话与消息恢复；
7. 无 JS 未捕获错误；网络断开有明确错误与重试；
8. 新增一个业务域（如活跃域）仅需：注册规则 + profile 配置 + 新面板组件，壳代码零改动。

## 八、分期

## 九、开放问题（请评审重点火力）
1. D3 的 L2「过程直播」保留在消息内是否会干扰阅读？是否应默认收起为一行、展开可看？
2. D6 LLM 生成判断文字的边界：只允许基于语义层返回的数据做描述性归纳，禁止外推——这个约束如何在产品上表达（用户可识别「哪句是判断」）？
3. 图表类型由谁决定：规则注册时声明（语义层定）还是 LLM 按数据形态选（灵活但有错选风险）？
4. 会话持久化放服务端（SQLite 新表）还是本地（localStorage）？多设备诉求是否存在？
5. 「证据编号」是否需要面向用户解释（如 hover 说明），还是仅作为审计标识存在？
