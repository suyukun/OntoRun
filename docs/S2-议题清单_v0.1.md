## 0.5 讨论管理机制（Jack 确认 2026-08-20）

**核心原则：不按难易，按影响面分层 + 滚动复核。** 简单议题先做的代价是：复杂议题结论一变，前面简单结论返工。故：

1. **议题分三档（按影响面）**：
   - **A 定调档**：#9 企业生成工具、#1 ChatBI、#8 方法论 —— 决定 S2 骨架，**先定"形态"**（一句话说清它是什么），细节后补；
   - **B 支撑档**：#2 规模化治理、#3 权限、#4 会话持久化 —— 依赖 A 的形态才能定；
   - **C 工程档**：#5 真实场景、#6 CI/UX、#7 一键起 —— 独立可收口，随时插空。
2. **A 类内部有先后**：#9（造真实企业战场）→ #1（ChatBI 在战场上演进）→ #8（方法论从落地里长出来）。落地先行，方法论不先空写。
3. **滚动收敛**：每个议题收口时检查依赖它的议题结论要不要改；每轮结束全量复核一次；新议题随时登记、定影响面后**入下一轮**，不插队当前轮。
4. **单一事实来源**：本文档每议题维护四字段 = 状态（待定/形态已定/细化/收口）+ 结论（一句话）+ 依赖 + 待决。结论一变 → 更新清单 → 标记受影响议题复核。

**不造轮子铁律（Jack 强调 2026-08-21，全 S2 适用）**：
- 成熟可用 = 大量人使用 + 充分认可（不因"能用"就当成熟）；
- 技术组件（引擎/框架/协议）一律优先成熟件：分析引擎 DuckDB、指标层 dbt Semantic Layer/LookML、LLM SDK、前端框架等；
- 自研边界 = 仅"研究本身"：本体运行时（S1 已定）、本体↔分析引擎映射（ChatBI 差异化点）。其余任何可被成熟件覆盖的，禁止自研；
- 落地时先调研候选成熟件（含国内可达性），再决定自研 vs 引入，绝不默认自研。

**当前讨论序**：A 档 #9 → #1 → #8（只先定形态）；B/C 档随后。

## 0. S2 的本质：把「机制可行」变成「经得起真实企业的量级、规模与治理」

S1 证明的是"一条端到端流程能通过语义接口闭环走通"；S2 要回答的是三件事：

1. **量级**：几百 TB~PB 级数据下语义接口不崩（ChatBI 是刀刃上最难的场景）；
2. **规模**：对象/动作从几个到几百上千，治理方式不再靠手写注册表；
3. **可信**：从演示环境到有权限边界、有审计、会话不丢、能给别人用的生产要素。

## 3. 议题 9：真实企业生成工具（Jack 新增，⭐）

**问题**：OntoRun 需要"接近真实企业的业务环境和数据"做演示与测试，而 S1 的 `data/seed_retail_source.py` 是**手工确定性脚本**（300 客户/60 商品/2200 订单 + 手工 corner case），不是"能生成一个企业"的工具。

**Jack 原意**：构造一个系统/工具，可以**把一个企业的真实业务流程、机构、ERP、财务系统、各种各样的表和数据真实地产生出来**，生成接近于真实企业的业务环境和数据信息，用于 OntoRun 的演示和测试。

**第一性原理拆解**（待 Jack 拍板的方向，非结论）：
- 核心矛盾：真实企业 = 业务（流程）+ 组织（机构）+ 系统（ERP/财务）+ 数据（多表、脏、有 corner case）。S1 只覆盖了"零售供应链交易链"一张网。
- 形态候选：
  - A. **企业生成器（Generator）**：配置化的企业"骨架"（行业/组织/流程/系统清单）→ 生成库表 + 带业务语义的数据（确定性+可复现），类似 S1 seed 脚本的规模化泛化；
  - B. **场景模拟器（Simulator）**：数据不是一次生成，而是按业务流程"运转"产生（时间推进、状态流转、跨系统写回），接近真实运行的 ERP；
  - C. **合成数据工厂**：偏数据侧，用生成模型/规则产出大规模、多脏度、多 corner case 的表数据。
- 与 OntoRun 的关系锚点（防目标漂移）：生成工具是"⑤ 数据/源系统"层的弹药——让本体运行时有更真实、更复杂的对象/链接/动作空间去治理；本身不是研究对象（不造数据治理轮子）。
- 与议题 5（真实场景试用）关系：生成企业当"练兵场"，真实场景当"验收场"。

## 3.5 议题 9 形态结论（2026-08-21，Jack 拍板）

1. **DES 定位** = OntoRun 模块 `des/`（非独立项目），先做 P0 最小集（YAML 配置 + 数据表生成 + 问题注入），3-4 周；
2. **本体映射做实**：维度 7（问题→本体概念）第一阶段必做——DES 产出的问题必须能对上 OntoRun 本体，防断链；
3. **技术降配**：SQLite + Python 标准库 + pydantic（复用现有栈）；砍 pandas/pyarrow/SimPy/NetworkX/Mimesis；
4. **SQLite 性能实测**（本机 100 万行+5 万客户，123MB）：插入 9.3s、等值 3ms、join 30ms、全表 SUM 67ms、TOP10 聚合 2.3s——覆盖 DES 目标量级（25 万行/季度）4 倍以上；
5. **量级真相**：真正瓶颈是无预聚合的即时大聚合（2.3s），反哺议题 1（ChatBI 需预聚合/物化视图）；SQLite 承载预聚合表没问题；
6. **规模策略**：1 企业 = 1 库（规避单库膨胀）；发布期 SQLite → PostgreSQL（schema 层预留）。

## 3.5 议题 1 形态结论（2026-08-21，Jack 拍板 v2）

1. **预聚合优先**：分析指标先物化（成熟数仓范式 + DuckDB/dbt 语义层），LLM/本体查的是**物化结果**，不是裸表现场算——继承 Jack 数仓"空间换时间"经验，Palantir 亦然（官方区分 pre-computed vs dynamically derived，<~1 万对象/查询才用动态派生）；
2. **本体读侧 = 物化指标的语义入口**：本体对象可"指向"预聚合指标（对象→指标定义→物化结果），Agent 在本体上选择，落到预聚合层执行；本体不取代数仓，是给数仓成果加语义外壳；
3. **不造轮子**：物化/维度建模用成熟范式（dbt 语义层/DuckDB），OntoRun 只做"本体↔物化指标"映射；
4. **Palantir 对照**：其查询机制 = Agent 在本体上"选 object set → 过滤/聚合/加载"，对象被索引进对象库（OSv2/Funnel）；预聚合走 pipeline，非查询期现场算；
5. **分析引擎选型**：DuckDB（成熟 OLAP 嵌入库，列存/向量化）作 ChatBI 分析层；SQLite 保留作源系统/写回层（S1 不变）；不用 SAP HANA 内存库（MVP 过度设计，DuckDB 即"穷人版分析内存库"）。

## 3.7 议题 2 形态结论（2026-08-21，Jack 拍板）

**问题本质**：S1 靠手写注册表（8 对象/8 链接/6 动作）；S2（DES 真实企业 30-50 表/几十对象动作）下手写必崩。核心难点 = **业务数据 → 本体映射**（Palantir FDE 最有价值部分），但中小企业项目养不起重人力 → 折中 = 工具自动化 + 轻人工审核。

**形态**：
1. **映射对象 = 两者都要（C）**：DES 生成数据（语义已知，半自动映射）+ 外部导入真实数据（语义未知，自动推断 + 审核）。演示用 DES，交付接真实数据——两者不内部绑定（未来落地数据都不是 DES 生成的）；
2. **映射自动化 = 分级置信度 + 轻人工审核**：builder 现有映射能力（FK 检测/命名对齐/LLM 提取）+ DES 自带语义 → 映射候选 + 置信度；**高置信度自动过，低置信度进审核队列**；人只审可疑项（~80% 自动 + ~20% 人审），人从不从零建模；
3. **映射审核工作台（Q2）**：本体驱动 UI 一页式 = 映射建议队列（源表/字段 → 候选对象/属性/链接 + 置信度）+ 批量接受/拒绝 + 冲突标记（同字段映射二义性高亮）+ 人工修正（改完即入注册表）+ 审核痕迹（对接议题 3 权限/审计）；不新造轮子，扩展现有 builder 页面（React+AntD）；
4. **动作规模化**：动作白名单保留 + **动作模板库**（create_order/cancel_order 家族做成可复用模板，新动作从模板派生）；
5. **校验规模化**：分两层 = 通用约束（自动套用：金额≥0/枚举合法）+ 业务规则（模板携带或人工），用"校验注册表"管理、可机验。

## 3.9 议题 3 形态结论（2026-08-21，Jack 拍板）

**问题本质**：S1 演示环境无鉴权；S2 要"可信"——谁能读/写/审，动作被审计。

**形态**：
1. **主体 = 双主体**（Agent 操作 + 人审核工作台/规则制定）；未来演进单主体理想态保留（系统价值 = 人定规则机器执行，非机器替代人）；
2. **客体 = 读/写/审三分治**：读（ChatBI 只读查询，不碰源库）、写（动作写回，S1 已有门控）、审（映射审核，人专属）；
3. **粒度 = 对象级 + 属性（列）级**，角色级作便捷分组（不够用）；**权限做在语义接口层**（本体对象/链接/动作挂权限策略），不依赖数据库层——因 SQLite 原生无行/列级权限、DuckDB 有 rls/table_guard 社区扩展但有限，语义层承载才匹配"本体即治理"（Palantir 同：对象类型级 + 属性级安全策略）；
4. **载体**：权限策略挂本体元数据（对象类型→谁能读/写），审核痕迹对接审计（议题 2 工作台天然接入）；
5. **不造轮子**：复用现有 FastAPI 鉴权 + 审计框架；字段级如需可引 DuckDB rls 扩展（成熟件）。

## 3.11 议题 4 形态结论（2026-08-21，Jack 拍板）

**现状**：前端 localStorage 已做 MVP（TD-15）；后端 session 内存态（src/app/session.py）。

**形态**：
1. **存什么**：会话消息 + 会话状态（选中对象/上下文）+ 审计关联（会话 id 挂动作审计，对接议题 3）；
2. **存哪**：**SQLite 单表**（sessions + messages，复用现有双库）；不引 Redis（发布期多实例才需要，S2 单机 SQLite 够，符合不造轮子+轻量）；
3. **TTL**：30 天清理；会话 id 串审计，可追溯"谁在什么会话做了什么"。
