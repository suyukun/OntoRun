## 2. 机制对照表（本体 vs 传统语义层 vs Palantir）

> 用途：知乎/公众号长文核心表；回答"这不就是语义层/指标层/数据中台换个名字吗"。

| 维度 | 传统语义层/指标层（LookML、dbt Semantic Layer 等） | Palantir Foundry Ontology | **OntoRun MVP（本项目可复现）** |
|---|---|---|---|
| 形态 | 设计期"度量/维度"定义 + 查询翻译 | **运行期系统**：对象被索引、可查询、可编辑 | **运行期系统**：Pydantic+注册表 → 索引/查询/动作执行 |
| 数据流向 | 单向：源 → 指标 → 报表 | **双向**：源 → 本体（读），本体 → 源（Actions 写回） | **双向**：源库=权威，动作真实写回源库 |
| 决策/行动 | 不建模决策 | 显式建模 Action（规则+审批+审计） | 6 个业务动作 + 前置规则 + 双签 + 审计 |
| 业务规则位置 | 报表层/应用层 | **Action 前置校验（submission criteria）** | 动作定义的前置规则（动作引擎权威校验） |
| 治理/审计 | 报表权限 | 本体层安全 + action log | 审计落库（writeback_json 自证）+ 双签 |
| 与 AI 的关系 | 可作 RAG 上下文 | 对象/链接/动作直接作为 Agent 工具 | **工具从 schema 自动生成**，LLM 走同一写入口 |
| 演进 | 增量，无版本化协作 | branching / scenarios | schema_version 版本号（发布期补分支） |

> 反方提示（写长文时引用）：建模符号层面，Palantir 的 Object/Property/Link 与 ER/表结构高度同构（vonng 批判）；**同构的是 schema，不同构的是运行时与写回回路**——本表最后一列即 OntoRun 对"机制可复现"的实证。

**可发等级**：✅ 表格本身可直接发；配文叙事（"Palantir 国内落地空白"等）🔒 需 Jack 审。

## 3. 三问测试（最锋利的表达单元）

> 用途：一条帖/一段话，验证任何"语义层"是不是真运行期。三问 + 本项目回答。

**三问**（源自 operational-ontology 参考实现）：

1. **能从你的语义层取消订单吗？** —— 语义层是否暴露业务**动作**，而不是裸 update？
2. **源系统记录真的变了吗？** —— 写回是否命中**源系统权威库**，而不是只改本体索引/内存？
3. **已发货的订单会被拦吗？** —— 业务规则是否在**动作前置校验**里权威生效？

**本项目回答（全部真实数据验证）**：

| 问 | 本项目回答 | 证据 |
|---|---|---|
| 1 | ✅ 能：cancel_order 是注册的业务动作，UI 与 LLM 走同一 `POST /actions/cancel_order` | tests/test_agent_e2e.py::test_cancel_order_full_chain_e2e |
| 2 | ✅ 真变：动作引擎对源库执行真实 UPDATE；E2E 直查源库 status=cancelled；审计 writeback_json 含 SQL+行数 | 同上 |
| 3 | ✅ 被拦：SHIPPED_ORDER_CANNOT_BE_CANCELLED，源库零变更 | tests/test_agent_e2e.py::test_cancel_rejected_shipped_order |

**配套金句**（可直接引用，出处 operational-ontology / Palantir 生态）：

> A semantic layer lets you **read** your business. An operational ontology lets you **run** it.

> 三种"假语义层"的鉴别：答"不能取消"= 只读层；答"能但任何系统记录都没变"= 平行数据库；答"能且已发货订单也被取消"= 只是裸写 API（缺规则门控）。

**可发等级**：✅ 三问与证据可直接发（事实+测试可复现）。

## 4. 亮点清单（可对外讲的 4 个亮点）

> 用途：每条可独立成帖（标题 + 3 段话 + 1 张截图）；也可串成合集。均为**已验证事实**。

### 亮点 1：本体驱动 UI——改 schema，界面跟着变 ✅
- **一句话**：前端所有页面（对象列表/详情/链接导航/动作表单）都由一份本体 schema 自动生成，**新增对象类型或动作，前端零代码改动**（验收标准 F1）。
- **细节**：schema 一处分发、四处消费——运行时索引、API /meta/schema、前端 UI、Agent 工具生成（技术方案 §3.2）。
- **证据**：web/src/components/*.test.tsx 23 用例；演示段②（对象浏览）。
- **锚定**：这回答"语义接口长什么样"——接口的形状由本体定义，不是人肉写死。

### 亮点 2：LLM 经语义接口真写回 ✅
- **一句话**：LLM 说"取消 ORD-1001"，不只是返回一句话——动作引擎校验后**真实 UPDATE 源系统库**，订单状态变 cancelled、库存释放。
- **细节**：UI 与 LLM 走同一写入口 `POST /actions/{name}`，无泛化写路径（结构性防注入）。
- **证据**：E2E 直查源库断言 status=cancelled（test_agent_e2e.py::test_cancel_order_full_chain_e2e）。
- **锚定**：这是"操作接口"与"只读语义层"的分水岭——LLM 能做事，且做得有据可查。

### 亮点 3：双签治理——高风险动作必须人工确认 ✅
- **一句话**：退款审核这类高风险动作，LLM 只能"提议"，必须用户点确认才执行——提议不执行、确认前零审计、拒绝零副作用。
- **细节**：need_confirm 契约（{id, name, arguments}）；/agent/chat → /agent/confirm 两段式。
- **证据**：test_approve_refund_double_sign_confirm / _reject（确认前审计 0 条）。
- **锚定**：回答"LLM 越权怎么办"——不是靠提示词求它守规矩，是接口层有闸 + 有痕。

### 亮点 4：审计自证——"源记录真变"的铁证 ✅
- **一句话**：每次动作（含被拒的）都落审计：谁、何时、传了什么参数、前置规则怎么判、写回 SQL 是什么、影响几行。
- **细节**：writeback_json 字段 = 写回 SQL + 影响行数，独立于"直查源库"可自证三问 2。
- **证据**：src/runtime/audit.py + audit_log schema（技术方案 §3.5）；E2E 断言。
- **锚定**：这是运行语义层区别于只读层的证据面——"改了没、谁改的、合不合规"都可追溯。

## 5. 对外发布分级与流程（重要）

### 5.1 分级规则（对应 AGENTS.md 边界三档）

| 等级 | 含义 | 内容 | 动作 |
|---|---|---|---|
| ✅ 可直接发 | 事实性、可复现、无叙事风险 | §1 架构图、§2 对照表、§3 三问、§4 亮点（单条） | 走 learn-in-public 常规流程，落盘即视为可复用素材 |
| 🔒 需 Jack 审 | 涉及项目叙事/未定项/对外边界 | §4 亮点合集叙事、白皮书全文、演示录像、任何提及"路线图/金融行业/Palantir 空白"的措辞 | 提交 Jack 过目 → 独立 red-team 审查 → 才可发布 |

### 5.2 发布前红线（逐条自查）

- [ ] 无密钥/内部部署细节（deploy-notes.md 绝不对外）；
- [ ] 数字可复现（测试全绿是前提；引用的测试/文件路径真实存在）；
- [ ] 不称"定稿"（本文档与白皮书均为 v0.1，待 red-team）；
- [ ] "待定"项不写成结论（流式输出/分支演进/多行业等）；
- [ ] 每篇可回答"这跟语义接口/本体论落地有什么关系"（防目标漂移）。

### 5.3 建议的对外节奏（待 Jack 确认，🔒）

1. 单条亮点帖（4 条，纯事实）→ 测试为证；
2. 三问测试帖（最有传播力）→ 配演示截图；
3. 一页架构图（配"最小闭环"叙事）→ 预热；
4. 白皮书全文（red-team 后）→ 长文沉淀；
5. GitHub/Gitee 公开（含可复现运行步骤）→ 压轴（发布期定）。
