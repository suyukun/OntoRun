## 一、四路共识（≥3 模型一致 → 高置信修正项）

### 🔴 P0-1 选表无标准：55 张是拍脑袋，必须"以演示剧本倒推"（4/4 一致）
- 四路模型全部反对"预估贴源 34 + 应用层 19 ≈55 张"的选法，无选表方法论 = M1 不可验收、M2 无法开工。
- **修正**：先写 M4 的 5-8 个 demo 问题（"今日新增橙色预警？""某集团客户集中度？""某押品估值变动？"），从剧本反推必选表。
- **规模**：首版 **15-20 张核心表**（贴源 8-10 实体 + 应用层 3-5 指标 + 字典/组织 2-3），55 张是 S4 量级。

### 🔴 P0-2 严格串行排期错误，违反 S2 已验证的"垂直切片先行"（3/4 一致）
- deepseek/kimi/doubao 均指出：M1 不依赖 M2 全部（表结构一周可定），M2 不依赖 M3 全部（第一版本体即可开工），M4 可完全并行（mock 数据开发 UI）。
- **修正**：拆 M1a（选表+脱敏+表结构确认，1 周）→ M2 立即开工；M2 出第一版本体（3-5 对象）→ M3 立即开工；M4 全程并行。
- **关键路径**：M1a → M2(迭代) ↔ M3(迭代) → 联调 → M5；M1b（数据生成）、M4 非关键路径。

### 🔴 P0-3 "表结构驱动"≠"自动本体建模"：M1 禁止做本体（3/4 一致，minimax 最强）
- minimax/kimi/doubao：表结构是物理层，本体是语义层，不可自动互推（"客户-集团是聚合还是组合"不会从 JOIN 长出来）。DES 若"顺便做本体"= 研究目标漂移。
- **修正**：M1 严格只做"表结构→模拟数据+物化指标"；M2 在 M1 的 schema metadata 之上**手写本体**。接口 = schema metadata。

### 🟠 P0/P1 业务动作设计是最大薄弱点（4/4 一致）
- 金控风控动作有标准流程（预警生成→人工确认→分派→处置→审批→执行→销号），每环节角色/权限/审批层级不同，状态依赖强。
- **修正（doubao 最佳方案）**：动作**做深不做多**——只做 2 个核心动作+完整状态链路：① 预警级别调整（建议→双签→执行→审计）② 处置单审批（创建→审批→执行→销号）。做深 = 状态机完整 + 角色权限分明 + 审计可追溯。
- **业务来源**：借 Jack 人保/中信真实风控流程（现成知识库），输出"风险预警业务动作说明书"（动作清单/状态机图/角色权限矩阵/审批规则）。
- **验收前置**：动作清单须 Jack 拍板后才派 M2 编码活（"待定项未定不派活"铁律）。

### 🟠 P0/P1 读/写引擎必须分离（minimax 最强，doubao/kimi 支持）
- 读的不变量 = "答案与表一致"；写的不变量 = "状态机合法+并发安全+可回滚+审计+双签"。S2 的 7 道校验针对读，搬到写上失效。
- **修正**：M3 拆两引擎——读引擎（沿用受限结构化查询）+ 写引擎（**动作模板**：每动作固定参数 schema+预检规则+双签门槛，LLM 只做问询理解+动作选择+参数填槽，**不生成任何写语句**）。
- 这是 S3 新增研究价值：**读易写难**，写动作的可表达集/预检/双签 UX 本身是新研究问题。

### 🟠 P1 范围控制：DES"一步到位标准化产品"过度（kimi/doubao/minimax）
- 三个模型同意 DES 表结构驱动方向（护城河），但"自动本体建模"是研究级问题，S3 只做到"表结构驱动数据生成"。
- **修正**：S3 定义为"金融风控 demo 跑通"，DES 完整产品化留 S4；M1 只做"为安平金控生成 20-30 万行"的配置化脚本。deepseek 补充：DES 保持"配置驱动+专用生成函数"混合模式（贷款合同号/五级分类迁移/押品估值等金融专用逻辑），保证数据真实感。

## 二、重要分歧（并列呈现，Jack 拍板）

| 议题 | 立场 A | 立场 B |
|---|---|---|
| DES 架构 | deepseek：保持领域专用生成器（专用逻辑=数据真实感来源），配置驱动+专用函数混合 | doubao/minimax：表结构驱动是护城河（快速适配任意行业） |
| 本体起点 | kimi/minimax：**本体优先**（先定义语义层再派生源表，防止表=本体） | deepseek：以表结构为输入反推本体（真实表结构携带复杂度） |
| 旧数据去留 | kimi：保留 data/retail 可切换（防丢 S2 regression 基线） | Jack 已拍板：<200M 备份后清空，未来只用新数据集 |
| 动作颗粒度 | minimax：demo 用单步即可（多步会签/转办留后） | doubao：做深 2 个动作含完整状态链路 |

> 我的倾向（供参考，最终你拍板）：DES 用"配置驱动 + 金融专用生成函数"混合模式（既保真实感又保可配置，兼顾 A/B）；本体以表结构为**输入参考**但坚持"业务对象视角"建模（防表=本体，取中间路线）。

## 四、复核补充的"遗漏项"（全部采纳进 S3）

- **30 题金融 ground truth 评测集**：M3 验收标准（无评测集=验收无据），S2 模式复用+金融扩写。
- **双签 UX 单独设计**：demo 高光时刻——LLM 提议→人工看 diff→确认/驳回。
- **拒答场景演示价值**：问一个答不了的问题展示 fail-closed 明确拒答（金融风控最大卖点）。
- **字段值脱敏**：不只表名，人名/金额/机构名也要脱敏（防 demo 像玩具）。
- **演示冷启动/预热**：1.6s 延迟需首批问题预热 + 物化结果缓存。
- **LLM 失败兜底**：超时/解析失败/拒答 fallback 话术 + 降级到可答清单。
- **演示环境隔离**：data/s3_demo/ + 切换开关。
- **AGENTS.md 阶段声明 + ADR**：docs/adr/0007-s3-金控风险预警.md（重大方向变更必记）。
- **"外行 5 分钟看懂"目标检验**：找 1-2 个目标受众试看迭代（M4 末）。
- **压测**：M3 末保留 P95≤500ms（金融复杂查询验证）。

## 五、复核结论

四路模型一致认可：**S3 方向正确、技术底座扎实**（复用 S2 已验证机制）。分歧集中在**范围控制**（55→15-20 表）与**排期策略**（串行→垂直切片并行）。三个 P0 修正（选表标准/串行排期/禁止自动本体）+ 动作设计（2 个核心动作做深）+ 读/写引擎分离，修正后即可开工，不推翻总目标。
