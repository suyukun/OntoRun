# OntoRun S3 设计独立复核报告 — doubao-seed-2.1-turbo
> 复核人立场：15 年金科/风控系统架构 + 大模型语义接口落地经验。

## 一、3 条最强支持
1. **技术路径已被 S2 实证，金融场景是"换数据域"而非"换范式"**。核心命题（自然语言精准问答+业务动作执行）与 S2 完全同构：本体对象注册→契约 JSON→七道校验→语义接口执行→审计落盘。风险量级远低于 S1→S2。
2. **"外行 5 分钟看懂价值"直击当前最大痛点**。S2 证明"能做"不等于"有价值"，可感知价值密度才是核心指标。5 步 walkthrough 精准对应"从看到懂到信"。
3. **DES 标准化方向正确，是项目从"研究"走向"产品"的关键一跃**。表结构驱动+配置化生成=可快速适配任意行业，这是语义接口层真正的可复制性。借金控场景倒逼 DES 标准化，节奏合理。

## 二、3 条最强反对
### 反对 1（P0）：211 表→55 核心表的"选表"环节没有定义选表标准和验收方法
55 是拍脑袋估的。选表直接决定本体建模复杂度、可表达集覆盖度、演示说服力。追求全（55 表×20 字段=1100 概念）做不完；追求少（一问就超可表达集）演示翻车。
**改**：① 以演示剧本倒推表清单（先写 M4 的 5 步 walkthrough 问什么问题/做什么动作，再反推需要哪些表）；② 首版目标 15-20 张表足矣（贴源 8-10 核心实体表+应用层 3-5 指标表+决策引擎 2-3 规则表）；③ 表选择记 ADR。
### 反对 2（P1）："真实业务动作"设计完全空白，Jack 不懂业务是结构性风险
金控风控业务动作有标准流程（预警生成→人工确认→分派→处置措施→审批→执行→销号），每环节不同角色/权限/审批层级，状态依赖强。动作设计浅=外行一看就假；设计深=工程量是 S2 的 5-10 倍。
**改**：① 动作做深不做多——只做 2 个核心动作+完整状态链路（预警级别调整、处置单审批），做深（状态机完整/角色权限分明/审计可追溯）；② 借用人保/中信真实风控流程做参考（Jack 现成业务知识库）；③ 输出"风险预警业务动作说明书"（动作清单/状态机图/角色权限矩阵/审批规则）。
### 反对 3（P1）：M1-M4 严格串行是错误的排期策略
M1 与 M2 强依赖吗？不是（表结构一周内定，本体即可开工）。M3 与 M2 强依赖吗？部分。严格串行=把所有风险压在最后。S2 已证明本体建模是迭代式的。
**改**：① M1 拆 M1a（选表+脱敏+表结构确认，一周完成）和 M1b（DES 标准化+数据生成）；② M1a 完成后 M2 立即开工；③ M2 出第一版本体（3-5 核心对象）后 M3 立即开工；④ M4 前端与 M2/M3 完全并行（mock 数据开发）；⑤ 关键路径：M1a→M2↔M3→联调→M5，M1b/M4 非关键路径。

## 三、不确定
1. 211 表具体内容未知（决策引擎 91 张是什么概念？规则表/模型表/运行时表？）——看到数据字典前所有表数量判断都是推测。
2. 安平金控业务复杂度边界不清晰（聚焦银行+证券？还是六板块每表几行？后者数据很薄演示一问就空）。
3. "外行"定义不明确（领导看"有没有用"/风控人员看"准不准"/投资人看"能不能卖"）。
4. 火山 Coding Plan token 配额与上下文长度（金融提示词会变长）。
5. DuckDB 对金融复杂查询性能边界（集团多层关联/共债/跨板块汇总能否保持毫秒级）。

## 四、跨项检查
- M1-M5 无循环，但有不必要的串行依赖。
- M1 表驱动 vs M2 本体建模：不矛盾，但警惕"表驱动本体"变成"表=本体"。本体建模必须坚持业务对象视角（贴源层 cust_base_info/cust_risk_info/cust_contact_info 三表→一个 Customer 对象）。
- M3 精准路线 vs 真实动作：不冲突，但动作的"可动作集"需单独定义——可动作集内保证安全执行+域外明确拒绝。动作安全门槛比查询高得多。

## 五、过度设计/遗漏/违反原则
- 过度：55 张表过度设计（15-20 核心表+8-10 对象+2-3 动作足够）；DES 一步到位"标准化产品"过度（"自动本体建模"是研究级问题，留 S4/S5）。
- 遗漏：演示数据"故事性"设计缺失（安平金控要有具体风险事件让演示围绕故事线）；"拒答"场景演示价值没利用（fail-closed 在金融是巨大卖点，问一个答不了的问题展示明确拒答比答对 10 个更建立信任）；缺性能基线与压测计划（保留 P95≤500ms）。
- 违反"落地先行"：M2 先建模再验证，应先选 3-5 核心对象+2 动作跑通端到端（M2a）再迭代扩展（M2b）。
- 违反"研究对象锚定"：M4 每页必须能回答"这体现语义接口什么价值"（数据浏览页要展示本体驱动的自动 UI 生成）。

## 复核结论
方向正确、技术底座扎实，但排期策略（严格串行）和范围控制（55 张表、DES 一步到位）有明显问题。最大结构性风险是"业务动作设计空白"和"选表无标准"。调整后再开工。
