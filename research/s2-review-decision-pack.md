# S2 复核 · 4 项决策建议（Rose 基于 4 模型共识 + 证据，2026-08-21）

> 用途：目标④收尾——4 个决策点已由 4 模型对抗复核收敛为证据充分的推荐；Jack 可一键确认或否决。
> 原则：每条建议给"采纳则改什么 / 证据 / 反对理由是否成立"，不空谈。

## 决策 1：C1 量级目标——建议采纳"诚实降级 100GB-1TB 级"
- **建议**：S2 量级目标从"几百 TB~PB"诚实降级为 **100GB-1TB 级**（DuckDB 胜任），设量级 gate（100 万 / 1 亿行），PB 级留 S3（引分布式引擎）。
- **证据**：4 模型一致（pro F3/kimi/m3 F9-4/doubao）——DES 25 万行 vs PB 是 S2 最大叙事裂缝；SQLite 单机天然天花板在千万行级；DuckDB 100GB-1TB 级完全胜任，3 个数量级跨越（S1 123MB → 1TB）足以证明"量级"。
- **反对理由检验**：唯一反对可能是"要保持宏大叙事"，但 4 模型指出——**宣称验证做不到的 PB 级 = 虚假承诺，比诚实降级更伤可信度**（Jack 核心关切"不是花架子"）。反对不成立。
- **采纳影响**：议题清单 §0 目标措辞、DES 切片 R3、ChatBI 引擎选型叙事，均按 1TB 级对齐。

## 决策 2：D1 DES 技术栈——建议"核心数据生成用标准库，流程驱动 S2 不做"
- **建议**：S2 垂直切片（3 系统×1 表）**不需要流程仿真**（无需 SimPy）；"业务流程驱动数据生成"明确推迟 S3；若 S3 需要，用**成熟状态机库**（transitions）而非自研、也非 NetworkX（图库）。
- **证据**：m3 F9-3（业务流=状态机用现成库，不用图库）、doubao（流程驱动推 S3 或复用 SimPy）、kimi（砍掉后自研=重造轮子）——4 模型共识：S2 不该为流程仿真自研内核。
- **采纳影响**：DES 技术栈确认 = SQLite + 标准库 + pydantic（数据生成部分）；流程驱动从 S2 范围移除（进 backlog）；不引 SimPy/NetworkX（S2 不需要）。

## 决策 3：D2 方法论 UI——建议"S2 做最小指针版，推迟完整交互 UI 到 S3"
- **建议**：S2 方法论 UI = **"指针层"**（每步链到真实运行的命令输出 + git commit，不重做可视化）；完整交互 UI（绑定真实系统演示）推迟 S3 有真实案例后。
- **证据**：m3 F8-4（UI 只做指针，避免与未冻结代码脱节）、pro F7（S2 只展示已跑通阶段，诚实>完整）、doubao（S2 做完整 UI=过度设计）——综合三立场：**最小指针版是共识的交集**，既兑现"防数字盆景"承诺，又不排错优先级。
- **采纳影响**：议题 8 方法论三层中的"方法论交互 UI"标注为"S2 指针版 / S3 完整版"。

## 决策 4：D3 ChatBI 查询形态——建议"先定契约 + 先跑 head-to-head 实验，S2 用受限结构化查询"
- **建议**：① 采纳 DES 切片 §8 的结构化查询契约 v0.1（object_type/filters/aggregations/group_by/link_traversal）；② S2 垂直切片内跑 **head-to-head 实验**（30 个分析问题：NL2SQL+守卫 vs 受限结构化查询，量化成功率/延迟/成本/可控性）再定终版；③ 默认形态 = 受限结构化查询（LLM 产出、本地执行、引用本体注册对象/指标）。
- **证据**：pro F4（先定契约，否则下游全悬空）、m3 F1-1（受限 IR=自研查询语言，必须先实验验证）、doubao（别假装不写 SQL，用本体约束）——共识：**契约先定 + 实验验证**，这是三方的交集，不是任一方单点。
- **采纳影响**：ChatBI 形态 v2 补上"契约 v0.1 + 实验验证"环节；若实验证明受限 IR 表达力不足，20% 冷问题允许 LLM 生成经安全校验的 SQL（兜底）。
