
# S2 第一轮全量复核 · 汇聚分析（Rose 整理，交 Jack 拍板）

## 一、共识项（≥3 模型一致的重大发现）

### C1. 量级断层：DES 25 万行 vs ChatBI PB 级 是 S2 最大叙事裂缝
- pro(F3): DES 不是 PB 练兵场，量级验证根本没设计
- kimi: DES 量级声明与工具选型根本性错位
- m3(F9-4): 百万→亿→十亿过渡路径空白
- doubao(部分): SQLite 单表性能≠企业级
- **共识**：DES 无法验证 ChatBI 的 PB 级设计；需诚实降级 S2 量级目标（100GB-1TB 级，DuckDB 胜任）或另设量级 gate

### C2. "80% 自动 + 20% 人审"是拍脑袋数字，缺置信度阈值与验证闭环
- pro(F8): 无置信度模型/阈值/反查机制，80% 是拍脑袋
- kimi: 无标注数据集/基线实验，阈值是拍脑袋
- doubao: 真实数据实际自动率可能只有 20-30%
- m3(F2-1): 未定义阈值校准方法/ground truth 集
- **共识**：S2 先做"建议+全人工审核"，跑 1-2 个月数据后再定阈值；必须有映射变更影响分析

### C3. 权限"做在语义层"与 Palantir 实践矛盾 + 字段级权限在 SQLite 不可行
- pro(F9): 语义层无字段级强制执行点，字段级权限=遮值露名
- kimi: 语义层做数据权限与 Palantir 直接矛盾，性能差易绕过
- doubao: 权限在语义层=没有真正安全边界，绕过 API 直连库就裸奔
- m3(F3-2): 在本体层做是绕开而非解决
- **共识**：数据权限应下沉数据源（PostgreSQL RLS/DuckDB 视图）；S2 字段级权限降级为"对象级+属性级标注"；语义层只做操作权限+策略分发

### C4. 双引擎（SQLite+DuckDB）一致性/同步机制未定义
- kimi: 写回 SQLite vs 分析 DuckDB，同步机制（CDC/ETL/刷新）未定义
- m3(F1-3): 双引擎引两套方言，Decimal/时区/null 语义有差
- pro(F11): session 并发写前提未声明
- **共识**：定义 SQLite→DuckDB 数据流转契约 + reconcile 测试；显式声明 S2 单用户前提

### C5. 审计与会话耦合（#3 vs #4 重叠）+ TTL 30 天不合规
- doubao: 审计与会话同库=删会话删审计；审计需独立只追加+哈希校验
- m3(F4-1/4-2): TTL 30 天硬编码=合规定时炸弹；#3#4 审计重叠
- pro(F10): 双主体责任边界模糊，审计链断裂
- **共识**：审计独立模块（WORM 存储+动作级+字段级镜像），TTL 按数据分级，会话只管会话本身

### C6. 方法论"学位级"+"反模式 Top15"= 先写方法论再落地，违反铁律
- pro(F6): 反模式 Top15 在 S2 开工前拟定=先写方法论再落地
- kimi: 学位级野心与落地先行冲突
- m3(F8-2): 数字配额是反方法论，会凑数
- **共识**：方法论分两阶段——S2 只做白皮书 v2 骨架+方法论 UI（绑定真实运行），反模式从落地中事后提取

## 二、分歧项（模型间立场不同，需 Jack 拍板）

### D1. DES 技术栈：砍 SimPy/NetworkX vs 复用
- kimi: 砍掉后自研数据生成内核=重造轮子，应引 Faker/Mimesis/SimPy
- m3(F9-3): 业务流程驱动需状态机库（transitions），不用图库
- doubao: 复用 SimPy 或 S2 降级为"规则+分布采样"，流程驱动推 S3
- pro: 未直接反对砍，但 F2 指出 4 层 YAML 继承=自研配置引擎
- **分歧**：技术栈裁剪的边界（哪些算"研究本身"，哪些必须用成熟件）

### D2. 方法论 UI：S2 做 vs 推迟 S3
- doubao: S2 做方法论 UI=严重过度设计，推迟 S3
- pro(F7): S2 只展示已跑通阶段，UI 是差异化点
- m3(F8-4): UI 只做"指针"链到真实运行，不重做可视化
- **分歧**：方法论 UI 的优先级和形态

### D3. ChatBI 查询形态：受限结构化查询 vs 承认 LLM 写 SQL
- m3(F1-1): 受限 IR=自研查询语言，风险大，先做 head-to-head 对比实验
- doubao: "LLM 不写 SQL"只是多一层翻译，别假装
- pro(F4): 受限结构化查询 schema 未定义，先定契约
- **分歧**：ChatBI 核心查询形态是否继续"受限结构化查询"

## 三、P0 级风险（任一模型标 P0，需优先处理）

1. **量级断层**（C1）——S2 核心叙事裂缝
2. **映射 80% 拍脑袋**（C2）——S2 最核心工程挑战
3. **权限语义层承载 vs 数据源下沉**（C3）——可信根基
4. **受限结构化查询 schema 未定义**（D3）——ChatBI 核心契约缺失
5. **DuckDB 单机 vs PB 级**（C1 变体）——引擎选型与目标匹配
6. **审计独立 + 合规**（C5）——等保/个保/SOX 标准
7. **真实场景 #5 单点失败**（"待 Jack 提供"= 风险）——S2 唯一硬判据
