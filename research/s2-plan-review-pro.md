## 一、三条最强支持（为什么这个计划可行）

### 支持 1：DES 垂直切片优先 + 串行门禁 = 工程上正确的风险对冲

【输入】P1 是"最高风险项，最先做"，整条链路 DES→ChatBI→映射→权限→方法论串行，每阶段配可机验门禁。

【我方判断】这是 S1 经验（"落地先行"）的直接延续，且是工程上唯一正确的顺序：把最不确定的件（DES 数据质量/真实感）放在最前面，用最短路径（3 周切片）验证"穿得通"，穿不通就止损，穿通了再横向铺开。这对一个研究型项目至关重要——你在 S1 已经验证了"LLM 能通过语义接口写回"，S2 要验证的是"DES 造的数据经得起 ChatBI 挑刺"，先切片再全量是最优解。门禁的可机验性（SHA256 确定性、注入率 ±2%、P95 延迟、recall ≥80%、越权 0）也符合 AGENTS.md 铁律②。

### 支持 2：4 模型对抗复核已前置消化，计划不是"处女稿"

【输入】计划依据 S2 议题清单 v0.12（形态全定 + 复核共识 C1-C6），C1-C6 六项共识已并入。

【我方判断】这个计划已经经过一轮跨模型独立对抗——C1（量级降级 100GB-1TB）、C2（"80% 自动"改"全人工审后定阈值"）、C3（权限下沉数据源而非语义层）、C4（双引擎一致性需定义）、C5（审计独立 WORM）、C6（方法论反模式事后提取）——全都在计划里体现了。这不是"写完就拍板"的计划，而是"被四个人找过茬后改过一版"的计划。在工程交付中，经历过一次独立 red-team 的计划，存活率远高于初稿。C1-C6 的修正尤其关键：如果没有这轮复核，这个计划会在量级叙事、映射阈值、权限承载三个致命问题上直接翻车。

### 支持 3：技术选型克制——"不造轮子"纪律在计划中可追踪

【输入】DES 砍了 pandas/pyarrow/SimPy/NetworkX/Mimesis，只留 SQLite + 标准库 + pydantic；ChatBI 用 DuckDB（已装+已验证读 SQLite/物化）；权限不造轮子，复用 FastAPI 鉴权 + DuckDB RLS 扩展。

【我方判断】S1 的 WorkBuddy 复盘最大的教训就是"机制过载 + 造轮子成瘾"。S2 计划在技术选型上表现出罕见的克制：DES 明确砍掉了 5 个候选库，ChatBI 用成熟 DuckDB 而非自研分析引擎，权限复用现有框架。这种"能砍就砍"的纪律，在一个研究型项目中比"加什么"更难。且验证先行——DuckDB 读 SQLite 和物化聚合在计划编制前已实测通过（commit 7f4bfe8），不是"计划里假设能行"。

## 二、三条最强反对（最致命的问题）

### 反对 1：P1 产出数据量级与 P2 ChatBI 需求之间存在维度错配

**问题**：P1 DES 垂直切片产出约 200 行 MARA 物料主数据（3 系统×1 表），P2 ChatBI 需要跑"head-to-head 30 问成功率报告 + 物化查询 P95 延迟"。200 行数据跑不出有意义的 P95 延迟，30 个问题也撑不起一个 head-to-head 实验——你问来问去就是一物多码这一个主题。

**为什么致命**：P2 是 S2 的"读侧核心价值"，也是整个 S2 对外最有说服力的产出。如果 P2 的 head-to-head 实验因为数据不够而无法得出有统计意义的结论，S2 最有价值的论证就塌了。M2 里程碑判据"3 个真实分析问题答对 + 拒答率>0 + P95 达标"——200 行 MARA 数据上，P95 延迟测出来是毫秒级，完全无法外推到 100GB-1TB。

**怎么改**：P1 的垂直切片验证"穿通"后，P2 不应直接接在 P1 切片数据上。两个方案：(a) P1 切片后立即横向铺开 DES 到 10-20 表、至少 10 万行级，再进 P2——这需要把 P1 拆成 P1a（切片验证）+ P1b（批量铺开），P2 接 P1b；(b) P2 先复用 S1 的零售供应链数据（已有 2200 订单/300 客户/60 商品，可扩展到 10 万行级）做 head-to-head，DES 制造业数据单独验证"一物多码跨系统映射"——两条线不互相阻塞。

**优先级**：P0。这是 S2 核心价值论证的地基裂缝。

---

### 反对 2：P3（映射治理）排在 P2（ChatBI）之后是依赖倒置

**问题**：P3 的映射治理（分级置信度 + 审核工作台）是 ChatBI 查询质量的前提——映射不准，ChatBI 的 head-to-head 结果就不可信。但计划把 P3 排在 P2 之后：P2 依赖 P1 数据，P3 依赖 P1 数据 + P2 查询契约。这意味着 P2 跑 head-to-head 时，映射质量还没有经过审核工作台的验证。

**为什么致命**：P2 的 30 问 head-to-head 实验如果因为映射错误而得出"受限结构化查询不如 LLM 写 SQL"的结论，你无法区分是"映射没做好"还是"方案本身不行"。这在工程上是典型的"前置条件未满足就做结论性实验"——实验结论不可信，可能误导 D3 的最终决策。

**怎么改**：P3 的映射核心管道（至少 分级置信度 + 映射候选生成）必须与 P2 并行或前置。P2 的 head-to-head 实验应该跑在"经过映射审核"的数据上，而不是 P1 的原始映射。建议：P1 → P3（映射核心管道，不包含完整审核工作台 UI）→ P2（在已验证映射上跑 head-to-head）。审核工作台的完整 UI 可以推迟到 P3 后期或与 P4 并行。

**优先级**：P0。这会污染 S2 最重要的实验结论。

---

### 反对 3：P4（权限）排在 P1-P3 之后 = 架构级返工风险

**问题**：4 模型共识 C3 明确要求"数据权限下沉数据源（DuckDB 视图/RLS）"。但 P1 的 DES 数据设计（1 企业=1 目录，N 系统=N db 文件）和 P2 的 DuckDB 物化设计都在 P4 之前完成。如果在 P1/P2 阶段没有预留权限视图的架构接口，P4 时给数据层加权限可能需要重构 P1 的数据库布局和 P2 的物化管线。

**为什么致命**：权限是"可信"的根基，C3 共识的结论是权限不能后加——语义层做权限已经被判定为"没有真正安全边界"。如果 P1 的 SQLite 文件结构和 P2 的 DuckDB 物化表结构在设计时没有考虑"后续要挂 RLS/视图"，P4 阶段加权限就是外科手术式的返工。这不是"加个中间件"的事，是数据模型层的变更。

**怎么改**：P4 的权限模型设计（不是实现，是设计）必须前置到 P1 启动前或 P1 同期。具体：在 P1 的 DES 配置规范中预留"数据权限标注"（哪些表/列属于哪个权限域），在 P2 的物化表设计中预留视图分层。P4 的实现可以后置，但架构约束必须前置。这相当于在 P1 和 P2 的 DoD 里加一条："权限模型兼容性检查通过"。

**优先级**：P1。架构层面预留是低成本的事，返工是高成本的事。

## 三、不确定 / 需要更多信息

1. **D3（ChatBI 查询形态）是否已拍板？** 计划把 D3 列为"需 Jack 拍板"，但同时 P2 已按"契约 v0.1 + head-to-head"编排。如果 Jack 否决了受限结构化查询，P2 的范围会大幅变化。需要确认：Jack 是否已看过 decision-pack（commit a3599e1）并给出结论？

2. **#5 真实场景的状态。** 计划说"待 Jack 提供；缺则 DES 兜底"，但 4 模型共识把 #5 标为 P0 风险——"S2 唯一硬判据"。如果 DES 是唯一的"兜底"，那 S2 的"真实场景试用"判据实际上是 DES 的自洽验证，不是外部验证。这跟 S2 定位"经得起真实企业"有差距。需要 Jack 明确：是否有至少一个外部真实场景的候选？如果没有，S2 是否接受"DES 自验证 = 真实场景"？

3. **双引擎数据流转机制（C4）。** 计划提到 P1 用 SQLite、P2 用 DuckDB 物化，但 SQLite→DuckDB 的数据流转方式（实时 sqlite_scan vs 定时 ETL vs 事件触发刷新）未定义。DES 切片文档说 DuckDB 可直接读 SQLite，但那是针对静态切片——S2 的 ChatBI 如果在 P1 数据持续生成时查询，一致性怎么保证？需要明确：S2 的数据刷新模型是什么？

4. **S2 是单人还是多人？** 计划 §4 列出了 6 个角色（数据/架构/AI/后端/测试/产品），但实际执行者是谁？S1 的 130 commits 是 Rose 协调子代理完成的。S2 的 10.5 周如果是 6 人并行，是合理的；如果是 1 人 + 子代理，至少翻倍。需要确认：S2 的执行模式。

## 四、跨阶段依赖链检查

### 依赖图（按计划声明）

```
P1(DES切片) ──→ P2(ChatBI) ──→ P3(映射治理) ──→ P4(权限+会话+审计) ──→ P5(方法论+发布)

      └──→ D1 拍板    └──→ D3 拍板   └──→ P1数据+P2契约   └──→ C3采纳+前面各阶段
```

### 发现的问题

| 问题 | 严重性 | 说明 |
|---|---|---|
| **P2→P3 循环依赖** | P0 | P3 的映射质量影响 P2 的 head-to-head 结论，但 P3 排在 P2 之后（见反对 2） |
| **P4 架构约束后置** | P1 | P4 的权限下沉要求（C3）影响 P1/P2 的数据层设计，但 P4 排在 P3 之后（见反对 3） |
| **P1→P2 数据量级错配** | P0 | P1 切片产出不足以支撑 P2 的 30 问 head-to-head（见反对 1） |
| **P5 对 P1-P4 的全量依赖** | P2 | P5 需要"一条命令 E2E 全链路"，任何前序阶段延期都会推迟 tag v0.2.0。这本身不是问题，但 P5 的 2 周时间预算里包含了"全量复核"，如果 P1-P4 有返工，P5 会被挤占 |

### 建议的优化顺序

```
P0: D1/D3/#5 拍板（前置决策，不可跳过）
 ↓
P1a: DES 垂直切片（3 周，验证穿通）+ 同步输出权限模型设计（架构约束前置）
 ↓
P1b: DES 横向铺开（1-2 周，10-20 表，10 万行级）← 新增，为 P2 提供足够数据量
 ↓
P2+P3核心: ChatBI 头对头 + 映射核心管道（并行，3 周，在已验证映射上跑实验）
 ↓
P4: 权限+会话+审计（1.5 周，架构已预留，只做实现）
 ↓
P3完整: 审核工作台 UI（1 周，可以并行 P4 或 P5）
 ↓
P5: 方法论+发布（2 周）
```

关键变化：P1 拆成切片+铺开两段；P3 核心映射管道与 P2 并行；P4 权限设计前置但实现后置。总时长增加约 1-2 周，但消除了三个 P0 风险。

## 五、过度规划、遗漏、造轮子

### 该砍的（过度规划）

1. **"白皮书 v2 骨架（六阶段框架 + 十条铁律 + 反模式 Top15）"**——C6 共识已明确"反模式从落地后提取"，但计划仍保留"反模式 Top15"的措辞。建议砍掉"Top15"的数字配额，改为"反模式从 S2 落地中事后提取，数量不预设"。数字配额是反方法论——会让人凑数。

2. **"方法论指针版 UI（每一步展示输入/输出/为什么/在系统里怎么跑）"**——2 周内做一个"绑定真实运行系统"的交互式 UI 是过度设计。建议 P5 只做"静态指针"（每个方法论步骤链到对应的 git commit/测试输出/配置文件），完整交互 UI 推迟 S3。D2 分歧中 Rose 推荐的就是"指针版"，不要滑向"交互版"。

3. **P3 的"映射审核工作台（本体驱动 UI + 批量接受/拒绝 + 冲突标记 + 人工修正）"**——2 周内做一个完整的 React 审核工作台是乐观的。建议先做 CLI/CSV 驱动的审核流程（映射候选 → CSV → 人工标注 → 回写），UI 工作台推迟到 S3。这符合"不造轮子"铁律——审核工作流用已有工具，不急着做 UI。

### 遗漏的（该有没加）

1. **双引擎数据流转契约（C4 未关闭）**——4 模型共识 C4 明确要求"定义 SQLite→DuckDB 数据流转契约 + reconcile 测试"，但计划中 P2 只提到"DuckDB 物化"，没有定义刷新机制。这是 C4 的遗漏，需要在 P2 的 DoD 里加一条："SQLite→DuckDB 数据流转契约文档 + reconcile 测试通过"。

2. **写回债务的架构预留**——计划 §5 风险表说"写回债务（S2 搁置）显式记录，S3 补；架构预留"。但计划中没有说明"架构预留"具体指什么。S1 的写回回路（action_engine + audit + action_runs）是 S1 的核心资产，S2 搁置写回意味着这些模块在 S2 期间可能 bit-rot。需要：(a) 在 P2/P3 设计时预留"对象→动作"的语义接口（即使不实现），(b) S1 写回测试在 S2 每阶段末至少冒烟一次，防止回归。

3. **S1 测试回归门禁**——S2 五个阶段会对 src/ 做大量修改，S1 的 19 个测试文件是否在每个阶段末保持全绿？计划没有提到 S1 回归测试的策略。建议每个阶段的 DoD 加一条："S1 全量 pytest 零回归"。

4. **量级 gate 的具体设计**——计划提到"设量级 gate：100 万 / 1 亿行"，但没有说明 gate 的内容、怎么测、在哪个阶段测。这是 C1 共识的产物，但未落地。建议在 P2 的 DoD 中明确：100 万行级物化查询 P95 延迟 < X 秒，1 亿行级（如果 DuckDB 单机可达）P95 延迟 < Y 秒。

### 造轮子嫌疑

1. **"结构化查询契约 v0.1"（P2）**——D3 分歧的核心。4 模型中 m3 明确说"受限 IR = 自研查询语言，风险大"。虽然计划采纳了 Rose 的推荐（契约 v0.1 + head-to-head 实验），但需要警惕：如果 head-to-head 实验做完发现 LLM 写 SQL 更优，这个"结构化查询契约"就变成了自研 DSL 的死代码。建议 head-to-head 实验明确成功/失败判据，失败则果断放弃受限结构化查询。

2. **"映射自动化管道"（P3）**——builder 已有 mapping 模块（fk_detection/naming/alias_matcher/auto_map），P3 是扩展而非从零造。但需要确认：是否调研过现有的 schema-mapping 工具（如 OpenRefine、Valentine）？避免在已有成熟方案上自研。

## 六、三种真实执行中会死的方式

### 死法 1：死在 P1——DES 数据"不够真"，Jack 不验收，下游全堵

DES 的验收判据是"Jack 业务验收"——这是单点主观判据。MARA 物料主数据 + 一物多码在制造业是对的，但 Jack 的背景是金融/零售/智驾，不是制造业。如果 DES 生成的制造业数据在 Jack 看来"不像真实企业"，P1 就需要重做。重做 DES 意味着 P2-P5 全堵。C1-C6 共识救不了主观验收失败。

**【我方判断】这是 S2 最可能的死法。** 建议 P1 在开工前先让 Jack 看"北华线缆"的 YAML 配置示例 + 目标表结构，而非等 3 周后看成品数据。

### 死法 2：死在 P2——head-to-head 实验证明方案不行，ChatBI 推倒重来

P2 的 head-to-head 实验（30 问：受限结构化查询 vs LLM 写 SQL+守卫）是 S2 最关键的决策点。如果实验结果是"受限结构化查询在 30 问中成功率显著低于 LLM 写 SQL"，那 P2 的设计基础就塌了。这本身不是坏事——实验就是为了验证假设——但计划没有为"实验失败"准备 Plan B。如果 P2 的实验否定当前方案，D3 需要重新决策，S2 可能延期 3-4 周。

**【我方判断】这是第二可能的死法，但也是"好死"——实验否定了错误方向，比闷头做到底强。** 建议在 P2 计划中显式写：如果 head-to-head 失败，Plan B 是什么（直接采用 LLM 写 SQL + 多层守卫？退回 dbt 语义层？）

### 死法 3：死在 P4——权限需求膨胀，从"下沉数据源"变成"重做数据层"

C3 共识说"数据权限下沉数据源（DuckDB 视图/RLS）"。但如果在 P1-P3 各阶段中，数据模型一直在变（DES 加表、ChatBI 加物化视图、映射加字段），到 P4 时数据层已经是一张复杂的网。给这张网加权限视图，可能发现"某些查询路径无法用视图表达"或"RLS 策略与现有物化表冲突"，需要回改 P1-P3 的数据设计。这本质上是"架构约束后置"的代价（见反对 3）。

**【我方判断】这是最隐蔽的死法——不是死在某个阶段，而是死在"看起来都做完了，但权限一加就崩"。** 唯一的解法是权限模型设计前置（见反对 3 的修改建议）。
