# S2 v0.1 平衡复核 · Rose 视角

【输入】v0.1 草案已读完。基于 S1 基线（130 commits / 19 测试 / 三问过）+ 议题清单 v0.12 + DES 切片 v0.2，按你六问结构给平衡意见。先说结论：**大方向对、风险识别到位，但权限定位、映射依赖、统计样本量是三处会爆的雷**。下面逐项展开。

## 1. 三条最强支持

**① 风险排序正确：DES 切片（P1）置顶**
【我方判断】S2 最大的未知是"DES 数据真不真"，P1 用 3 周做最小可机验切片（SHA256 确定性 / 注入率 ±2% / 编码 100% / 跨系统可查），并把 Jack 业务验收写进门禁——这是从 S1 三问测试直接迁移的纪律。先解决最大未知再分兵,规避了"全栈铺开后才发现数据是假的"灾难。【输入】§2 P1 段。

**② 量级诚实降级 + 双档 gate**
【我方判断】从 PB 降到 100GB-1TB,且设"100 万 / 1 亿行"两档 gate,是工程上难得的诚实。DuckDB 在 1TB 内能 hold 住,但跳一档就要重做物化/分区策略——双档 gate 强迫每次升级都有数据支撑,避免"跑得动就当过关"。【输入】§0 + §2 P2。

**③ 写回债务显式记账 + S1 资产复用**
【我方判断】把"写回"显式列为 S3 补、并写"架构预留"——这是诚实的范围切割;S1 沉淀的 builder/mapping 被 P1 标"复用"——资产没浪费。【输入】§1 P1、§5 风险表。

## 2. 三条最强反对(最致命)

### 反对 1:P4 权限"沉到底"——结构性埋雷(P0)

- **问题**:权限模型 / 数据源 RLS / 审计 / 会话持久化全部塞在 P4(week 7.5–9)。
- **为什么致命**:【我方判断】P1 在用 SQLite + 1企业=1目录 N系统=N db 文件的形态生成 DES 数据时,如果不同时定权限元数据(租户隔离键、行级过滤维度、审计写入位),P2 一旦开始物化(多企业合并/分片/视图),P4 就只能在已建好的查询路径上打补丁——典型的"在桥修好后再补承重柱"。更要命的是"越权 0 发生"门禁到 P4 才验证,意味着 P1–P3 跑出的所有数据**全部假设无权限边界**,回溯成本巨大。【输入】§2 P4。
- **怎么改**:
  - 拆出 **P1.5(权限骨架 0.5 周)**:仅做权限元数据 schema + DES 生成器写入位 + 一条只读 RLS 演示用例,不做 UI/审计完整实现;
  - P4 只做"完善 + 自动化审计 + 会话持久化",不再是设计阶段;
  - 或把 P4 前置到 P2.5,但 P1.5 更轻。

### 反对 2:P2 head-to-head / P3 ground truth 样本量过小 + 统计无靶(P0)

- **问题**:head-to-head 30 问 + ground truth "50 问题×3 域",都没有成功率靶值、统计检验、置信区间。
- **为什么致命**:【我方判断】30 问连一个 95% 置信区间都撑不起,pass/fail 会被一次问法改变结论;50 问×3 域 = 150 条样本人工标注,若 Jack 不提供 #5 真实场景,标注只能由 Rose 子代理做,**人审 + 人标同时存在 = 评估者偏差嵌套**。这会让 P2/P3 的"成功"变成政治判断,不是工程判断。【输入】§2 P2/P3 门禁、§5 #5 风险。
- **怎么改**:
  - 显式定 head-to-head 成功率靶值(如 baseline LLM 直查 ≥X% / 本体版 ≥Y% / Δ≥Z 个百分点),写进 M2;
  - ground truth 扩到 ≥300 问/域,标注者至少 2 人 + 仲裁;
  - #5 不来则改用 DES 兜底时,**标注协议 + 评估者盲测**强制列入门禁(避免"我自己标自己测")。

### 反对 3:P2 ↔ P3 映射依赖倒挂(P0)

- **问题**:P2 head-to-head 依赖映射质量,但 P3 才建映射自动化管道。
- **为什么致命**:【我方判断】P2 跑出来的"本体版 vs 直查版"对比,本质是在**手工映射**上做的;P3 用同一份 head-to-head 数据再跑一次,会发现自动化映射达不到 P2 时的手工质量——这是结构性的,不是工程细节。P3 的"先全人工审积累数据"对策也承认了这点,但把人工审推到 P3 = P2 阶段的"成功"无法保证可复现,P2/P3 之间的 DoD 会出现证据断层。【输入】§2 P2/P3 依赖、§5 风险表"映射 recall 不达标"。
- **怎么改**:
  - 把"映射置信度打标 + 人工审核痕迹"骨架挪到 P1 末(仅骨架,不做自动化);
  - P2 head-to-head 输出**两份数据**:手工映射版 + 自动化初版(哪怕自动化只有规则),作为 P3 起点;
  - P3 门禁改成"自动化映射在 head-to-head 上对人工版的 recall ≥X%"——把 P2→P3 的证据链显式化。

## 4. 跨阶段检查

**依赖链**:P1→P2→P3→P4→P5 严格串行,**无循环**,但**有两处断裂风险**:

- **P1→P2 断裂点**:P1 门禁只验 MARA 类确定性,**没验"DES 数据在 ChatBI 查询下是否真得像"**。需要补一个"数据可信度"gate,由 Jack 或 #5 真实场景出题。
- **P3→P4 断裂点**:P3 mapping 自动化假设审计落库格式稳定,但 P4 的 WORM + 动作级审计格式未定——P3 写完 P4 改了,等于 P3 返工。

**阶段顺序**:
- P1 第一 ✓(最大未知先验证)
- P4 应该提到 P1.5(见反对 1)
- P5 不应整体压到末尾:方法论骨架(六阶段框架名)应**在 P1 开工前定稿**,落地时只填血肉;否则 P5 重写框架是大概率事件。
- 缺一个 **P0.5 / P1.5 治理骨架**(权限 + 审计 + 映射置信度的最小可机验骨架),把"治理"从 P3/P4 末段前移,避免后期补丁式返工。

## 5. 过度规划 / 遗漏 / 造轮

**过度规划(可砍)**:

- M1–M4 里程碑表与 P1–P5 一一对应,**冗余**——把 P1–P5 的门禁直接当 DoD 即可,M 表删除或合并到 §3。
- 6 角色派活表:当前是 Rose 一人公司,**表里的角色名就是责任范围**,写成"职责矩阵"而不是"派活表"更诚实,避免给"会有专人"的错觉。
- §6 前置清单中"建 S2 goal"和"切新窗口"是流程动作,不是计划内容;放这里只是凑数。

**遗漏(该有没加)**:

- **rollback 计划**:每个阶段失败如何退?P1 不通过是重做还是降级?没有。
- **性能基准协议**:P95 延迟达标——靶值多少?在哪个数据集上测?没说。
- **可观测性**:P4 有审计但无 metrics/tracing/logging,100GB-1TB 规模生产必需。
- **数据安全 / PII**:DES 模拟数据有客户、订单、金额,**生产标准下 PII 脱敏 + 字段级加密**没说。
- **编码 / 本地化**:北华线缆是中文,编码(GBK/UTF-8)、中文分词、字段长度是真实生产坑。S1 可能没踩到,S2 量级一上来必踩。
- **embeddings / 向量检索**:本体驱动查询是否引入向量召回?还是纯规则?S2 量级下纯规则的扩展性是个隐藏天花板。
- **CI/CD**:AGENTS.md 写 P6 前不建 CI,但 S2 跨度 10.5 周无 CI 的话,回归风险全压在 Rose 阶段末全量 pytest——与"零到一档"纪律可兼容,但**生产跨越**标签下值得重新评估。
- **写回执行路径**:S2 写回债务划给 S3,但 M1 写"全程审计"——审计是写回的一部分还是只读侧审计?语义不明。

**造轮**:

- **WORM 审计**:S3 Object Lock / immudb / 国产瀚高 / 麒麟 append-only 都有,自建风险高、审计合规认不认另说。
- **受限结构化查询**:直接用 sqlglot(解析/AST 化/参数化)做 SQL 安全网,不要从零写 parser。S1 如果有现成则保留。
- **会话持久化**:SQLite OK,但 TTL 分级 + 多设备同步如果要复杂,**直接用 Redis / KeyDB** 比自建 TTL 调度省 0.5 周。
- **head-to-head 实验框架**:自己写评估器没问题,但标注协作如果上 2 人以上,**Label Studio 比自建快 2 倍**且可审计。

## 6. 计划在真实执行中死在哪三处

1. **死在 P0 → P1 之间**:【我方判断】5 项决策(尤其 #5 真实场景)卡 2 周,主线程无活可干;切新窗口后子代理无目标 → 上下文轮换收益归零,S2 实际启动比计划晚 3 周。
2. **死在 P1 → P2 验收**:【我方判断】DES 数据合成通过机验门禁,但 Jack 业务验收不通过("这就是个模板数据"),P1 重做数据模型,3 周变 5 周,P2 启动连带顺延,10.5 周计划膨胀到 14 周。
3. **死在 P3 → P4 之间**:【我方判断】mapping 自动化在 300 问 ground truth 上 recall < 60%,P3 延长 1 周仍不达标;P4 开工时数据形态已变(WORM 写入位/审计格式随 P3 改),P4 实际工作量翻倍,最终 M3 至少延 2 周,**S2 砍掉 P5 UI 一半范围保发布**。
