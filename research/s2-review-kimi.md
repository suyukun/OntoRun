# OntoRun S2 对抗复核报告

**复核者视角**：企业数据架构，15 年落地经验。  
**原则**：只找问题，不赞。每条 = 问题 / 为什么是问题 / 怎么改 / 优先级。

---

## 一、逐议题 findings

### A 档

#### #9 DES 真实企业生成工具

**P0 问题：量级声明与工具选型根本性错位。**  
S2 宣称目标是“玩具→生产跨越（几百 TB~PB）”，但 DES 选型是 SQLite + Python 标准库 + pydantic，1 企业 = 1 SQLite 库，最小垂直切片是“1 表+1 问题+1 映射”。SQLite 单库在 TB 级即进入不可服务区，PB 级更是无从谈起。  
**Why**：SQLite 是单文件、单 writer、无分布式执行引擎，不是“先小后大”的缩放问题，而是架构天花板问题。DES 如果作为 PB 路径的起点，必须从第一天就支持分片/分区/列存/批量导出。  
**Fix**：把 DES 定位从“生成工具”改为“企业 schema + 数据契约定义器”，数据实体用 Parquet/ORC 分区输出到对象存储；保留 SQLite 仅作本地 quick-start。  
**Priority**：P0。

**P1 问题：砍掉了 pandas/pyarrow/SimPy/NetworkX/Mimesis，却在自研数据生成内核。**  
Rose 声明“不造轮子铁律”，但 DES 要实现“业务流程驱动数据生成 + 多系统按系统生成 + 问题注入”，这些正是 Mimesis/SimPy/NetworkX 解决的领域。砍掉后意味着用 Python 标准库重写时间序列、网络关系、分布采样。  
**Why**：这是典型的“为了轻量而重造”。标准库没有企业级合成数据能力，结果大概率写出脆弱、不可配置的生成脚本。  
**Fix**：引入 Faker/Mimesis 做基础分布，SimPy 可选做流程驱动，用 pyarrow 写 Parquet；只自研“本体映射”这一研究核心。  
**Priority**：P1。

**P0 问题：“真实企业”的验证标准缺失。**  
“接近真实企业数字画像”没有可量化判据。什么叫“真实”？行业分布是否符合国家统计局？表间外键一致率？业务流程覆盖度？  
**Why**：没有验收标准，DES 会变成“看起来真实”的玩具数据，导致下游 ChatBI 和治理结论不可信。  
**Fix**：定义可机验指标（主键唯一率 100%、外键引用完整率 ≥99%、业务规则通过率、与公开行业基准分布的 KS 距离等），并写进 CI。  
**Priority**：P0。

#### #1 ChatBI 智能分析

**P0 问题：DuckDB 与 PB 级目标冲突。**  
DuckDB 是单节点嵌入式 OLAP，适合 GB~TB 级本地分析。PB 级需要分布式查询引擎（Spark/Trino/ClickHouse/Doris）。  
**Why**：S2 同时说“几百 TB~PB”和“分析引擎=DuckDB”，这是互斥的。 DuckDB 可以作开发/测试/轻分析，不能作为生产级 PB 架构的“分析引擎”。  
**Fix**：明确 DuckDB 为 S2 本地原型引擎，生产路径另选分布式引擎；或把 S2 目标 honest 地降到“TB 级企业原型”。  
**Priority**：P0。

**P1 问题：“预聚合优先”与 ChatBI 的探索性本质矛盾。**  
预聚合要求预先知道指标定义和维度组合；ChatBI 的核心价值是 ad-hoc 提问，大量问题无法命中预聚合。  
**Why**：如果所有指标都要先物化，ChatBI 退化为“预定义指标查询器”，不是智能分析。LLM 把自然语言映射到受限结构化查询，但受限查询若只能查预聚合，则无法回答“未注册指标”的问题。  
**Fix**：分两层——热指标走预聚合（DuckDB/数仓），冷/探索性问题走受限 SQL 或 LLM→SQL 在可控数据子集上执行；引入查询成本/超时限制。  
**Priority**：P1。

**P1 问题：双引擎（SQLite 写回层 + DuckDB 分析层）一致性未定义。**  
动作写回 SQLite，分析查 DuckDB，二者如何同步？CDC？定时 ETL？物化视图刷新策略？  
**Why**：没有同步机制，ChatBI 会读到脏数据，动作执行会基于 stale 状态做决策。  
**Fix**：显式定义数据流：SQLite → DuckDB 的增量同步机制（如 duckdb 直接 attach SQLite 做定期 refresh，或引入更可靠的 CDC）；写回动作必须触发分析层失效/刷新。  
**Priority**：P1。

#### #8 本体论落地方法论

**P0 问题：方法论主张与 S2 系统能力出现断层。**  
方法论写“Action 写回是闭环关键”，但 S2 搁置写回、先做 ChatBI。  
**Why**：这不仅是“北极星 vs 当前能力”的坦诚记录，而是动摇了项目核心论点——“大模型要操作企业，必须先有现实世界的语义层当接口”。如果 S2 不做写回，就无法证明语义层能支撑操作闭环，方法论成了无根之水。  
**Fix**：要么 S2 保留最小写回切片（1~2 个动作），要么方法论白皮书把“写回”降级为远期主张，并诚实说明 S2 不验证此主张。  
**Priority**：P0。

**P1 问题：方法论“学位级作品”野心与落地先行的原则冲突。**  
AGENTS.md 铁律是“落地先行，方法论从闭环里长出来；禁止先写方法论再落地”。#8 却规划了六阶段、十条铁律、反模式 Top15、十个开放张力点。  
**Why**：过早体系化会导致方法论变成文献综述，而非从真实问题中提炼。  
**Fix**：S2 只记录已验证的决策和失败案例；未验证的张力点标记为“待验证假设”，不写入正式方法论。  
**Priority**：P1。

### B 档

#### #2 对象/动作规模化治理

**P0 问题：“80% 自动 + 20% 人审”是拍脑袋数字。**  
没有标注数据集、没有基线实验、没有业务领域验证，无法确定 80% 阈值。  
**Why**：高置信度自动过的误判风险无法量化；阈值设置过高则人工负担重，过低则质量崩。  
**Fix**：建立映射质量闭环——自动推断 → 人工标注采样 → 计算 precision/recall → 按业务可接受风险设定阈值；阈值必须可配置、可审计。  
**Priority**：P0。

**P1 问题：映射审核工作台与数据血缘能力脱节。**  
#2 提到“冲突标记 + 审核痕迹”，但没有数据血缘（设计包未把 Palantir lineage 映射为自有能力），无法回答“改这个映射会影响哪些指标/动作/报表”。  
**Why**：没有血缘，映射变更就是盲改，真实企业不敢接受。  
**Fix**：把 lineage 纳入 S2 最小集，至少实现“对象/指标 → 源表/字段 → 下游动作/查询”的依赖图。  
**Priority**：P1。

#### #3 权限/鉴权

**P0 问题：语义层承载对象级/属性级数据权限，与 Palantir 实践直接矛盾。**  
Palantir security 文档明确：“Ontology 角色挂对象/链接/操作类型控编辑配置，不给数据权限，数据权限仍在数据源”。OntoRun 却设计“权限做在语义接口层（本体对象/链接/动作挂权限策略），不依赖数据库层”。  
**Why**：在语义层做数据权限，意味着每次查询都要在应用层过滤，无法利用数据库索引/视图/RLS，性能差、审计分散、容易绕过。  
**Fix**：数据权限下沉到数据源（PostgreSQL RLS、DuckDB 受限视图、数仓行级策略）；语义层只负责“操作权限/编辑配置”和策略分发。  
**Priority**：P0。

**P1 问题：双主体（Agent + 人审核）的权限边界模糊。**  
Agent 能做什么？人审能覆盖/阻止什么？Agent 的 token 代表谁？写回动作以哪个主体的身份审计？  
**Why**：双主体如果没有清晰的 identity 模型，审计链无法追责。  
**Fix**：引入服务账号 + 用户委托模型；Agent 操作挂用户身份 + Agent 实例 ID；人审动作必须显式签名。  
**Priority**：P1。

**P2 问题：列级权限在 SQLite/DuckDB 支持有限，却被列为 S2 目标。**  
SQLite 无原生列级权限；DuckDB rls 扩展能力有限。  
**Why**：目标与工具能力不匹配。  
**Fix**：S2 先做对象级 + 行级权限，列级放发布期；或换支持列级 ACL 的数据源。  
**Priority**：P2。

---

#### #4 会话持久化

**P1 问题：SQLite 单表会话与 PB/生产目标不匹配。**  
30 天 TTL、单表、无分片，无法支撑多用户并发会话。  
**Why**：会话表会成为写热点和查询瓶颈；TTL 过期数据需要 vacuum，否则文件膨胀。  
**Fix**：S2 用 SQLite 足够，但需声明为本地原型；生产路径必须引入专用会话存储（PostgreSQL/Redis/OLAP 审计库）。  
**Priority**：P1。

**P1 问题：会话 id “串审计”缺少完整性保证。**  
“会话 id 串审计”没有说明如何防止篡改、如何与动作审计关联、如何保证时序一致性。  
**Why**：审计链如果不防篡改，合规不可接受。  
**Fix**：每条审计记录包含前一条哈希（类似日志链），或写入只追加存储；会话与动作审计通过 correlation id 关联。  
**Priority**：P1。

### C 档

#### #5 真实场景试用

**P0 问题：DES 先行、真实后迁是逃避关键假设验证。**  
S2 硬判据是“待 Jack 提供真实场景”，但如果没有真实场景，S2 结束后无法证明设计对企业有用。  
**Why**：研究“大模型如何嵌入真实业务系统”却用合成数据跑完全程，结论外部效度极低。  
**Fix**：把“获取 1 个真实业务场景”设为 S2 入口条件，而非待决项；若无法获取，S2 目标应降级为“合成企业验证架构可行性”。  
**Priority**：P0。

---

#### #6 CI + UX

**P2 问题：CI “权限确认后真跑”缺少安全策略。**  
“真跑”意味着 CI 会接触 LLM key、数据库、外部服务；但没有说明 secrets 管理、成本上限、沙箱隔离。  
**Why**：CI 真跑容易导致 key 泄漏、账单爆炸、测试数据污染。  
**Fix**：CI 分阶段——lint/unit 真跑，E2E 用 mock LLM + 本地 SQLite；只有发布门禁才用真实 key，且需审批 + 预算告警。  
**Priority**：P2。

---

#### #7 一键起

**P2 问题：`scripts/start_dev.sh` 读 credentials 的 key 启动，安全面过宽。**  
脚本直接读 key 起前后端，没有说明 key 存储位置、权限、是否打印日志。  
**Why**：开发便利容易牺牲安全，key 可能进入 shell history、日志、Docker 层。  
**Fix**：强制通过环境变量或本地密钥管理（如 1Password CLI / doppler）注入；脚本不触碰 credentials 文件。  
**Priority**：P2。

## 二、跨议题矛盾

| 矛盾双方 | 问题 | 修复建议 | 优先级 |
|---|---|---|---|
| **#9 DES（SQLite） vs #1 ChatBI（PB）** | 数据生成在 SQLite，分析目标 PB，中间无迁移桥 | DES 输出改为分区 Parquet；SQLite 仅 quick-start | P0 |
| **#8 方法论（写回是关键） vs #1/#5（S2 不做写回）** | 核心论点在 S2 无法验证 | S2 保留最小写回切片，或方法论降级 | P0 |
| **#3 语义层权限 vs Palantir 数据权限在数据源** | 复刻 Palantir 却说反其道 | 数据权限下沉，语义层只做操作权限 | P0 |
| **#1 预聚合优先 vs ChatBI ad-hoc 探索** | 预聚合无法覆盖未注册问题 | 热指标预聚合 + 冷查询受限 SQL/成本限制 | P1 |
| **#2 映射自动化 80% vs 无标注/无基线** | 阈值无依据 | 建立标注-评估-阈值调整闭环 | P0 |
| **#4 会话 SQLite vs #1 PB 生产** | 会话层无法扩展 | 声明 SQLite 为原型，生产引入专用存储 | P1 |

## 三、不造轮子违反处

1. **DES 数据生成内核**：砍掉 Mimesis/SimPy/NetworkX 后用标准库重写，实质自研合成数据引擎。→ 引入成熟合成数据/流程仿真库。
2. **权限模型**：语义层数据权限是自研，而业界成熟方案（DB RLS、Palantir 数据源权限）已被验证。→ 数据权限下沉。
3. **映射自动化工作台**：没有利用现有数据血缘/Schema 匹配工具（如 Amundsen、DataHub、Deequ）。→ 先集成开源血缘与数据质量工具，只自研本体映射决策层。

## 四、部署死亡风险（真实落地会在哪里暴雷）

1. **DuckDB 撑不住真实企业数据量，S2 结束后发现无法迁移。**  
   风险：投入一年后，发现 DuckDB 架构无法平滑升迁至分布式引擎，被迫重写。→ 现在就要定义生产引擎候选和迁移路径。

2. **语义层权限成为性能与合规黑洞。**  
   风险：应用层过滤导致大表查询超时；审计分散无法满足金融/零售合规；数据绕过语义层直接查库即失控。→ 数据权限必须下沉。

3. **映射自动化 80% 阈值在真实数据上崩塌。**  
   风险：自动过的低质量映射产生错误指标和动作，人工审核队列爆炸，业务方失去信任。→ 必须有标注基线和可调整阈值。

4. **没有真实场景，S2 成果无法外推。**  
   风险：DES 数据再漂亮，也只是“玩具企业”，论文/产品/方法论都缺乏说服力。→ 把真实场景获取设为 S2 入口条件。

5. **写回被搁置导致核心论点悬置。**  
   风险：S2 结束时只能演示“查指标”，无法演示“LLM 操作企业”，项目失去差异化价值。→ 即使最小化，也必须保留一条写回闭环。

---

**总结**：S2 在“玩具→生产跨越”的口号下，实际仍停留在玩具架构（SQLite + DuckDB + 自研生成器）。最危险的不是某个技术选型，而是**量级目标、核心论点、落地验证三者互相脱节**。若不收敛到诚实可验证的范围，S2 大概率会产出一份漂亮但不可迁移的方法论和一组只能在演示环境运行的代码。
