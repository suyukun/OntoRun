# S2 开发计划平衡复核 v0.1

> 角色：资深工程程序负责人（15 年数据平台经验）｜ 性质：对抗性平衡评估（非纯赞、非纯挑错）

---

## 一、三条最强支持（这个计划为什么行）

**支持 1：风险前置的阶段顺序——最高风险项最先碰**

【输入】P1 阶段做 DES 垂直切片（≈3 周），标注为"最高风险项，最先做"；风险表中 DES 质量（真实感）列为高风险。
【我方判断】这是整个计划最扎实的决策。从 S1 的 8 对象玩具数据跳到几十个对象的真实企业级数据，数据真实性和结构复杂度是最大的不确定项。把 DES 切片放在第一阶段，意味着如果数据基建跑不通，三周就止损，而不是等做了 ChatBI 和治理才发现地基有问题。这符合"验证先行"的工程哲学，也与项目 AGENTS.md 中"先跑通最小闭环"的铁律一致。

**支持 2：全阶段可机验门禁——软目标全部量化**

【输入】每个阶段都配了可机验门禁：P1 的 SHA256 确定性、一物多码注入率 ±2%、编码规则 100%；P2 的 head-to-head 30 问成功率、P95 延迟、拒答率；P3 的 top-5 recall ≥80%；P4 的越权 0 发生。
【我方判断】这是计划的第二大优点。大部分项目计划的问题是"做完了但不知道算不算做完"，而这个计划每一步都有可量化、可自动化验证的出口条件。这恰好命中项目 AGENTS.md 中"规则必须能机器验证"的铁律。门禁不是装饰——它强制每个阶段交付真实可运行的产物，而不是文档或 PPT。

**支持 3：诚实的范围裁剪——降级和搁置都明明白白**

【输入】量级从 PB 诚实降级到 100GB-1TB（"诚实降级自 PB，DuckDB 胜任"）；方法论 UI 做 S2 指针版而非完整版；写回债务显式搁置到 S3，架构预留。
【我方判断】敢于降级比敢于加码更难。很多项目的死法是目标膨胀、什么都想做、什么都做不透。这个计划有三个明确的"不做"：不做 PB 级、不做完整方法论 UI、不做写回。每个不做都有理由和后续安排（S3 补、架构预留）。这种范围纪律是研究项目能活过第二个阶段的关键。

## 二、三条最强反对（最致命的问题）

### 反对 1：阶段顺序倒挂——ChatBI 建在未治理的映射上（P0）

**问题**：P2（ChatBI 最小闭环）在 P3（映射治理 + 审核工作台）之前，但 ChatBI 的语义层质量直接取决于映射质量。
**为什么**：【输入】P2 门禁是 head-to-head 30 问成功率，但这些问题的答案质量依赖于本体到物理表的映射是否准确。P3 才做分级置信度和人工审核，意味着 P2 的 30 问是在"未经治理的映射"上跑的。如果 P3 发现映射架构有根本性问题（比如置信度分级方式不对、跨系统映射的歧义无法消解），P2 建好的语义层和物化管线要返工。而且 P2 产出的"查询契约"会作为 P3 的依赖输入，但这个契约本身是建立在未经验证的映射之上的——相当于先画靶再射箭。
**怎么改**：把 P3 拆成两部分——映射数据模型 + 置信度分级 schema 前置到 P1 末尾/ P2 开头（与 ChatBI 语义层设计并行），审核工作台 UI 留在 P3。至少确保 P2 的语义层是基于一个已经过审视的映射治理框架来建的，而不是事后补。
**优先级**：P0——架构级返工风险。

### 反对 2：DuckDB 规模化未经过实际工作负载验证（P0）

**问题**：计划假设 DuckDB 能胜任 100GB-1TB / 1 亿行级别，但验证仅停留在"已验证读 SQLite/物化/parquet"的连通性层面。
**为什么**：【输入】S1 只有 123MB。从 123MB 到 100GB 是三个数量级的跳跃。DuckDB 在单表大查询上很强，但 OntoRun 的查询模式是**本体驱动的多系统跨库 join + 动态物化 + 语义层转换**——这不是 DuckDB 的典型 sweet spot。特别是"1 企业=1 目录 N 系统=N db 文件"的架构，跨 N 个 SQLite 文件做 join 在 1 亿行规模下的内存行为和性能是未知的。如果 P2 做到一半发现 DuckDB 内存爆了、或者物化时间从秒级跳到小时级，整个技术栈要重选，P2-P4 全部作废。
**怎么改**：在 P1 阶段末尾加一个"量级压力测试门禁"——用 DES 生成 1000 万行规模的数据，跑 5 个代表性的本体查询（跨系统 join、聚合、过滤、链路查询各一），测 P95 延迟和内存峰值。不达标就提前切换方案（比如换 PostgreSQL + Citus，或者 DuckDB + 外部 Parquet 分区），不要等 P2 中期才发现。
**优先级**：P0——技术选型赌命级风险。

### 反对 3："真实场景"缺失被手挥掉，但它是 S2 的核心价值锚点（P1）

**问题**：风险表中"#5 真实场景缺"被列为高风险，但对策是"DES 兜底，不阻塞主线程"——等于没解决。
**为什么**：【输入】S2 的定位是"玩具→生产跨越"。DES 合成数据本身就是"玩具"的升级版，不是"生产"。如果没有真实场景（Jack 提供的真实企业数据或真实业务问题），S2 从头到尾都是在用自己造的数据验证自己造的系统——循环论证。head-to-head 30 问在合成数据上成功率可能很高，但合成数据的模式是 DES 生成规则决定的，LLM 很可能学到的是 DES 的生成规律而不是真实业务语义。到发布的时候，没有人能区分 S2 和 S1 的本质区别——只是"数据更多了、界面更花了"，研究价值大打折扣。
**怎么改**：把"真实场景确认"从"前置决策"升级为"P1 门禁的一部分"。P1 结束时如果还没有真实场景，要么降级 S2 目标为"DES 规模化验证"（坦诚这还是玩具），要么停一下等场景——而不是假装 DES 兜底等于生产跨越。
**优先级**：P1——不致命但会让整个 S2 的叙事空心化。

## 三、不确定 / 需要更多信息

1. **团队实际产能未知**。计划列了 6 个角色但没说几个人、多少投入度。10.5 周 × 6 角色可能是 63 人周，也可能是 1 个人戴 6 顶帽子（10.5 人周）——后者的话计划时间要翻 3-4 倍。
2. **S1 映射基线不明**。S1 的 8 对象映射是规则写死的还是 LLM 生成的？baseline recall 是多少？没有基线，P3 的 80% recall 目标就是拍脑袋——可能太容易（没有挑战性）也可能太难（根本达不到）。
3. **"几十个对象"的具体数字模糊**。20 个和 80 个是完全不同的规模。"几十个"这个颗粒度不足以评估工作量和风险。
4. **写回搁置对"生产跨越"叙事的影响**。S1 的核心创新是 LLM 经语义接口写回源系统。S2 搁置写回，那"生产"的含义就只剩读侧了——这算不算"跨越"，需要明确定义。
5. **指针版 UI 的边界不清**。"指针版"具体指什么——只有导航链接？只读视图？能做什么不能做什么？这直接影响 P5 的工作量评估。

## 四、跨阶段检查

**依赖链（无循环）**：P1 → P2 → P3 → P4 → P5，串行清晰，无循环依赖。

**隐藏断裂**：
- P2 → P3 之间有**反向隐式依赖**：P2 的 ChatBI 语义层设计会隐含地假设映射的置信度模型、错误处理方式，但这些是 P3 才定义的。如果 P3 的映射框架和 P2 的假设不兼容，语义层要重写。
- P4 依赖"C3 采纳（权限下沉）"，但 C3 不在前置决策表中——是笔误还是遗漏？需要确认 C3 的内容和拍板时间点。

**阶段顺序是否最优？** 【我方判断】大体方向对，但有两个可优化点：

1. **P3 的映射数据模型应前置**（见反对 1）——不是整个 P3 提前，而是"映射 schema + 置信度分级 + ground truth 标注规范"这部分提前到 P1 结束后、P2 开始前，作为 P2 的设计输入。
2. **P4 的审计模块 schema 可以与 P3 并行启动**。审计是跨切面的，数据模型设计不依赖映射治理的最终形态，可以在 P3 做审核工作台的时候并行做审计模块的数据结构和基础 API，P4 再集成权限。这样 P4 的 1.5 周可能压缩到 1 周。

## 五、过度规划 / 遗漏 / 重复造轮子

### 过度规划（该砍）
- **方法论白皮书 v2 "六阶段框架"**：S2 才 v0.2.0，还在研究阶段，就出六阶段框架？框架是从多个项目/多个企业提炼出来的，不是一个 S2 就能撑起来的。建议改成"S2 落地笔记 / 观察与反模式"，诚实记录做了什么、踩了什么坑，不要硬凑成"方法论框架"。
- **完整的审核工作台 UI**：计划说"轻人工审核（先全人工审）"，全人工审阶段用 CLI 或简单表单就够了，做一个完整工作台页面投入产出比太低。建议 P3 先做 CLI/API 级审核流程，UI 留到 S3 确有需求再做。

### 遗漏（该有没加）
- **可观测性（监控/日志/追踪）**：100GB-1TB 规模 + LLM 调用 + 语义层转换，没有 metrics、tracing、结构化日志，出了问题根本不知道卡在哪。至少要加一个"查询链路追踪"的最小方案。
- **LLM 成本模型**：head-to-head 实验、生产查询都要花钱。没有成本预算、没有单次查询成本上限、没有低成本模型 fallback 策略——可能跑着跑着账单爆了。
- **S1 → S2 迁移策略**：S1 有 19 个测试文件、8 个 src 包、130 个 commits。S2 是在 S1 上演进还是另起炉灶？测试怎么迁移？本体定义怎么扩？没有迁移计划，容易出现"推倒重来"的隐性成本。
- **性能基线定义**："物化查询 P95 延迟"——在什么硬件上？多大数据量？什么查询 mix？没有这些定义，门禁就是空的。

### 重复造轮子
- **会话 SQLite 持久化（TTL 分级）**：会话管理 + TTL 是非常成熟的领域。FastAPI 有现成的 session middleware，Redis 更是标准方案。自研 SQLite TTL 分级会话，除非有特殊的"语义层感知会话"需求，否则属于纯造轮子。
- **独立审计模块（WORM+动作级）**：如果只是通用的 WORM 审计日志，SQLite 触发器 + append-only 表就能搞定，不需要独立模块。但如果是"本体动作级语义审计"（记录的是"哪个 LLM 对哪个本体对象执行了哪个动作，权限依据是什么"），那这是研究内容，自研合理。【我方判断】边界模糊，需要澄清是通用审计还是语义审计——前者砍，后者留。

## 六、三种真实执行中的死法

**死法 1：DuckDB 优化泥潭（死在 P2）**
P1 切片用小数据跑得很顺，P2 一加量级就发现 DuckDB 跨库 join 内存爆、物化慢、查询计划不稳定。团队陷入"加索引→换存储格式→调参数→还是慢"的循环，三周的 P2 拖成六周。等爬出来的时候，P3 映射治理和 P4 权限审计被压缩到几乎没有时间，最后带一堆技术债硬上线。

**死法 2：映射治理的死循环（死在 P3）**
"先全人工审积累数据，再定阈值"听起来对，但实操中是个鸡生蛋问题：自动化映射质量差→人工审核量大→团队审不过来→标注数据积累慢→自动化映射质量没法提升。100 万行级别的映射，人工审核是不可能全覆盖的。top-5 recall 80% 可能在 50 个测试问题上达标，但在真实场景下迅速掉到 50%，然后发现阈值校准需要的数据量比预期大一个数量级。

**死法 3：叙事空心化——S2 发布了，但没人看出和 S1 有本质区别（死在 P5）**
真实场景迟迟不到位，DES 数据再"真实"也是合成的。head-to-head 30 问全答对，但问题都是从 DES 生成规则反推出来的。白皮书写了六阶段框架，但每一阶段的论据都来自同一个合成数据集。发布 demo 时，观众的反应是"哦，数据变多了"，而不是"哇，这东西真能解决我业务里的问题"。研究价值和产品价值双双落空，S3 立项困难。
