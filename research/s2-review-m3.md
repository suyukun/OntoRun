## 一句话总评（BLUF）

S1 闭环证明了"能跑"，S2 复盘暴露的是"在真企业接入瞬间会在哪里崩"。A/B/C 分档是好治理，但 #5"待 Jack 提供真实场景"= 单点失败，整个 B 档（治理/权限/会话）有"为治理而治理"嫌疑。以下每议题至少一条 finding，标 P0/P1/P2。

## 逐议题 findings

### #9 DES 真实企业生成工具

**F9-1 形态锁定过早（P1）**
- 问题：1 企业=1 库 + 4 层继承（L0 行业/L1 规模/L2 企业内/L3 生成参数）。
- 为什么：S1 玩具期 1 库合理，S2 一旦跨企业比对/多租户，4 层继承解析 + 跨库 JOIN 直接报废；YAML 4 层继承 = 强耦合配置图，加新企业时配置维护成本随层数指数增长。
- 怎么改：先 1 层（行业模板），S2 内只增 1 层（企业内 L1），剩余进 backlog；测试 golden 集先建 3 企业 × 3 流程，再谈层数。

**F9-2 本体映射"做实"无验收口径（P0）**
- 问题：写"本体映射做实，第一阶段必做"，无 ground truth、无 precision/recall 指标。
- 为什么：映射错 = DES 退化为加大号 Mimesis，整个 ChatBI 上游语义都是脏的；"最小垂直切片 1 表+1 问题+1 映射"过小，做不出可信评估。
- 怎么改：定义 50 问题×3 业务领域的人工标答集，映射模块 ≥80% top-5 recall 才算 S2 入场券。

**F9-3 砍 NetworkX 但仍要"业务流程驱动"（P2）**
- 问题：技术栈砍了 NetworkX，又声称"业务流程驱动数据生成"。
- 为什么：业务流程是图，纯 Python 标准库写图遍历/拓扑排序/状态机效率差且易错，等于把"业务流"逻辑重写两遍（一次 DES 内部、一次本体 runtime）。
- 怎么改：业务流 = 状态机用现成库（transitions / statemachine），不用图库；如真要图分析再引 NetworkX，不要提前砍。

**F9-4 与 #1 量级断裂（P0）**
- 问题：DES 25 万行/季度 vs ChatBI 讨论的 PB；过渡路径（百万→亿→十亿）空白。
- 为什么：S2 上线半年内只要遇到真实大客户，DES→ChatBI 整条链路爆，且 DuckDB 集群化路径不清晰。
- 怎么改：定义两个量级 gate（100 万行 / 1 亿行），每个 gate 配 benchmark + 降级方案，gate 没过不接下一个。

### #1 ChatBI 智能分析

**F1-1 "受限结构化查询"= 自研查询语言，最大风险点无 PoC（P0）**
- 问题：LLM 不直接写 SQL，产出"受限结构化查询"。
- 为什么：受限 DSL/IR 实质是自研一套查询语言，工程量 ≈ 半个 dbt semantic layer；S1 没跑过 NL2SQL vs 受限 IR 的对比实验，凭直觉下注。
- 怎么改：S2 前 2 周先做 head-to-head：同一组 30 个分析问题，对比 NL2SQL + 守卫 vs 受限 IR，量化成功率/延迟/成本/可控性，再拍板。

**F1-2 "引用本体注册对象/指标"无主语（P1）**
- 问题：注册谁维护、版本化、冲突怎么办全部空缺。
- 为什么：本体注册表是 ChatBI 唯一可信源；S2 多 LLM provider / 多分析师并发改注册表 = 必然冲突。
- 怎么改：注册表走 Git 管理（schema-as-code）+ PR review 流程；与 #2 审核工作台共用 UI。

**F1-3 DuckDB + SQLite 双引擎引两套方言（P2）**
- 问题：源/写回 SQLite，分析 DuckDB，类型/函数/时区/null 语义全有差。
- 为什么：跨引擎时 Decimal 精度、时区、空值聚合行为是已踩坑高发区；DES→ChatBI 路径上必踩。
- 怎么改：定义数据流转契约（类型映射表 + 测试 fixture），跨引擎必跑 reconcile 测试。

**F1-4 性能/成本/并发预算空白（P0）**
- 问题：无 P95 延迟目标、无单查询成本上限、无并发上限。
- 为什么：PB 虽远，但百万行下的"用起来卡"是 S2 第一天就会被真实用户骂的点。
- 怎么改：S2 必交付三条预算线：P95 延迟 / 单查询 token 上限 / 并发 QPS，超出 = 降级（缓存/拒绝/排队）。

### #8 本体论落地方法论

**F8-1 "学位级"与"中小企可裁剪"定位冲突（P1）**
- 为什么：学术深度和落地裁剪通常不能在同一个文档里都做好，强行合并必有一方虚浮。
- 怎么改：拆成 2 个产物——主白皮书（学术骨架）+ 落地手册（中小企裁剪卡），引用关系而非互嵌。

**F8-2 数字配额是反方法论（P2）**
- 问题：十条铁律 + 反模式 Top15 + 十个开放张力点。
- 为什么：数字配额定下后必然凑数，凑出来的"开放张力点"会变成行业烂梗。
- 怎么改：去掉固定数字，写"涌现 N 条观察"，N 随材料长出。

**F8-3 S1 收官时已晚于最佳沉淀窗口（P1）**
- 问题：方法论随闭环"长出来"在 S2 阶段，但 S1 三问测试的鲜活细节（怎么失败的、为什么这样设计、卡在哪）会随记忆衰减。
- 怎么改：S1 收官时强制做一次"昨日重现"——3 个动作 1 周内从失败到通过的真实时间线，比 S2 二次回忆高保真 10 倍。

**F8-4 方法论 UI 与系统强耦合的"数字盆景"风险（P1）**
- 为什么：方法论 UI 每步展示"在系统里怎么跑"，但 S2 系统形态仍在变（DES/ChatBI/写回都未冻结），UI 必跟代码脱节。
- 怎么改：方法论 UI 只做"指针"——链到真实运行的命令输出和 git commit，不重做一遍可视化。

### #2 对象/动作规模化治理

**F2-1 "80% 自动"是愿望不是机制（P0）**
- 问题：未定义置信度阈值校准方法、未定义 ground truth 集、未定义审核工作台 SLA。
- 为什么：S2 真实数据接入，映射质量必跌；阈值不校准 = 全自动误判 = 脏数据进本体。
- 怎么改：先做 1000 条人工标答，分布拟合定阈值；审核工作台 SLA 24h，逾期自动降级到"高置信度"队尾。

**F2-2 S1 规模不够 vs S2 治理补齐是矛盾信号（P1）**
- 为什么：S1 已"三问测试通过"，到 S2 才补"映射自动化 + 审核"= 承认 S1 规模仅够演示；演示级通过 ≠ 规模化能力。
- 怎么改：在 #9 增加"映射规模化"作为 S1 收官后必做的"补课"前置项，不能等 S2。

**F2-3 校验两层 + 校验注册表 = 与 #8"可机验"同义反复（P2）**
- 为什么：#8 强调"可机验"治理测试，#2 又定义一遍"校验注册表"——同一概念两处定义，治理混乱。
- 怎么改：归一为 `governance/checks/` 单一注册表，#2 #8 引用，不重定义。

**F2-4 动作灰度缺失（P0）**
- 问题：动作白名单 + 模板库但无灰度/回滚/熔断。
- 为什么：动作新增 = 数据风险新增，无灰度 = 无 SRE 兜底；S2 一旦上线"删除"类动作，无熔断 = 真实事故。
- 怎么改：动作上线走 1%→10%→100% 三段灰度，每段配独立审计与回滚命令。

### #3 权限/鉴权

**F3-1 "未来单主体理想态"是伪命题（P1）**
- 为什么：业内共识是"人在回路"是 AI 操作企业的长期态，不是过渡态；保留接口 vs 预留长期架构是两件事，写法混了。
- 怎么改：删"未来单主体"描述，写"长期双主体，按行业合规要求演进"。

**F3-2 字段级权限 = 已知不可行 + 替代方案无证据（P0）**
- 问题：材料自承"字段级权限在 SQLite 不可行、DuckDB rls 有限——语义层承载是否足够"。
- 为什么：Palantir 在数据底层做行/列级，您在本体层做是绕开而非解决，CC/PA/PII 字段一旦要"按用户脱敏"语义层扛不住。
- 怎么改：明确"字段级脱敏在应用层做，语义层只声明策略"；脱敏组件独立可换（如接入 Presidio/阿里云脱敏服务）。

**F3-3 LLM prompt 注入 = 权限层旁路（P0）**
- 为什么：权限挂在本体对象/动作上，但 LLM 拿到 schema 即可绕过——这不是权限设计问题，是 LLM 不可信输入问题。
- 怎么改：动作参数做"显式白名单 + 类型/枚举校验 + 二次确认"三件套，LLM 输出当作不可信输入。

**F3-4 审计粒度未达合规线（P0）**
- 问题：写"会话 id 串审计"——这是会话级，等保三级/SOX 通常要求动作级 + 字段级 + 不可篡改。
- 为什么：S2 真实企业 PoC 必被问审计标准，会话级审计直接卡合规。
- 怎么改：审计设计独立模块（#4 不应承载），WORM 存储 + 动作级粒度 + 字段级前后镜像，先定标准再实现。

### #4 会话持久化

**F4-1 TTL 30 天硬编码 = 合规定时炸弹（P0）**
- 为什么：个保法/等保/SOX 对操作类系统留存要求远超 30 天，且不同数据类型要求不同。
- 怎么改：TTL 按数据分级可配置（审计/会话/分析分别设置），最小 7 年（与 #3 审计解耦设计）。

**F4-2 与 #3 审计重叠（P1）**
- 为什么：#4 说"会话 id 串审计"，#3 说"审计"，无单一事实来源。
- 怎么改：审计独立为 #10 议题（或归到 #3），#4 只管会话本身。

**F4-3 单表 + 30 天 TTL → 多实例/多副本下立即坏（P1）**
- 为什么：S2 单机自限合理，但 #5 真实场景一旦上多副本，会话粘性/分布式锁/跨实例读一致性问题全部冒出。
- 怎么改：会话存储接口抽象（Repository pattern），先 SQLite 实现，预留 Redis 切换路径。

**F4-4 messages 单表性能上限未说（P2）**
- 怎么改：超 100 万消息自动按 session 拆表/分区，给出明确边界。

### #5 真实场景试用

**F5-1 S2 唯一硬判据是"等 Jack"= 单点失败（P0）**
- 为什么：这是整个 S2 进度最大风险。其他 8 个议题在没有真实场景时只能造场景自测，治理与权限是否真有用 = 无人能回答。
- 怎么改：S2 开局即定真实场景的"兜底"——若 Jack 未提供，启用 S1 场景扩展（多企业/多流程）作为替代验证；不阻塞主线程。

**F5-2 真实场景"成功"无定义（P1）**
- 为什么：几场会议、几笔写回、几个真实流程？没标准 = 试用无限拖延。
- 怎么改：定义"试用通过 = 5 个真实业务问题在本系统被解决且源系统真变"。

**F5-3 DES→真实迁移成本未估（P1）**
- 为什么：DES 先行、真实后迁 = 长期两套数据规范并存，切换时本体要重映射、数据要回灌、SOP 要重写。
- 怎么改：迁移路径写明"回灌脚本+本体重映射+审计对比"三件套，不留到迁移日才发现。

### #6 CI + UX

**F6-1 "权限确认后真跑"语义不清（P1）**
- 为什么：是 GitHub Actions 资源配额？组织权限？Jack 个人账号？一句话 4 种解读。
- 怎么改：写明"GitHub Actions 公网仓库可跑/需自托管 runner/需 Jack 批准 secrets 范围"。

**F6-2 UX 推迟 = ChatBI 无法被真实评估（P0）**
- 为什么：UX"待试用反馈"= 无止境推迟；但 ChatBI 的"受限结构化查询"必须被真人试过才知道好不好用，这是 #1 的核心验证。
- 怎么改：S2 早期交付"能用的丑版本"ChatBI UI，可读可用即可，审美后置。

### #7 一键起

**F7-1 无凭据/凭据错误时无引导（P1）**
- 为什么：读 credentials 的 key 是单向读取，但用户最常卡的是"少配了一项、错配了一项"，没诊断输出。
- 怎么改：起服务前先 dry-run 校验所有凭据，给出"缺什么/在哪配"的可执行提示。

**F7-2 无幂等性与失败回滚（P2）**
- 为什么：一键起的真正价值是失败可回退；当前设计只管"起"，不管"退"。
- 怎么改：提供 `scripts/stop_dev.sh` + `scripts/reset_dev.sh`，起停回三件套。

## 跨议题矛盾（5 条）

1. **量级断层 #9 vs #1**：25 万行/季度 vs PB，中间的百万/亿级 gate 空白。
2. **审计重叠 #3 vs #4**：同一概念两处定义，治理混乱。
3. **方法论 #8 vs 系统 S2**：写回是闭环关键 vs 系统先 ChatBI 不做写回——"显式记录冲突"是延期不是治理。
4. **"不造轮子" vs 实际自研**：本体运行时 / 受限 IR / 置信度审核工作台 = 三件轮子，应明确"研究本身"边界。
5. **#9 DES 已知半自动 vs #2 外部未知全自动**：同一本体表达，难度差 10x，方法论不应共用一套话术。

## 过度/不足设计

【我方判断】**过度**：4 层 YAML 继承（先 1 层）、校验注册表（先 1 套）、数字配额铁律反模式。
【我方判断】**不足**：无 SLO/性能预算、无数据治理（保留/删除/合规）、无 LLM 成本与限流策略、无回滚降级、无数据血缘（对照 Palantir data-lineage）、未覆盖文档/文件/外部对象类型（真企业大量非结构化）。

## 真实落地 5 大死亡点

1. **真企业 ERP 字段非标 → 本体映射 80% 跌到 20%** — 真实接入瞬间 #2 审核工作台无人、无流程、无 SLA，所有 DES 整洁语义被真企业脏数据击穿。
2. **合规审计不过关** — 会话级审计 / 30 天 TTL / 无 WORM / 无字段级镜像，进等保三级或 SOX 评估必败，且补做周期 3-6 个月。
3. **LLM 成本与延迟失控** — 受限 IR fallback 路径 / token 上限 / 重试策略空白，1-2 季度账单失守；同时 DuckDB 单机在 P95 延迟上必被真实用户骂。
4. **DuckDB 单点 = 高可用零设计** — 真企业 PoC 第一问"你们 HA 怎么做的"直接卡死，且 DuckDB 集群化/冷热分层路径不清晰。
5. **写回冻结的延迟债** — S2 不做写回、S3 重启时 #2 #3 #4 全部要补，且要补的恰是 S2 跳过的"无法在玩具期验证"的部分；"显式记录冲突"是延期不是治理，欠债集中爆发。

## 最后一句

【我方判断】这份设计在"研究 demo 阶段"扎实度足够；跨入"生产 PoC"时漏洞密度极高。最该做的不是再细化九个议题，而是先冻结 #5 真实场景 + 合规边界（等保/个保/SOX），其他八个议题会自动重排优先级。在 S2 启动前，把"先定规则再动手"的铁律套在合规边界上，比套在编码规范上更有杠杆。
