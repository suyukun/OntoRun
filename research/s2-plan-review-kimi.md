# S2 开发计划平衡复核

【我方判断】这是一份**方向正确、风险认知清醒**的计划，但存在“阶段顺序与门控错位”“时间压缩过度”“生产跨越定义模糊”三个致命点，需在开工前调整。

---

## 1. 三条最强支持（为什么能成）

1. **量级降级诚实，避免了 S2 硬扛 PB 级分布式的自杀路线**  
   【输入】目标从 PB 降级到 100GB–1TB，并设 100 万/1 亿行 gate。这保住了 S2 的可行性：DuckDB 在该量级单机可跑，团队能把精力放在语义接口和映射治理，而不是分布式工程。

2. **风险前置：P1 先做最高风险项 DES 垂直切片**  
   【输入】P1 被标为“最高风险项，最先做”。这是正确的工程直觉：数据/语义/映射的不确定度远高于 ChatBI 和权限，前置能尽早暴露真实问题，降低后期返工半径。

3. **每阶段配可机验门禁，拒绝模糊验收**  
   【输入】SHA256 一致性、一物多码注入率 ±2%、head-to-head 30 问、映射 recall ≥80%、越权 0、审计不可篡改、一条命令 E2E。这些门控把“可信”从形容词变成可执行测试，符合 AGENTS.md“规则必须能机器验证”的铁律。

---

## 2. 三条最强反对（会死在哪 / 严重返工）

### 反对 1：P1 仍是“玩具切片”，与“生产跨越”目标存在张力
- **问题**：3 系统 × 1 表（MARA 类）+ 模拟数据，无法代表真实企业几十系统、数百表、一物多码/字段语义冲突/历史编码规则交织的复杂度。
- **为什么**：S2 量级敢降级到 100GB，但“生产跨越”的核心不是数据大小，而是**多源异构语义对齐的复杂度**。1 张表切片成功后，不能直接推广到几十张表。
- **怎么改**：① P1 扩展为 3 系统 × 3–5 张核心表（物料/工单/库存/BOM/订单）；② 或把 P1 重命名为“生产切片第一刀”，明确 S2 不完成全企业映射；③ 延长 P1 到 5–6 周。
- **优先级**：P0。

### 反对 2：P3 映射治理放在 P2 ChatBI 之后，顺序可能导致 P2 建在沙上
- **问题**：P2 head-to-head 实验需要语义层映射可信，但 P3 才做映射置信度、人工审核和阈值校准。
- **为什么**：如果 P1 的映射质量不高，P2 的 30 问成功率低会被误判为“LLM/prompt 问题”，实则是映射错误。最终 P2 可能陷入 prompt 调优泥潭，P3 返工时又得推翻 P2 语义层。
- **怎么改**：P2 先限定在“已验证映射”上跑通查询与物化；P3 负责规模化映射+置信度+审核。或者把 P2/P3 合并为“可信语义层 + ChatBI 闭环”，共 4 周。
- **优先级**：P1。

### 反对 3：P4 权限 + 会话 + 审计 1.5 周，且“不可篡改”承诺过重
- **问题**：P4 要同时落地数据权限下沉、语义层权限、独立审计 WORM、会话持久化，门控是“越权 0 + 审计不可篡改 + 会话重启不丢”。
- **为什么**：真正 WORM + 不可篡改审计需要独立存储、append-only 结构、哈希链/签名、校验机制，不是普通日志表。DuckDB/PostgreSQL RLS 与 SQLite 混合架构下，1.5 周只是设计时间。
- **怎么改**：① P4 拆为“权限模型设计（1 周）+ 审计会话实现（2 周）”，共 3 周；② 明确 WORM 实现：独立 append-only 文件/表 + Merkle/哈希链，并提供校验 API；③ 或把“不可篡改”降级为“防误删 + 校验和”，降低门控。
- **优先级**：P0–P1。

## 3. 我不确定 / 需要更多信息

1. **DuckDB 在 100GB–1TB 量级、目标查询模式下的真实表现**  
   【输入】计划提到 DuckDB 1.5.5 已验证读 SQLite/物化/parquet。但 1TB 级、多表 join、物化视图刷新、并发会话的实际内存/CPU/稳定性，需要 PoC 数据支撑。我不知道当前是否已有量化基线。

2. **“真实场景 #5”缺位的真实影响**  
   【输入】计划说“缺则 DES 兜底”。但 DES 本身是否足够真实、Jack 业务验收标准是什么， unclear。如果 #5 始终缺位，S2 是否仍算“生产跨越”，还是只是“更复杂的玩具”？

3. **团队实际执行者映射**  
   【输入】团队派活映射列出 6 个角色，但项目实际是“一人公司”。这些角色是子代理、Jack 本人、还是外部协作？人力并行度直接决定 10.5 周总排期是否可行。

4. **S1 写回债务对 S2 架构的影响边界**  
   【输入】写回明确搁置到 S3，但 P4 权限设计、P3 映射审核是否需要考虑写回权限与写回审计？如果现在不留接口，S3 可能重构 P4。

## 4. 跨阶段检查：依赖与顺序

- **依赖链**：P1 → P2 → P3 → P4 → P5，线性，无循环。依赖关系合理。
- **断裂点**：P3 门控要求“审核痕迹落审计”，但审计模块到 P4 才建。【输入】P3 产出含“审核痕迹落审计”，P4 才开始“独立审计模块”。这意味着 P3 验收时审计基础设施不存在，只能用临时日志充数。
- **顺序问题**：除 P3/P2 顺序外，P4 也应提前至少一个最小审计原型到 P2/P3，否则 P3 门控无法严格验收。
- **优化建议**：P1 建最小审计日志骨架 → P2 在审计日志上跑 ChatBI → P3 映射审核痕迹落入同一审计 → P4 加固为 WORM。

## 5. 过度规划 / 遗漏 / 重复造轮

### 过度规划（该砍）
- **P5 方法论 2 周可能过早包装**  
  【输入】P5 要产出“白皮书 v2 骨架（六阶段框架）+ 指针版 UI”。AGENTS.md 铁律是“方法论随闭环长出，禁止先写方法论”。S2 还没跑完就定“六阶段框架”，有先写方法论倾向。建议 P5 改为：① 沉淀真实运行素材；② 只输出方法论 v0.2 草稿，不对外称“框架”。
- **P4 三重目标 1.5 周过度压缩**  
  见反对 3。

### 遗漏（该加）
- **数据生成/扩容到 100GB–1TB 的具体方案**  
  没有说明如何从 S1 的 123MB 扩到目标量级：数据生成策略、存储、测试环境、成本。
- **量级 gate 不过的回滚/降级方案太笼统**  
  【输入】只有“缩小范围/抽样”。需要具体触发条件、回退到哪个阶段、保留哪些交付物。
- **真实企业数据接入的合规/脱敏/导入计划**  
  如果 #5 提供，如何接入？没有体现。
- **S1 写回债务对 S2 权限/审计接口的预留设计**  
  写回搁置不等于架构不预留。

### 重复造轮风险
- **ChatBI 语义层**  
  【输入】计划“参考 dbt 语义层模式”。应明确为什么不直接用 dbt-duckdb，自研点在哪里（本体映射层 vs 度量定义层），否则有重复造轮风险。
- **审计模块**  
  若“WORM”只是 append-only 日志 + 哈希校验，可用成熟模式；若重写完整审计数据库，则造轮。需界定范围。

## 6. 真实执行中三条死法

1. **P1 死在“真实感”上**：Jack 无法及时提供真实场景，DES 模拟数据又不足以暴露一物多码/字段语义冲突的真实复杂度，3 周后切片通过技术门控但业务验收不过，P2–P5 全部延期或建在玩具数据上。
2. **P2 死在 prompt 泥潭**：head-to-head 30 问成功率不达标，团队反复调 prompt，2 周拖成 4–6 周；根因实为 P1/P3 映射错误，但被误判为 LLM 问题，最终语义层被迫返工。
3. **P4 死在“不可篡改”承诺**：1.5 周内发现真正 WORM + 审计签名需要重构存储层，但 P5 发布临近，只能降级为普通日志 + 文档声明“未来补强”，M3 验收蒙混过关，留下 S3 重大债务。

---

**总结【我方判断】**：S2 计划的战略方向（降级量级、风险前置、机验门控）是对的，但**P1 切片深度不足、P2/P3 顺序颠倒、P4 目标过重且被低估**，是三处最可能在真实执行中引发返工甚至计划死亡的结构缺陷。建议开工前调整这三点，并明确真实场景 #5 的兜底标准。
