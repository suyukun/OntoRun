# S2 计划复核 · 汇聚（2026-08-21，4 模型平衡评估）

> 方式：skill v1.1（平衡评估版）审 S2 计划 v0.1——4 模型 pro/kimi/doubao/m3
> 结论：方向对（风险前置/量级诚实/机验门禁），但 3 处结构缺陷需开工前修。

## 共识改进点（≥3 模型一致，必须改）

### A1. P2↔P3 依赖倒置（4 模型一致，P0）
ChatBI head-to-head 建在"未经治理的映射"上 → 实验结论不可信，可能误导 D3。
**改**：P3 的映射置信度 schema + ground truth 标注规范**前置到 P1 末/P2 前**（做骨架，不做完整 UI）；P2 head-to-head 输出手工映射版 + 自动化初版两份数据。

### A2. 权限/审计架构约束后置（pro/doubao/m3 一致，P0-P1）
P4 才做权限下沉 + 审计，但 P1/P2 数据层设计没预留 → 后期补丁式返工。
**改**：加 **P1.5 治理骨架**（0.5 周）——权限元数据 schema + 审计最小骨架 + 映射置信度打标骨架；P4 只做完善实现。

### A3. head-to-head/ground truth 样本量小 + 无靶值（m3/kimi 一致，P0）
30 问撑不起统计意义；50 问×3 域人审+人标嵌套评估者偏差。
**改**：定成功率靶值（baseline ≥X% / 本体版 ≥Y% / Δ≥Z 百分点）；ground truth ≥300 问/域；标注 ≥2 人+仲裁。

### A4. P1 切片数据量不足支撑 P2（pro/kimi，P0）
200 行 MARA 跑不出有意义 P95/30 问。
**改**：P1 拆 P1a（切片验证 3 周）+ P1b（横向铺开 10-20 表 10 万行级 1-2 周）；P2 接 P1b。或 P2 先复用 S1 零售数据扩展。

### A5. DuckDB 规模化未实测（pro/doubao/m3，P0）
100GB-1TB 未经过实际工作负载验证（跨库 join/物化/内存）。
**改**：P1 末加"量级压力测试门禁"——1000 万行跑 5 个代表性查询测 P95/内存；不达标提前换方案。

### A6. 过度规划（3 模型一致，砍）
- 方法论"反模式 Top15"数字配额 → 改"事后提取不预设数量"；
- 方法论 UI 完整版 → 只做静态指针；
- P3 审核工作台完整 UI → 先 CLI/CSV 审核流程；
- 白皮书"六阶段框架"在 S2 前定稿 → 改"落地笔记/观察与反模式"。

### A7. 遗漏（多个模型）
- S1 回归测试门禁（每阶段 S1 全量 pytest 零回归）；
- 量级 gate 具体设计（内容/怎么测/哪阶段测）；
- 可观测性（metrics/tracing）；
- LLM 成本模型 + 单查询成本上限；
- rollback 计划（每阶段失败如何退）；
- 数据安全/PII 脱敏；
- C4 双引擎流转契约（SQLite→DuckDB 刷新机制）。

## 分歧（需 Jack 关注）
- D-团队产能：一人公司 6 角色 → 排期是否翻倍（Rose 判断：子代理并行可部分缓解，但 P1 切片串行为主）；
- D-真实场景 #5：DES 兜底 vs 升级为"P1 门禁一部分"（doubao 强烈主张升级）。

## 死法排名（4 模型）
1. P1 DES 数据"不够真"、Jack 业务验收不过 → P2-P5 全堵（3 模型）；
2. P2 head-to-head 失败/数据不足 → ChatBI 推倒或延期（3 模型）；
3. P4 权限/审计补丁式返工（2 模型）。

## 结论
计划改 4 处即可"从会爆变可控"：加 P1.5 治理骨架、head-to-head 加靶值扩样本、P1 拆切片+铺开、权限元数据 P1 同步设计。版本升 v0.2。
