## 一、逐议题发现

### #9 DES（真实企业生成工具）

**F1 — SQLite 单库 1 企业 = 1 库，但 DES 目标是"多系统"（ERP/财务/CRM/WMS）**

- **问题**：输入包 §2 #9 说"1 企业=1 库，规避单库膨胀"，但 §3 Jack 原话要求"按系统分别生成"。如果 1 企业 = 1 库，所有系统表挤在同一 SQLite 文件里，跨系统 schema 隔离靠命名约定——这正好是建模反模式"System Silos"的镜像问题（用前缀区分，而非物理边界）。
- **为什么是问题**：真实企业 ERP 和 CRM 是独立系统，有独立 schema、独立连接串、独立权限。把 4 个系统塞进同一个 SQLite 文件，生成出来的"企业"在系统边界上不真实，误导后续的映射治理（议题 2 练的是"跨系统映射"，但数据源只有一个文件）。
- **怎么改**：**1 企业 = 1 目录，N 系统 = N 个 SQLite 文件**（或至少 N 个 schema）。DES 输出 `des/output/{enterprise}/erp.db`、`crm.db`、`wms.db`。这是最小代价的真实感提升——S1 已证明双库可行（retail_source.db + ontology.db），DES 扩展到 4-6 库零技术风险。同时，DES 配置中"系统"应为独立节点，而非表的上级分组。
- **优先级**：P0（DES 尚未开工，现在改无返工成本；一旦开写再改，所有映射逻辑要重写）

**F2 — DES 4 层 YAML 继承 = 自研配置引擎，违反不造轮子铁律**

- **问题**：L0（行业模板）→ L1（规模）→ L2（企业内）→ L3（生成参数）4 层继承合并。这本质是一个配置合并/覆盖引擎，加上模板变量替换。JSON Schema + JSON Merge Patch（RFC 7396）或 YAML 原生的 `<<:` merge key 即可覆盖 90% 场景。自研 4 层继承 = 又造了一个配置 DSL。
- **为什么是问题**：输入包明确"成熟件优先、自研仅限本体运行时+映射"。4 层 YAML 继承不是研究对象，写它的代码量可能超过本体映射本身。而且 DSL 的 corner case（数组合并策略、深层覆盖、循环引用检测）会在实现中不断膨胀。
- **怎么改**：降为 2 层（行业模板 + 企业覆盖），用 JSON Merge Patch 或 YAML anchor/alias。去掉 L1/L3 两个中间层——它们的设计意图是"规模参数化"和"生成参数"，但实际操作中 L2 的企业覆盖直接覆盖 L0 即可，L1/L3 只是把覆盖拆成两步，无增量价值。如果确实需要参数化，用一个 `{{ var }}` 模板引擎（Python `string.Template` 标准库），不造新语法。
- **优先级**：P1（不影响核心链路，但会吃掉工期并增加维护负担）

**F3 — DES 25 万行/季度目标 vs ChatBI PB 级 = 量级断层，DES 不是"PB 的练兵场"**

- **问题**：输入包已知冲突 §3 明确写了"量级跨越路径未定"，但 #9 结论说"覆盖 DES 目标 4 倍以上"（100 万行/123MB）。25 万行 SQLite 跑得动，不代表 PB 级 DuckDB 跑得动——二者差 6 个数量级。DES 生成的数据不能在量级上验证 ChatBI 设计。
- **为什么是问题**：如果 DES 是 ChatBI 的"弹药"（议题清单明确说 DES→ChatBI 消费），那么 DES 生成 25 万行去验证 PB 级 ChatBI 架构，相当于用玩具车测试高速公路——ChatBI 的预聚合策略、分区、物化刷新频率，在 25 万行上全都不需要，测不出真实问题。
- **怎么改**：① 承认 DES 的量级上限（单机 SQLite 天然天花板在千万行级），不宣称 DES 验证 ChatBI 的量级能力；② ChatBI 的 PB 级验证另辟路径——方案 A：DES 增加一个"规模膨胀模式"（按配置的参数 N×放大已有数据，相同分布、不同基数，DuckDB 直接生成 Parquet，不进 SQLite）；方案 B：拉真实公开数据集（如 TPC-DS/TPC-H 的 PB 级实例）作为 ChatBI 的独立压力测试，DES 只验证"语义正确性"。
- **优先级**：P0（这是 S2 最核心的叙事裂缝——"我们从玩具跨到生产"的前提是量级，而量级验证根本没设计）

### #1 ChatBI（智能分析）

**F4 — "LLM 不直接写 SQL，产出受限结构化查询"——受限到什么程度，形态未定义**

- **问题**：输入包说"LLM 产出受限结构化查询，本地引擎执行"。但"受限结构化查询"的 schema 是什么？是 JSON 表示的过滤条件（`{object: "Order", filters: [...], aggregations: [...]}`）？还是受限 SQL 子集（SELECT+WHERE+GROUP BY，禁 JOIN/子查询）？还是 DSL？这是 ChatBI 形态的核心，输入包只说了"是什么"（结构化），没说"具体是什么"。
- **为什么是问题**：如果不定义结构化查询的 schema，后续三个议题（#2 映射、#3 权限、#8 方法论）全部悬空——映射不知道要映射到哪种查询语法，权限不知道要拦截哪种查询模式，方法论不知道"本体→查询"的桥是什么。
- **怎么改**：定义结构化查询的 JSON schema（至少 v0.1 草案），字段：`object_type`、`filters`（字段+操作符+值）、`aggregations`（聚合函数+字段+可选的 GROUP BY）、`link_traversal`（沿链接到关联对象，最多 1 跳）。这个 schema 就是"本体→分析引擎映射"的契约。优先级高于 DES 垂直切片中的 ChatBI 查询实现——先定契约，再实现。
- **优先级**：P0（ChatBI 形态已定但核心契约缺失，现在不定后面必返工）

**F5 — DuckDB 单节点 vs PB 级，架构缺口存在**

- **问题**：DuckDB 是单机 OLAP（虽支持多文件并行读取，但无分布式）。PB 级数据 DuckDB 单机跑不动（内存/磁盘 I/O 都会成为瓶颈）。输入包说 DuckDB 是"穷人版分析内存库"，但 SAP HANA 是共享内存多节点，DuckDB 不是。
- **为什么是问题**：S2 的核心叙事是"从玩具到生产（几百 TB~PB）"，但选的分析引擎在 PB 级根本不成立。DuckDB 在 100GB 级表现优秀，但 100GB 到 1PB 差 10000 倍。
- **怎么改**：两种路径：① 诚实降级 S2 量级目标为"100GB-1TB 级"（这仍然远超 S1 的 123MB，且 DuckDB 完全胜任），PB 级留到 S3 讨论（引入 Spark/Daft/ClickHouse 等分布式引擎）；② 在 DuckDB 之外预留分布式接口（如 Apache Arrow Flight SQL），但 S2 不实现。**推荐①**——S2 从 123MB→25 万行 SQLite→1TB DuckDB 已经是 3 个数量级的跨越，足以证明"量级"。
- **优先级**：P0（S2 定位锚定在 PB 但引擎选型不支持，必须修正两者之一）

### #8 方法论（本体论落地方法论）

**F6 — "反模式 Top15 + 十个开放张力点"在 S2 开工前拟定 = 先写方法论再落地**

- **问题**：输入包 §2 #8 说方法论包含"反模式 Top15 + 十个开放张力点"，但 S2 尚未开工。这 15 个反模式从哪来？S1 只覆盖了 1 条零售供应链、8 对象/6 动作，远不足以支撑 15 个反模式。剩下的只能来自"设想的反模式"或"Palantir 文档的二手转述"——恰好是项目自身铁律"方法论从落地里长出来，禁止先写方法论再落地"所禁止的。
- **为什么是问题**：这是 S2 设计中最隐蔽的自相矛盾。输入包 §1 "不造轮子铁律"下方紧跟着 §2 #8 描述方法论三层（含反模式 Top15），但输入包自身在 §3 也承认方法论"冲突显式记录"。如果现写反模式，它们会在 DES/ChatBI 落地后被证伪；如果等落地后再写，现在就不该列入交付物。
- **怎么改**：方法论三层调整为两阶段交付：① S2 期间只做"方法论交互 UI"（绑定真实运行系统，展示每一步，这是差异化点）+ 白皮书 v2 骨架（六阶段框架，不填反模式）；② 反模式 Top15 和开放张力点从 S2 落地中**事后提取**（DES 生成→映射→ChatBI 全链路跑通后，自然涌现哪些模式反复踩坑），不预设。这正好兑现"方法论交互 UI 防数字盆景"的承诺——反模式必须有真实案例支撑。
- **优先级**：P0（设计自身的逻辑自洽问题，影响方法论的公信力）

**F7 — 方法论 UI "绑定真实运行系统"——但 S2 搁置了写回，运行时只有读侧**

- **问题**：输入包 §3 已知冲突明确写"系统 S2 搁置写回（先 ChatBI）"。但方法论 UI 要展示"每一步在系统里怎么跑"——如果写回（Action）是方法论六阶段中的"应用赋能"核心，而系统里根本没有跑写回，那 UI 展示的"真实运行"就是残缺的。
- **为什么是问题**：方法论交互 UI 是 #8 的最大差异化点（"业界空白"），但它的核心卖点"绑定真实运行系统"在 S2 只能展示读侧。这会让方法论 UI 退化为"静态图文 + 一个只读查询的 GIF"——恰好是它要反对的"数字盆景"。
- **怎么改**：① 方法论 UI 在 S2 只展示"已跑通"的阶段（数据映射→本体构建→ChatBI 读侧），不展示 Action 写回；② 在 UI 上显式标注"写回闭环见 S1 演示（三问测试）"，用 S1 的录屏/回放来补这个缺口，而不是假装 S2 有写回。诚实 > 完整。
- **优先级**：P1（方法论 UI 是 S2 后期交付，DES/ChatBI 先跑通，有时间调整范围）

### #2 对象/动作规模化治理

**F8 — "80% 自动 + 20% 人审"缺置信度阈值与验证闭环**

- **问题**：输入包 §2 #2 说"高置信度自动过，低置信度进审核队列，~80% 自动+~20% 人审"。但没有给出置信度模型、阈值设定方法、以及最关键的反查机制——自动过的 80% 里有多少是错的？（假阴性率）这个数字不测，80% 就是拍脑袋。
- **为什么是问题**：映射自动化是 S2 最核心的工程挑战（Palantir FDE 最有价值的工作）。如果 80% 自动过但误判率 10%，意味着每 100 个映射有 8 个错误——这些错误会污染本体，进而污染 ChatBI 查询结果和权限判断。S2 没有设计"映射正确性验证"的闭环（比如：用 ChatBI 的查询结果反查映射是否有误）。
- **怎么改**：① 在 DES 垂直切片中，用已知 ground truth 的映射（DES 自带语义 = 答案已知）测置信度模型的精确率/召回率，定出阈值；② 设计"映射审计查询"——ChatBI 跑一批已知答案的查询，反向验证映射是否有误（如果"客户数"查出 0 或异常大，触发映射复核）；③ 把 80% 从"目标"改为"实测后设定"。
- **优先级**：P1（DES 垂直切片中可一并验证，不阻塞 DES 开工）

### #3 权限/鉴权

**F9 — "字段级权限在语义层承载"——但语义层没有字段级强制执行点**

- **问题**：输入包 §2 #3 说"权限做在语义接口层，不依赖数据库层"，粒度"对象级 + 属性（列）级"。但语义接口层（FastAPI routes）的拦截点在哪？如果是 API 响应序列化时掩码字段——那 LLM 通过本体 schema 元数据（GET /meta/schema）已经看到了所有字段名和类型，掩码响应体只是"不给看值"，但"知道有这个字段"本身就是信息泄漏。
- **为什么是问题**：字段级权限的本质是"不知道该字段存在"。SQLite 做不到，DuckDB 的 rls 扩展只做行级，语义层如果不控制 schema 元数据的暴露，字段级权限就是"遮住值、露出名"——在金融/医疗等合规场景下不满足"字段级脱敏"要求。
- **怎么改**：① 字段级权限 = 三层联动：schema 元数据（不暴露无权字段名）+ 查询层（DuckDB 不 SELECT 无权列）+ API 响应（双重保险）。② 承认 S2 字段级权限在 SQLite 上不可行，降为"对象级权限 + 属性级标注（字段标记为敏感但不强制拦截）"，真正的字段级权限列为发布期 PostgreSQL（列级 GRANT）+ DuckDB 列屏蔽。③ 在方法论中诚实记录这个限制，不假装已解决。
- **优先级**：P0（权限是"可信"要素，声称有但实际做不到比不做更危险——虚假安全感）

**F10 — 双主体权限（Agent + 人）边界模糊，审计链断裂**

- **问题**：Agent 操作 + 人审核，但输入包未定义：① Agent 的操作是否需要人实时确认？还是事后审计？② 如果 Agent 做错了，人审核通过，责任归谁？③ 审计日志里，Agent 的操作 actor 是 `llm` 还是 `human`（审核人）？S1 的 actor 枚举只有 `human/llm/api`（TD-9），双主体下一条操作链（Agent 提议→人批准→执行）的 actor 应该是复合的。
- **为什么是问题**：没有责任边界，审计在合规场景下就是废纸——"谁干的"答不出来，权限模型就只是学术练习。
- **怎么改**：① 审计日志扩展为"操作链"：`initiator: llm` + `approver: human` + `executor: api`，三条记录关联同一 `request_id`；② 双主体权限明确为"Agent 的权限是人权限的子集，人可随时否决"——这是最简单且可审计的模型；③ 单主体演进路径保留但 S2 不实现，不写进方法论当承诺。
- **优先级**：P1（S2 主要是读侧，Agent 写回搁置，有时间设计）

### #4 会话持久化

**F11 — SQLite 单表 session 并发写——S2 是单机单用户，但设计没声明这个前提**

- **问题**：SQLite 单表 sessions + messages 在单用户单线程下没问题。但设计文档没说"这是单用户假设"。如果方法论 UI 或 ChatBI 将来被多人同时访问（比如演示时两个人同时开浏览器），SQLite 的写锁（同一时间只允许一个 writer）会导致会话写入排队/失败。
- **为什么是问题**：输入包没声明"单用户"前提，未来如果有人基于这个设计做多用户扩展，会踩坑。而且 SQLite 在 WAL 模式下读可并发，但写仍然串行——如果 ChatBI 查询产生大量会话消息写入，与 DES 生成同时跑，可能互相阻塞。
- **怎么改**：① 在议题 4 形态结论中显式加一句"S2 假设单用户单会话，SQLite 足够；多用户场景发布期迁 PostgreSQL"；② sessions 库和 DES 生成库分开（S1 已有双库，再加一个 session.db 零成本），避免会话写入阻塞 DES 读取。
- **优先级**：P2（单机单用户下无实际问题，文档补一句即可）

### #5 真实场景 + #6 CI/UX + #7 一键起

**F12 — #5 "真实场景试用"被列为硬判据，但依赖 Jack 提供的场景尚未出现，整个 C 档是空壳**

- **问题**：输入包 §2 #5 状态是"贯穿；候选场景待 Jack 提供"。作为 S2 硬判据，它目前是零信息量。而且 #5 与 #9（DES）"互为表里"——但如果 Jack 的真实场景是金融风控，DES 生成的制造业数据（MARA 物料主数据）就没法复用。
- **为什么是问题**：C 档的三个议题（#5/#6/#7）加起来不到 10 行描述，但 #5 被标注为"硬判据"。如果 #5 迟迟不定，S2 的"真实场景验证"就是空头支票。
- **怎么改**：① 把 #5 从"待 Jack 提供"改为"S2 中期由 Jack 给一个候选场景的 1 页描述（行业/系统/表/问题），DES 按此方向调整"；② 如果 Jack 在 DES 垂直切片完成前仍未提供，#5 降级为 S2 不验证，DES 自身作为 S2 的"真实场景"（DES 生成的企业够复杂，本身就是场景）。不能让一个待定项卡住 S2 的硬判据。
- **优先级**：P1（DES 开工前需要知道目标行业，否则生成方向可能白做）

## 二、跨议题矛盾

**X1 — #1 ChatBI（预聚合优先）vs #8 方法论（脊柱之问：为 Agent 而建的建模范式）**

方向宪法 §3 的脊柱之问是"当消费者从人变成大模型，建模范式必须变"。但 #1 ChatBI 的答案是"预聚合优先，物化指标，LLM 查物化结果"——这是标准的 Kimball 维度建模 + 语义层，正是"为 BI 而建"的范式。如果 LLM 最终查的是物化聚合表，那建模范式没有变——只是查询接口从 SQL 变成了 LLM→结构化查询→SQL。脊柱之问的答案在 S2 设计里没有体现。【我方判断】ChatBI 的形态是务实正确的，但需要承认"预聚合优先"与"为 Agent 而建的新范式"之间存在张力，不是方法论一句话"本体是运行期语义层"能消解的。

**X2 — #9 DES（模拟企业）vs #2 治理（外部真实数据）**

议题 2 说映射对象"两者都要"：DES 数据（半自动）+ 外部真实数据（全自动推断）。但 DES 自带语义（表名/字段名/关系都是生成器已知的），映射 DES 数据根本不需要"自动推断"——生成器直接输出映射配置即可。这导致议题 2 的"80% 自动推断"能力在 DES 数据上无法验证，必须等外部真实数据。而外部真实数据来自 #5（真实场景），#5 尚未定。【我方判断】议题 2 的验证应该分两阶段：先用 DES 验证"映射工作台"（审核流程 UI），再用外部真实数据验证"自动推断"（置信度模型）。两者不能混在一起说"80% 自动"。

## 四、风险：这个设计会在真实落地里死在哪个阶段

**R1 — DES 方向偏航（开工第 2 周）**：#5 真实场景未定，DES 按制造业（MARA）生成，Jack 提供的真实场景是金融或零售——DES 垂直切片白做，横向铺开方向全错。**概率：高**（#5 是已知待定项）。

**R2 — ChatBI 量级叙事崩塌（DES 完成后的第 1 次演示）**：DES 生成 25 万行 SQLite，ChatBI 的 DuckDB 物化查询在 25 万行上秒级返回。有人问"PB 级呢？"——没有答案。DES→ChatBI 全链路在功能上通了，但 S2 最核心的"量级"叙事没有证据支撑。**概率：极高**（见 F3/F5）。

**R3 — 方法论成为"数字盆景"（S2 收口时）**：方法论 UI 展示的是"一个表→一个映射→一个 ChatBI 查询"的最简路径，没有写回闭环，没有多系统跨库，没有脏数据降级。它恰好是方法论自己反对的"数字盆景"——看起来完整，但缺了真实企业的所有 messy 要素。**概率：中高**（见 F7，但可通过诚实标注范围缓解）。

**R4 — 权限模型在字段级上被证伪（S2 演示时）**：演示时有人问"这个字段我权限不够，能告诉我它叫什么吗？"——GET /meta/schema 返回了所有字段名。字段级权限声称已做但实际只掩码了值，被当场指出。**概率：中**（见 F9，取决于演示观众的挑剔程度）。

**R5 — 映射自动化 80% 被 DES 数据"假验证"（议题 2 收口时）**：DES 自带语义（已知映射答案），置信度模型在 DES 数据上轻松达到 95%+。但接到真实外部数据（#5 尚未定）后，自动映射率掉到 40%。80% 变成不可复现的数字。**概率：高**（见 X2——DES 数据与外部数据的语义完整度天差地别）。
